# P2 执行器与运行状态详细设计

> 本文定义执行器的状态传播、非阻塞调度、单 act 控制权、查询、停止与故障恢复规则。配置参数是实现起点，不是实测性能保证。
>
> 关联：[主架构](ARCHITECTURE.md)、[接口契约](CONTRACTS.md)、[扩展生命周期](BEHAVIOR-LIFECYCLE.md)。

## 1. 执行责任与进程

每个 body 首版只绑定一个角色，由人工 start 后的 bridge 创建并持有，使用 stdio 通信；调度仍在独立 body 进程内执行，不等待模型。一个串行调度器推进一棵 behaviorTree，至多一个 act 持有控制权。模型推理、文件编译、只读查询等待不占用该控制权。

body 中的可信执行器只运行内置控制结构和有界表达式求值，不直接调用 agent 生成的任意 JavaScript 回调。behavior 构建在独立构建进程完成；自定义 act 在独立运行进程中执行，通过消息请求 op。树调度、操作归属和错误处理仍由唯一 body 执行器决定。隔离进程并不引入并行行为树或两个控制 act。

operation broker 是可信基础库的一部分：校验调用、记录持续操作、向选定实现转发请求、执行清理。act runner 不能直接持有游戏连接。停止时，即使 runner 挂起，broker 也知道需要撤销哪些操作。具体游戏线程调度由 operation 实现完成。

首版使用一个可重建的 act runner，串行接收当前 act 的生命周期调用；同一时刻不执行两个 hook。模块构建和候选检查使用另一个一次性进程。进程创建、加载与握手在授予动作控制权前完成，不将冷启动耗时藏入 act 的停止预算。

## 2. 三组独立状态

### 2.1 节点运行状态

`idle → running → succeeded | failed`；取消则 `running → stopping → cancelled`。没有进入过的节点无需为了取消先执行初始化，可作为未执行节点丢弃。

- 成功、失败、取消都是已收尾终态。正常结束但正在收尾时仍是 running，附内部阶段 `finishing` 和预期结果；取消时为 stopping。
- 同一次运行不能从终态回到 running。repeat、重试或重新进入创建新的 nodeRunId。
- 父节点只在活动子节点完成收尾后传播终态；失败原因带原始节点路径。
- 晚到结果不能改变已完成的 nodeRunId。持续效果的迟到确认只能交给 broker 对账，不能重新驱动树。

### 2.2 behavior 实例状态

| 状态 | 规则 |
| --- | --- |
| running | 推进树、查询完成条件或执行收尾。 |
| blocked | 已完成动作收尾，无控制 act，等待明确外部输入。 |
| succeeded | 有限目标已获满足证据，收尾完成。 |
| failed | 无法继续，收尾完成。 |
| cancelled | 被停止或替换，收尾完成。 |

queued 是切换请求状态，不是已经运行的 behavior。blocked 默认不自行恢复、不轮询重试，不自动超时；允许查询、取消或替换，不占角色控制权。外部恢复创建新的运行实例并重新读取当前事实，首版不恢复任意节点栈。

`blocked/CONFIRMATION_REQUIRED` 是已完成执行后的外部验收：有效确认或否定直接结束原实例，不恢复树执行。它与普通 blocked 后重新启动执行不同，具体见[外部完成验收](#44-外部完成验收)。

持续 behavior 的树根成功，默认仍不能报告业务成功：将其结束为 `failed/CONTINUOUS_TREE_ENDED`，提示作者使用 repeat 或显式等待。有限 behavior 的根成功但最终完成条件为 false，返回 `failed/GOAL_NOT_MET`；需要继续努力必须在树中显式表达。

### 2.3 执行器健康与连接状态

健康状态为 ready、stopping、faulted、recovering；连接状态单独记录 disconnected、connecting、connected。faulted 不伪装成普通 behavior failed/blocked，尚未确认停止的实例保持原运行/停止阶段并附故障。

一旦故障使控制权不确定，所有新的控制 act 都暂停。只读查询和诊断在实际连接允许时继续；“查询接口仍存在”不保证断开的游戏可被查询。

## 3. 每轮调度与资源上限

按单调时钟安排 tick；不把墙钟跳变用于超时或有效期判断。每轮顺序固定：

1. 在轮首固定已到达结果与命令的批次，依 ingressSeq 排序并校验归属；更新操作账本，暂存待处理结果。本轮推进期间到达的消息留到下一 tick。
2. 处理本批有效的人工停止、切换、失联撤销和故障；在推进业务结果或启动新动作之前应用取消请求。无效命令不能打断当前运行。
3. 推进已开始的清理，检查总期限。停止期间不启动普通控制操作。
4. 更新查询等待、完成判定与活动路径上的反应式条件。
5. 按选择结果请求分支切换，或串行推进树与当前 act；合格的局部写入立即生效。每次启动新 act 和提交终态前经过统一检查点，不等待外部 I/O。
6. 汇总并发布状态变化和必要事件；轮末不再统一提交 locals，也不回滚本轮已经成功的写入。

D2 采用执行器内部顺序可见：符合 [D1 写入规则](#43-局部状态与结果写入)的值写入后，同一 tick 的后续节点立即读取新值。单次 assign 原子替换，但一个 tick 不是事务；后续节点失败不撤销此前成功的赋值。尚未就绪的 query 或尚未成功收尾的 act 不能提前发布输出。

每轮最多 200 次节点转移，可信调度处理时间目标 10ms；预算耗尽则让出，不把整棵树判为失败。repeat 的下一轮至少推迟到下一 tick。错过 tick 后不进行无限补跑，记录调度延迟并使用当前时间处理超时。

事件监听器只能入队，不能在回调中重入树、写 locals 或提交终态。本批有效取消优先于本轮尚未提交的终态，不以成功消息在批内排得更早为由抢先成功。批次固定后到达的取消在下一 tick 处理；若届时实例已终态，返回 alreadyTerminal。统一检查点使用本批已处理事实及当前单调时间检查 owner 授权、bridge 存活期限和数据有效性，不中途吸收下一批消息。

### 3.1 新动作与终态的统一检查点

启动新 act 前，确认无取消或故障、旧控制已释放，并检查有限目标的 predicate 完成条件及活动路径上的 reactivePriority guards。externalConfirmation 不要求每个动作前取得外部确认。条件评估使用当前 locals 和仍有效的观测；依赖未变且证据仍新鲜时可复用，不要求每个动作前无条件重查。必要条件 pending、过期或未就绪时不启动新 act，条件 error 进入失败/显式恢复流程，不能按 false 放行。

提交节点或 behavior 终态前，统一检查其归属、已处理取消、错误与结束意图以及应有的收尾证明；behavior 的成功还须满足最终完成确认。已选择的普通分支不因这个检查点重新执行一次性 if；反应式条件才持续参与分支选择。检查和纯表达式求值计入本轮预算，预算耗尽则让出，不能跳过检查点。

## 4. 控制结构的完整规则

| 节点 | 进入／推进 | 终止与取消 |
| --- | --- | --- |
| sequence | 记住子节点索引；成功后推进下一个。空列表成功。 | 一个失败则停止；活动子节点取消完成后才能结束父节点取消。 |
| if | 一次进入求值条件；unknown 等待，true/false 选择对应分支；未提供 else 等于空 sequence。 | 传递所选分支结果。条件查询失败则失败，不当作 false。 |
| reactivePriority | 有序 guards；检查到首个 true 即短路；首个 unknown 阻止选择其后的新分支。 | 选中分支成功/失败成为本次节点结果；无分支适用为 NO_BRANCH，不吞执行失败。 |
| repeat | 子节点成功后下一 tick 新建子运行，可有限次数或持续循环；有限 0 次成功。 | 失败默认传播；持续循环不会自然成功；取消当前子运行后结束。 |
| subtree | 内联可复用定义，进入时捕获只读输入、创建独立局部帧和运行标识；构建展开仍保留帧及输入/输出映射，拒绝递归引用环。 | 根成功后校验并发布声明输出；失败或取消不发布，重新进入创建新帧。 |
| assign | 求值受限表达式，完整校验后替换当前帧的目标 local，不占控制权。 | 求值或校验失败则失败，保留原值；不产生部分更新。 |
| query | 输出槽标记为待产出，仅一次请求，通过归属、schema、完整性及新鲜度校验后写入。 | 失败、超时、时效不合格返回原因，不发布成功输出、不自动再次查询。 |
| act | 输出槽标记为待产出；先加载 runner，再授予控制权，启动并推进一次运行。 | 业务成功且结果合法，在 act 和 broker 双重收尾确认后发布成功输出并结束；其他结束路径不发布成功输出。 |
| wait | 等待声明的单调时间，不占动作控制权，不阻塞调度。 | 到期成功；取消立即完成。 |
| recover | 仅捕获明确列出的子树失败码；依据声明选择有限重试、备用子树或 blocked。 | 未列出的失败直接传播；取消和 executor fault 不作为可恢复子树失败。 |

recover 是统一控制结构，不是让执行器自行猜测策略。声明重试须同时给出最大追加次数、间隔和本恢复范围总期限；总期限从初次进入开始，清理也计入。没有声明则重试次数为 0，默认失败。超预算以 `RECOVERY_EXHAUSTED` 结束并保留最后原因。

### 4.1 反应式重新评估

祖先 reactivePriority 在 act 运行时仍被调度。只评估 guards，不执行未选中分支的动作。高优先级 guard 变为 true 时，先停止旧分支再进入新分支；旧分支取消不使 selector 本身取消。

重新评估使用独立 evaluationId，查询结果不混用到其他评估轮。等待期间当前 act 可继续内部推进，但其结束后不基于 unknown 或过期条件启动下一个 act。低优先级条件的未知不能推翻已经确定的高优先级 true。

条件记录所依赖的 local 槽位及版本。写入或输出槽变为未就绪后，依赖它的旧判定失效；在下一检查点重算。若查询参数、归属和有效性均未变化，可在同一有效 evaluation 中仅重算纯表达式；查询参数变化则创建新 evaluationId，旧评估结果不能满足新参数。查询失败不会被 local 更新或下一 tick 自动重试掩盖，仍须按显式恢复规则处理。这些依赖规则也适用于完成条件。

一旦开始停止，条件恢复也不撤回停止。切换目的地可被新结果替换，但不能启动新 act。停止完成后重新确认候选 guard；过期则发起新一轮正常评估，不使用已失效授权。

默认没有最短驻留时间，不用驻留规则阻止更高优先级分支。作者可显式用状态、等待或不同阈值避免抖动；核心不自动增加游戏策略。

### 4.2 完成判定

采用 predicate 的有限 behavior 进入时、根结束时以及声明的检查周期读取完成条件，并在新 act 启动前按统一检查点确认判定仍有效。它是只读的；查询失败按正常失败/显式恢复处理。条件为 true 且通过结束裁决后锁定“准备成功”，停止后续动作并收尾。

收尾后再进行一次完成确认，使用新鲜证据：true 则 succeeded；false 则 GOAL_NOT_MET；查询失败则按声明进入 blocked 或 failed。对“曾达到某累计里程碑”的目标，可用实例局部累计证据表达；不能把“现在拥有”悄悄改成“曾经拥有”。

因目标已满足而停止活动子树，与人工取消整个behavior不同：子act可以被取消，但behavior保留准备成功的结束意图，最终仍由收尾后的完成确认决定。人工取消、节点失败、目标完成各有独立结束原因，不能只沿用子节点的cancelled来判断业务结果。

不能自动判断的目标必须声明 externalConfirmation：仅在树根成功且 act 与 broker 均确认收尾后，进入 blocked/CONFIRMATION_REQUIRED，由明确归属的外部命令确认或否定。确认事件注明来源，不能伪称游戏查询已证明完成。根失败、取消及持续 behavior 不进入完成验收；详细规则见[外部完成验收](#44-外部完成验收)。

#### 同轮结束原因的裁决

控制健康与业务结果分开判断。控制权释放尚未确认时，保留结束意图和原始诊断，继续收尾而不提交终态；确认清理失败、期限耗尽或控制结果不确定时，按既有规则进入 faulted。不能将故障直接折算成 succeeded、failed 或 cancelled。以下顺序用于尚未锁定结束意图时，对本批已接受事实及本轮求值结果进行裁决：

| 优先顺序 | 情况 | 处理 |
| --- | --- | --- |
| 1 | 实例此前已提交终态 | 终态不变；晚到停止返回 alreadyTerminal，旧结果不再驱动树。 |
| 2 | 有效 stop、switch、shutdown 或 owner 授权撤销 | 取消意图优先；完成收尾后 cancelled，同时保留已发现的失败诊断。 |
| 3 | 未被显式恢复处理的程序或契约错误 | 失败意图优先，不能用目标成立掩盖表达式异常、act 运行异常或结果 schema 不合法。 |
| 4 | 有限目标 predicate 有效为 true，无竞争失败或仅有普通环境失败 | 准备成功，保留已有动作失败记录；收尾后仍须最终新鲜确认。 |
| 5 | 普通节点失败，没有有效的目标达成证据 | 按声明 recover 或传播失败，不把 pending/error 当作完成证据。 |
| 6 | 无需结束 | 继续运行或等待。 |

普通环境失败指契约明确的 PATH_UNREACHABLE、MATERIAL_MISSING 等业务阻碍。不能只凭错误 category 或 retry 字段把程序错误、未知控制结果或任意 timeout/transport 错误归入此类。例如背包目标已由有效查询确认满足，即使寻路同时报告不可达，behavior 仍可准备成功；这不改变寻路 act 自身的失败，也不发布它的成功输出。完成查询本身失败仍按完成判定规则处理，不复用失效的 true。

同批竞争事实先参与裁决，再锁定结束意图，不能逐条消息先到先提交终态。锁定成功或失败意图后，不再启动业务节点；晚到的普通结果不能反转它。终态提交前新处理的有效取消仍可覆盖该意图；控制故障阻止提交并保留意图，准备成功仍受最终确认约束。因目标满足而停止子树不等于取消整个 behavior。externalConfirmation 的确认、否定及去重遵循 [D3 外部完成验收](#44-外部完成验收)，同样不能绕过有效取消和控制故障。

### 4.3 局部状态与结果写入

数据契约见[数据归属与寿命](CONTRACTS.md#31-数据归属与寿命)和[显式赋值与成功输出](CONTRACTS.md#32-显式赋值与成功输出)。执行器统一维护局部帧；作者通过 assign、query/act 输出绑定、子树输出声明表达写入，不能直接修改帧对象。

behavior 参数在实例内只读，behavior locals 在同一实例内跨循环与分支切换保留。子树每次进入捕获输入并初始化独立 locals；等待期间保留，结束后或取消后重新进入不沿用旧帧。跨子树调用的累计状态必须显式保存在外层并通过输入/输出传递。新 behavior 实例重新初始化，不恢复旧局部栈。

调用进入时先固定输入，再将其输出槽标记为待产出；这不清空同一帧中的其他普通 locals。结果只由当前生产者运行写入，重复、已取消或旧 epoch 的结果不能发布。读取未就绪输出与合法 null/空结果不同，不得使用上一轮结果填补。

assign 的求值和 schema 校验全部通过后才替换值；失败保留原值。query 先完成归属、完整性和新鲜度校验；act 则先保留合法的业务候选结果，待成功收尾确认后发布。任何失败或取消都不发布本次成功输出；broker 仍按控制契约处理已经发生的动作效果。子树只在成功结束且返回结果合法时向调用者发布声明输出。

每次节点运行最多完成一次对应写入；重复结果不得重新触发后续 assign。正常 repeat 或显式重试的新运行仍可执行自己的写入。元数据随当前观测的赋值、派生和传递保留，不能用写入时间延长数据有效期；策略计数及历史执行证据按各自含义处理，不统一套用观测有效期。

写入后同轮后续节点立即可读，相关条件依赖随之失效并在检查点重新确认。这里只保证变量写入的可见性，不保证其中的游戏观测仍代表最新环境；消费时仍须独立校验时效与作用域。

### 4.4 外部完成验收

D3 将 externalConfirmation 定义为一次执行后的外部验收。仅适用于显式声明该方式的有限 behavior：树根成功、act 与 broker 均已收尾、无遗留控制操作时，由 body 创建待确认记录并进入 blocked/CONFIRMATION_REQUIRED。每个 run 最多创建一条完成确认请求。节点失败仍走失败传播或显式 recover，不能用外部验收覆盖未处理的执行错误；普通 blocked 不能被 confirm 当作完成验收。

待确认记录固定目标说明及运行参数引用，关联 bodyEpoch、runId、confirmationId 和 owner，并提供执行结果摘要；契约见 [CONTRACTS §7.1](CONTRACTS.md#71-外部完成验收契约)。确认只结束这个原实例，不重新执行节点，不修改 locals，也不发起游戏控制。

| 输入 | 原实例与请求的处理 |
| --- | --- |
| 有效确认满足目标 | blocked → succeeded；关闭请求，记录外部确认来源和依据，不标为游戏自动验证。 |
| 有效否定目标达成 | blocked → failed/EXTERNAL_GOAL_REJECTED；关闭请求，保留否定原因。 |
| 暂时无法判断 | 不提交决定，保持 blocked；第一版不增加第三种决定或自动重询。 |
| 有效 stop、switch、shutdown 或 owner 授权撤销 | 按取消规则结束原实例并关闭请求；有控制故障时仍不得越过终态检查点。 |
| 身份、归属、请求标识或载荷不合法 | 拒绝命令，保持实例原状态；命令被拒绝不等于外部否定目标。 |

否定后需要补做工作时，重新查询当前环境并启动新实例，不恢复旧树栈。确认和否定结束原实例，均不属于 blocked 后恢复执行。

等待确认没有额外倒计时，不自动成功、失败或定期催问；首版仍受 bridge 存活期限和 owner 授权约束。运行被取消或替换、授权撤销或 body 重启后，旧请求不再接受新决定，不能迁移到新 run/epoch。管道有效且原 body/run 仍存活时，可通过 status 取得同一请求；stdio 断开进入清理退出，不重连到旧 run。确认请求及决定只在内存管理，历史日志仅供人工调试，不用来恢复决定。WS 的 lease 内重连规则保留在[后续方案](WS-FUTURE.md)。

命令去重先校验调用者权限：同 commandId 同内容返回已有命令结果，同 id 不同内容拒绝。不同 commandId 对同一请求重复提交相同决定时，返回已处理结果，不重复发布终态事件，也不覆盖首次决定的来源和依据；相反决定返回冲突。请求已因取消、替换或 epoch 变化失效时，不接受新决定，返回关闭/失效结果；对已提交终态的历史查询不改变运行状态。

同批出现确认和否定时，按 ingressSeq 接受第一条有效决定；同批有效取消优先于两者，已提交的终态不被下一批消息改写。决定提交须通过 D2 终态检查点，控制故障不能被外部确认解除；未提交终态不得对外报告验收已成功处理。accepted 仅代表命令已受理，最终结果仍按命令状态和 run 状态查询。首版消息与方法见 [CONTRACTS §8](CONTRACTS.md#8-bridgebody-消息协议)；D6 只保留调试日志与内存记录，持久化恢复及崩溃对账见[后续恢复边界](FEEDBACK-AND-RECOVERY.md#7-异常退出与后续恢复功能)。

## 5. act 与操作控制权

broker 为每次 act 发放 actEpoch，所有控制请求携带 bodyEpoch、connectionEpoch、runId 和 actEpoch。一个角色至多一个有效控制授权。正常结束和取消首先关闭普通调用入口，保留限定的清理通道。

清理通道只接受该 act 已登记持续操作的 stop/release；不能借收尾移动到新目标、开新攻击或执行新的策略。通用取消不能撤销已发生的放置、消耗、破坏。

持续 op 必须在发送给游戏前登记，避免“已发出但未记账”。即使启动确认丢失也视为可能活动；broker 必须查询/撤销该请求或保持故障。act hook 抛异常、返回失败或进程退出，均走相同收尾路径。

act 自称完成不等于控制权释放：只有 broker 确认持续操作已停止、回调已隔离、无未决控制请求，才进入终态。终态后拒绝旧 runner 的普通请求；迟到结果只对账。

## 6. 停止、重试与未知结果

沿用主文档共识：首次停止或正常收尾开始建立总 deadline。每个明确可重试的清理操作最多追加一次，所有操作共享总期限；不重发整个 act，不重置计时，不在 broker/runner/driver 各叠加次数。

可重试条件：契约允许重复安全执行、上次明确结束、错误明确 retryable、尚有次数和剩余期限。超时或连接丢失且结果未知时，不等同于 failed；不启动第二个同类操作。

查询清理状态也是 QueryOp，每次只请求一次；若要再次检查，必须是清理流程中显式的有界轮询，不能由 QueryOp 内部隐藏重试。不支持可靠撤销的操作应在能力声明中明确，不能假装“立即取消”。

无法收尾或预算耗尽进入 faulted，保留归属。恢复只接受旧操作停止的有效确认，或可信驱动给出的整体撤销确认；单纯杀死 runner/body 不能证明游戏已停止。底层确实撤销之后才建立新 epoch。

## 7. 切换命令与版本一致性

切换请求明确指定 artifactId、参数和 commandId；先验证 owner、产物及闭包摘要、适用凭据、启用资格、当前加载 binding 和实际连接能力，再停止旧 behavior。候选或依赖已退休、缺失、摘要不符、环境不符或能力缺失时拒绝请求，无效候选不能打断现有行为。切换响应只代表 accepted，最终通过 commandId 查询或事件得到 activated/rejected/superseded。

首版 pending 切换槽只有一个：同一 owner 的后到有效请求覆盖尚未激活的候选，旧请求记为 superseded；人工 stop 清空 pending。停止一旦发起不可撤回。故障期间可以记住候选，但不能自动跨故障启动，恢复后须重验 owner、binding 与候选有效性。

当前 run 固定 behavior artifactId、确切 act 产物及传递依赖闭包、环境 binding 和参数，不能热改。源码 revision 不足以选择产物，同源码采用不同依赖或环境可生成不同 artifactId；默认启用映射须在请求进入执行器前解析，不能运行中重新查 latest。

新增或启用 H2 不改变仍锁定 H1 的旧 run，也不重新加载 provider。H1 退休后，依赖它的新 run 被拒绝，旧 run 包括后续节点仍使用原闭包直到按约定结束；需要立即停止须另发停止命令。候选切换等待收尾期间若其依赖被退休，授予新控制权前复核应拒绝新启动；旧 run 已停止时保持无主动行为，不自动替换成同名新产物或恢复旧动作。

可被动检查并按目标 binding 启用另一环境的候选，但当前 body 仍只加载一个 provider，普通 switch 不执行环境升级。更换 provider/执行环境仍走人类管理流程：先停止并确认清理，再加载/握手新环境，显式启动匹配产物。详见[环境与依赖范围](OPERATIONS-AND-RELEASE.md#31-环境产物依赖与运行实例)。

## 8. QueryOp 的具体执行

每次调用有 requestId、consumerRunId、connectionEpoch、deadline。请求在 body 单调时钟上计时；取消/超时后从等待集合移除，晚到结果不落入实例 locals。

观测新鲜度采用保守年龄上界：同进程可记录 monotonic sample time；跨进程驱动若无可信时钟映射，则保证采样发生在接收本请求之后，以 body 发出时间作为保守起点。若返回驱动缓存，必须附缓存年龄上界，不能只给回复时间。无法建立年龄界且调用要求新鲜度时返回 FRESHNESS_UNPROVABLE。

每次消费都检查年龄，而非只在收到回复时检查。多个 QueryOp 的结果不承诺原子快照；有此需要时由一个明确的复合 QueryOp 保证。结果限本次运行使用，不进入持久世界缓存；实体引用必须带连接/世界作用域，跨重连无效。

结果为空可以是成功；partial 必须注明范围，调用方明确允许才接受，否则 QUERY_INCOMPLETE。对过期/不完整结果的拒绝不自动查询第二次。对同一条件的失败不能靠下一 tick 重新发起掩盖，须经过显式 recover；成功后的周期刷新是新的正常评估。

## 9. 托管生命周期、断连与重启

- **正常关闭/插件释放**：bridge 拒绝新业务，通过 shutdown 停止 run、清空 pending，待 act/broker 收尾确认后关闭游戏连接和辅助进程，再退出 body。模型 stop 只停止行为，人工 /p2 stop 关闭整个托管 body。
- **stdio 关闭或失效**：stdin EOF、输出管道失效、不可恢复协议错误均撤销 owner 授权，主动清理退出；不保留服务等待重连，也不自动启动新 body。
- **bridge 卡住**：管道尚开但 heartbeat 超过存活期限时撤销授权并清理退出。heartbeat 由 bridge 独立于模型回合维护，模型推理慢本身不代表 bridge 失活。
- **热重载/再次启动**：插件释放旧 body 及其 runner/构建进程，重载后保持未启动。人工 start 创建新 bodyEpoch；旧进程树未回收或控制未决时，不启动新的控制者。换 owner session 也采用先关闭旧 body 再人工启动新 body。
- **游戏连接断开**：立刻禁止新控制调用，连接 epoch 作废；不能假定游戏输入已解除，按驱动停止证明处理 fault。
- **body 崩溃**：底层驱动的控制释放/watchdog 能力仍须验证；新 body 生成新 epoch，从空运行开始，只做当前启动与连接核验，不从日志重建旧控制账本或自动对账。未知游戏效果由开发者/人类核查，不将重新启动当成停止证明。
- **runner 崩溃**：body 仍负责清理，业务失败为 ACT_RUNTIME_ERROR；清理失败另报 executor fault。
- **机器重启**：保留已正常保存的源码、artifact、显式目标及可用调试日志，不保证有上次运行终态；不恢复节点栈、命令或通知，不自动归档未完成运行。新的执行需人工启动，不能伪造上次已取消或成功。

退出和进程树回收必须有界，并在 Windows 上验证；正常路径不能先强杀再宣布收尾成功。强制结束时由存活的一方尽力显示 interrupted/结果未知，不承诺记录可靠保存。平台回收不保证游戏控制已释放，插件 dispose 回调也不保证可完整等待；EOF/存活检测、内存 broker 清理与进程回收分别验证。首版不实施崩溃恢复；独立常驻服务及断线后保留 body 的设计仅属于[后续 WS 方案](WS-FUTURE.md)。

驱动 watchdog 只撤销控制，不决定战斗/逃跑等游戏策略，因此不构成第二套并行 behavior 或未经讨论的反射 AI。若接入方案无法提供这一保证，必须作为接入验收限制披露，不能宣称崩溃安全。

日志只是异步调试输出。命令受理和运行终态均不等待日志落盘；loggingUnavailable 或丢日志不改变 executor health，也不触发业务停止。正常退出仅有界尽力刷新日志，停止和控制清理不能等待日志恢复。普通请求、输出与构建队列仍须有界，停止/心跳/清理预留通道按[首版队列规则](FEEDBACK-AND-RECOVERY.md#33-有界队列与停止优先)执行。

## 10. 首版配置起点

以下默认值为本轮设计取值，可由开发者/人类配置覆盖，需在两套游戏候选环境实测；不是模型可任意放大的预算。

| 配置 | 初值 | 责任 |
| --- | --- | --- |
| tree tick | 100ms | body 调度器 |
| 每轮转移上限／处理目标 | 200／10ms | 超限让出并计量 |
| 默认 QueryOp deadline | 1000ms | 单次查询，0 自动重试 |
| 控制条件数据最大年龄 | 500ms | 调用可声明更严要求；可显式配置其他值 |
| 面向 agent 的摘要数据最大年龄 | 2000ms | 仍标示时间和范围 |
| 停止／正常收尾总期限 | 2000ms | 每个失败清理 op 最多追加 1 次 |
| act hook 软预算／无响应上限 | 50ms／500ms | runner 超限后撤销普通调用并清理 |
| bridge heartbeat／存活期限 | 2000ms／10000ms | 管道尚开时检测 bridge 失活；超期清理退出，已知 EOF 立即进入关闭流程 |
| 驱动控制续租／失联释放目标 | 100ms／1000ms | 必须由具体接入验证支持 |
| 进度停滞提醒 | 30s | 默认仅产生进度诊断，不自动结束长动作 |

runner 无响应检测依赖 body 正常调度；硬件、GC、进程调度会影响实际时间，不能据此承诺硬实时。有限 act 的最长业务执行时间由其契约/参数声明，不能统一用停止期限代替。

## 11. 验收场景

1. 两个 goto 连续节点只启动一个；没有 Parallel 节点可供构建。
2. 采集过程中高优先级条件成立：确认停止前攻击 act 从未取得控制权。
3. guard unknown：当前 act 可推进，完成后不启动依赖旧 guard 的下一 act。
4. 取消与成功同批到达：已接受取消者归 cancelled；此前已终态者返回 alreadyTerminal。
5. 旧请求晚到、旧 runner 发送 op、重连前实体引用均不能控制新运行。
6. 正常失败收尾超时与主动取消超时进入同一种控制故障，不误报 failed/cancelled。
7. QueryOp 超时只有一次请求；清理 retryable failure 最多两次尝试且共用 deadline。
8. 单个构建/act 无限循环不阻塞 body；broker仍能撤销操作，不能仅靠杀进程宣布停止。
9. stdio EOF/写端失效立即进入清理退出；管道尚开但 heartbeat 超期也退出。模型慢但心跳正常不触发停止；游戏重连不重放旧动作。
10. assign 表达式或类型校验失败时原值不变；不能写只读参数、其他局部帧或留下部分更新。
11. query/act/子树的新调用不会读取上一轮成功输出；失败、取消和未就绪输出不被转换为空结果或旧值。
12. act 报告 complete 后清理尚未确认时不发布成功输出；清理失败不发布候选结果，重复确认不重复累计，旧运行晚到结果不写入新帧。
13. 同一子树的两个调用点、循环中的多次调用及取消后重入均拥有独立 locals；只读输入和显式输出映射有效，外层 behavior 计数可跨轮次保留。
14. 观测经过集合选择、记录构造、assign 和子树返回后，来源、年龄及作用域仍可校验，复制不刷新时间；普通策略计数不会仅因经过观测有效期而失效。
15. 成功采集次数与实际背包数量分别处理；失败或取消前已发生的游戏变化不因缺少成功输出而被当作未发生。
16. sequence 中 assign 成功后，后续节点在同轮读到新值；后续节点失败不回滚这次赋值。等待和预算耗尽可跨 tick，但不改变可见性规则。
17. local 更新使先前 guard/完成判定失效：新 act 启动前重新检查；查询参数变化使用新 evaluationId，旧结果不能放行，查询失败不被自动重查掩盖。
18. 同批成功与有效取消无论消息先后均按取消收尾；批次固定后到达的消息留待下一轮，终态一旦提交不被晚到取消改写。
19. 有效目标证据与 PATH_UNREACHABLE 同轮出现可准备成功，保留失败诊断并最终确认；换成未处理的 EXPRESSION_ERROR 或非法结果 schema 时不得成功。
20. 准备成功期间清理超时进入 faulted，不发布成功；收尾后的最终目标为 false 时返回 GOAL_NOT_MET。收尾期间收到有效取消则按取消意图处理。
21. 一次性 if 不因检查点而重选分支；反应式依赖 unknown 时可继续当前 act，但不得启动依赖该条件的下一 act。repeat 下一轮仍至少等待下一 tick。
22. 仅 externalConfirmation 的有限 behavior 在根成功且双重收尾确认后创建一次待确认请求；清理未完成、根失败/取消、持续 behavior 或其他 blocked 原因均不能被 confirm 判为成功。
23. 有效确认使原 run 成功，有效否定使原 run 失败并保留原因；两者都不恢复树。否定后补做工作使用新 run，无法判断时不提交决定、不自动催问或超时结束。
24. 错误 owner、runId、confirmationId、bodyEpoch 或非法载荷只导致命令被拒绝，不使待确认 run 失败；模型填写“玩家同意”不能改变可信来源。
25. 同命令重发、不同命令重复同一决定不重复发终态事件；相反决定冲突。同批相反决定按 ingressSeq 接受首个有效者，同批有效取消优先，终态不被晚到决定改写。
26. 同一有效管道可取回待确认请求；管道关闭、授权撤销、有效切换及 body 重启使旧请求不可再决定。控制故障下确认不能绕过终态检查，accepted 不被报告为 succeeded。
27. 当前 run 使用 H1 时检查/启用 H2 不改变 binding 或运行依赖；只有显式切换到引用 H2 的 artifact 才使用 H2，默认映射变化不影响 pending 或当前 run 的确切引用。
28. H1 退休阻止依赖它的新 run，旧 run 后续节点仍用 H1；候选在停止等待期间出现退休/缺失依赖时不得接管，不自动换版本或恢复旧动作。
29. 同一 revision 的多个产物按 artifactId 区分；其他 binding 的候选虽可静态检查/启用，环境不匹配或实际能力缺失时 switch 被拒绝，当前行为不被打断。
30. 插件安装/加载/热重载不创建 body；人工 start 只创建一个 body 且不自动启动 behavior。模型 stop 保留 body，人工 stop/插件释放关闭进程树而不销毁用户 agent。
31. shutdown、宿主异常退出、runner 卡住及输出背压下，控制清理与进程回收分别验证；强制结束由存活一方尽力报告结果未知，不伪装停止成功；新 epoch 不恢复或重放旧命令。
32. 日志不可写、磁盘满、缓冲满和轮换删除不影响当前内存去重、业务结果及停止；丢弃计数/日志不可用状态可观察，终态响应不等待落盘。
33. 普通请求、查询、构建或输出达到额度时拒绝新增普通工作，停止/心跳/清理仍有独立处理额度；日志和 stderr 背压不阻塞执行器。重启不从日志修复、恢复索引或补投递事件。

这些是未来运行时测试验收，未在本次文档工作中实现或执行；不属于用户 behavior 检测器的模拟测试。

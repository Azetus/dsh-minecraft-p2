## 1. 项目目标与设计原则

让 agent 以第二名玩家的身份参与 Minecraft，与人类玩家交流、协作，并根据玩家指令、自身目标和环境变化安排角色的行动。

agent 的控制方式类似策略游戏或 RTS：为角色选择和调整持续生效的行动策略，而不是逐次决定移动、攻击等具体操作。策略执行期间，角色通过程序持续与世界交互，不必为每个动作等待模型回复。

这是个人项目。设计优先考虑可理解、可开发和可维护，接受行为细节与反应能力上的取舍，不以 agent 能够即时决策为前提。

首版只支持本机一个body控制一个角色，一个拥有写权限的DSH会话。目标是模型选择/编写策略、代码持续执行；不承诺硬实时生存或无条件完成任务，不实现多角色编队、通用视觉接入或任意op自动自升级。

## 2. 系统组成与职责

### 2.1 系统组成

agent 是调度者与 behavior／act／policy／op 作者。P2 的运行机制包含以下三个部分：

| 部分 | 职责 |
| --- | --- |
| 观测层 | 基于查询 operation 提供当前事实，并用纯函数整理查询结果与生成摘要，供 agent 及执行中的行为使用。 |
| 行为系统（behavior 系统） | 保存、描述和管理可用的行动策略，包括预设 behavior、自定义 behavior 及其附属 policy。 |
| 执行器 | 驱动当前 behavior 及其 act 的执行，落实具体动作与行为切换。 |

系统初始提供一组预设 behavior。人类开发者与 agent 都可以添加新的自定义 behavior；agent 根据目标和情况选择适用的 behavior，在现有 behavior 无法表达所需行为时编写新的 behavior。policy 是 behavior 层内部的纯计算决策单元，不是第四级控制层，详见 §3.6。

operation 库统一提供游戏查询与控制的基础接口及对应实现。观测层不另行维护一套直接对接游戏的查询实现，act 也不自行绕过该库调用游戏接入接口。

**Mineflayer 是首套 operation 实现的底层依赖，不是 P2 公共接口。** core 的执行器、观测层及 behavior／act 仅使用统一契约；Mineflayer 对象、类型、事件和插件句柄不向这些上层泄漏。适配层转换数据、控制生命周期与失败结果，并声明实际能力。后续真实客户端主要替换 operation 实现及游戏驱动，不改写核心机制；行为内容仍需按能力与游戏规则检查适用性。详见[接入决策与依赖边界](MINECRAFT-INTEGRATION-OPTIONS.md#12-mineflayer-与-p2-的依赖边界)。

### 2.2 观测层：查询接口与摘要纯函数

**观测层由数个游戏环境查询接口，以及根据查询结果生成摘要的纯函数方法组成。P2 提供当前事实与执行反馈，不维护 Minecraft 世界状态副本，也不记录环境变化事件。**

- **游戏环境查询接口**：通过 QueryOp 读取当前游戏数据并返回结构化结果。查询结果随游戏状态变化，读取接口本身不是纯函数；具体游戏适配由 operation 库承担。
- **摘要纯函数**：根据传入的查询结果进行筛选、计算与格式化；相同输入产生相同输出，不自行读取游戏、不保存历史、不产生副作用。
- **观测层的范围**：不保存历史观测，不比较前后环境差异，不生成环境变化事件，也不主动触发模型会话。

```text
查询 operation（QueryOp）
    ↓
结构化观测结果
    ├─→ behavior 与执行器读取、判断
    └─→ 摘要纯函数 → agent／LLM
```

一次查询的结果可以供当前判断与摘要处理使用，这不等于维护一份持续同步的世界状态。behavior 的局部变量、目标引用、执行位置与运行状态仍由 behavior 实例及执行器保存，属于行动状态，不属于世界状态副本。

查询接口具体有哪些、返回什么数据、摘要如何组织，均不在当前机制设计阶段确定。

### 2.3 环境变化理解与执行反馈的分工

| 部分 | 职责 |
| --- | --- |
| 观测层 | 提供“现在观测到了什么”。 |
| 执行器 | 提供“正在做什么、执行结果如何”。 |
| agent／session | 根据上下文中的新旧观测及执行记录，理解变化并决定下一步。 |

agent 读取的观测、发出的操作及其实际执行反馈应进入同一 session 上下文。上下文不能只记录指令并将其视为已完成；实际进度与结果应关联对应的 behavior 实例。无需将每个 tick 或每个底层动作都送入上下文。

session 承担变化的理解与回顾，不持续观察游戏，也不会因游戏发生变化自动开始推理。agent 在下一次取得观测并被调度处理时，才能据此发现变化；当前设计接受这一反应时机上的取舍。

session 中的历史信息不替代 behavior、执行器与 act 对当前数据的读取及运行时判定。未进入或未保留在上下文中的历史，不视为已知事实。

**不记录环境变化事件，不影响执行器提供执行反馈。** behavior 完成、受阻、失败、取消等仍按照第 8 章的统一机制报告；它们属于 P2 自身的执行结果，不是对世界变化的追踪。当前不为观测层另行设计环境事件系统。

### 2.4 “身体”与“大脑”的职责

**P2 核心是“身体”，agent／LLM 是“大脑”。P2 核心独立于具体游戏版本；接入差异由 operation 实现承担，游戏规则差异及其策略影响由 agent 处理。**

| 部分 | 责任 |
| --- | --- |
| operation 库 | 将统一的查询与控制契约落实到对应游戏版本或发行版。 |
| P2 核心 | 检查、登记和执行 behavior 定义，管理控制权，提供当前事实与执行反馈。 |
| agent／LLM | 理解游戏特性，判断策略是否适用，选择、修改或编写 behavior／act／policy；开发阶段也可编写 op 产物。 |

agent 编写的 behavior／act 是由 P2 执行的可替换行为内容，不等同于 P2 核心机制。为适应游戏版本而重写行为，不代表核心执行架构需要适配。

P2 核心不内置 Java 版或基岩版的策略分支，不负责保证同一策略跨版本有效，也不自动修正不适用的策略。operation 忠实执行并返回结果，P2 按契约反馈，agent 根据当前环境与 session 决定后续处理。

### 2.5 部署与所有权

```text
人类 ↔ DSH现有session/agent
              ↕ P2 scoped tools、执行反馈
          薄bridge插件
              ↕ 消息协议／stdio传输适配器
          插件持有的独立body子进程
          ├─ 可信执行器、状态与事件
          ├─ 隔离的模块检查／act·policy runner
          └─ operation broker → 选定provider → 游戏连接/驱动
```

DSH不逐tick操控角色。body的串行调度器控制唯一活动act，隔离runner只承载其代码；辅助进程不产生第二个控制者。broker持有实际游戏操作的账本与清理能力，生成代码不持原始连接。act 通过 op 桥提交控制与查询请求；policy 只通过纯桥接收输入并返回值，不能提交 op。

policy 不是独立的控制层或调度单位：它由 behavior 通过 `yield ctx.decide` 调用一次，异步等待并返回一个受限 JSON 值，由 behavior 代码决定如何使用。执行器始终持有调度权与控制权。

首版人工 /p2 start 后，bridge 为正确项目的现有会话创建并持有一个 body，通过 stdio 通信。初版 bridge、body 与内置 provider 同包交付；body 仍是独立子进程。安装、加载或热重载不自动创建 P2 进程；启动 body 不自动启动 behavior。body 独立调度但生命周期跟随插件，插件释放时收尾并回收 body/辅助进程，不销毁用户 agent。模型 stop 只停 behavior，人工 stop 关闭托管 body；换 session 先关闭旧 body 再人工启动。

协议层与传输层分离：首版 UTF-8 JSON Lines，stdout 专用于协议、stderr 日志；保留命令去重、epoch 和事件语义。管道失效或 bridge 存活超时后清理退出，不重连旧 body。**正式模式不自动重启**；开发模式可启用**有界自动重启**：心跳连续缺失或子进程异常退出时，强制结束整棵进程树，以新 epoch 重启 body，旧 run 记 `faulted`、在途控制记 `unknown`、guard/watch 随 epoch 失效，并按预算退避；预算耗尽或重连失败后保持 `faulted` 等人工处理。强制结束不构成游戏停止证明。独立 launcher、WS 鉴权及 lease 重连已整理为[后续设计](WS-FUTURE.md)，不阻塞首版；未来迁移还需补全独立服务生命周期。详见[运行时](RUNTIME.md)与[DSH 接入](DSH-INTEGRATION.md)。

## 3. 核心概念

### 3.1 behavior：持续行动策略

**behavior 是一段持续生效的行动策略，由 manifest、生成器代码与运行内状态组成，其本质是交给执行器逐步运行的程序。**

| 组成 | 形式 | 职责 |
| --- | --- | --- |
| 行为 | behavior 模块（manifest + 生成器 `run`） | 用 JS 写顺序、条件、循环、函数复用、错误处理与 act 调用；决定何时开始、何时停止、失败怎么办。 |
| 决策 | 受限纯函数（policy），由 `yield ctx.decide` 调用 | 在明确的决策点做有限计算：选哪个目标、走哪个分支、下一个目标是什么。异步等待，没有副作用，不提交 op。 |
| 状态 | 生成器局部变量与闭包 | 保存本次运行的策略状态与执行证据；不跨 run 保留，不构成世界副本。 |

三者都在 behavior 层内，policy 不是独立的第四级控制层（见 §3.6）。behavior 代码决定「做什么」，policy 决定「用哪个值」，act 决定「怎么做」。

P2 的策略定义统一称为 `behavior`（行为），`job` 留作 DSH 自身的事务术语。

behavior 是策略定义（模块 + manifest），执行器负责运行它；它包含参数、完成方式（finite / continuous）与失败处理规则。术语统一使用“behavior 定义”“behavior 实例”和“行为系统”；动作层级保持 behavior → act → operation。

behavior 通过 JS 的条件、循环、函数与顺序组织 act，并在局部变量中保存策略需要的状态。它不是一次性指令，也不局限于顺序动作列表。

设计借鉴 RimWorld ThinkTree 的决策组织思路：通过条件、优先级和短路选择决定下一步。behavior 由代码编写，由统一执行器驱动；控制流与状态都留在代码中，具体共识见后文。

例如，“跟随玩家并处理靠近的敌人”可以在同一个 behavior 内完成跟随、接敌和恢复跟随，不需要每次都让 agent 更换 behavior。

区分以下两个概念：

- **behavior 定义**：可复用的策略程序，例如“区域采集”。
- **behavior 实例**：带有具体参数和执行状态的一次运行，例如“在指定森林收集 32 个云杉原木”。

### 3.2 act：可复用的完整行为

**act 是可复用、可中断的完整行为，协调基础 operation 完成一项边界明确的动作。** 此概念原称 step，今后统一使用 act；改名保留原有职责与生命周期，并明确其下的 operation 实现层。

典型例子包括移动到目标附近、装备指定物品、采集一个目标。

act 的粒度不按代码量、耗时或引擎原子操作划分。移动 act 可以持续较长时间，并在内部处理寻路与局部调整；behavior 无需重复实现这些细节。

act 是可执行代码，运行在独立的隔离 runner 中，通过消息向 broker 提交 op 并读取结果；它不持有游戏连接，也不直接调用 provider。每个 act 产物必须在 manifest 中强制声明使用的 QueryOp 与 ControlOp（`stop` 作为撤回原语隐式授予），运行期提交未声明的 op 立即失败。

act 的边界由两件事判定：**需要 op 副作用，或者需要中断与收尾契约**。因此「选哪个目标」「要不要改策略」不属于 act，属于 behavior 的决策层；act 只接收已经确定的参数，把这一件事做完并如实报告结果。控制结构（条件、循环、优先选择）属于 behavior，不与具体动作混为一谈。控制结构可以由统一语法或接口提供，暂不单独增加业务层级。

act 的**完成可以由调用方提前终止**：behavior 可用非阻塞句柄启动 act，并显式 `actWait`/`actStop`；终止条件属于调用语境，act 不内置策略条件。同一时刻至多一个控制 act 在飞；停止仍走统一的两阶段停止/释放确认；run 结束或取消时必须先停止并确认未完成句柄，再进入终态。

### 3.3 operation：游戏基础操作

**operation（简称 op）是直接对接游戏的、可复用的基础操作，包括读取游戏数据的查询操作和改变角色或游戏状态的控制操作。**

| 类型 | 职责 | 使用约束 |
| --- | --- | --- |
| QueryOp | 读取当前游戏数据并返回结果。 | 不改变角色或游戏状态；供观测层、behavior 条件及 act 使用。 |
| ControlOp | 发起动作，设置或清除控制状态。 | 只有当前持有角色控制权的 act 可以调用。 |

“原子化”表示基础操作的粒度，不承诺瞬间完成、不可中断、事务原子性或自动回滚。部分 op 的效果会持续生效，需要 act 协调和清理。op 不拥有独立策略，也不复制一套 behavior 调度机制；底层完成或错误结果由 act 接收并形成行为反馈。

**op 的声明与实现分开归属**：名称、类别、参数与结果契约、持续效果、停止语义与能力标记由 P2 核心维护；具体实现由可替换的 provider 包提供。初版两者同包但分目录，后续把 provider 整包拆出，核心不需要知道底层是 Mineflayer 还是其他客户端。检查阶段只读取静态声明，不连接游戏；连接后再核验实际能力与声明一致。

**开发阶段开放 op 现场编写**：agent 可提交 op 产物（查询/控制），经检查后在 **body 进程内**加载，按 binding 激活使用；op 目录不再作为固定清单。op 实现直接持有 provider 能力，因此停止/清理契约由作者负责；broker 只对经其提交的效果记账，**直接调用 provider 的 op 不被账本跟踪**，相关 run 的释放结论必须标 `unknown/unconfirmed`，status 不得谎称 `released`。provider 接入面（连接、底层库版本、能力握手）仍由核心维护，属于后续拆分的边界。

`QueryOp` 与 `ControlOp` 作为 `Operation` 的两个类别继续沿用；类别是结构维度，具体 op 名是裸标识（例如 `position`、`moveTo`），不在名字里编码类别。

```text
动作控制路径：behavior → act → ControlOp → 游戏
数据读取路径：游戏 → QueryOp → behavior／act 的判断
                              → 观测层组织与摘要 → agent
```

因此，behavior → act → op 的层级约束适用于动作控制，不要求所有读取都经过 act。behavior 查询与完成判定不占用角色动作控制权。

behavior 通过 `yield ctx.query` 发起查询；查询在运行时执行，不存在预先声明的数据引用。QueryOp 可以采用异步实现，但等待查询不能阻塞整个调度循环；等待、结果有效性与失败处理的暂定规则见第 7.11 节。

### 3.4 一个 act 协调多个基础操作

同一时刻至多一个 act 持有角色控制权，不意味着角色只能产生一种底层动作效果。一个 act 可以在短暂更新中依次计算并提交多个 op，协调移动、朝向、交互等效果；具体游戏行为留待后续设计。

这些协调可以分解为 act 内部的可复用函数，不要求实现为一个巨大函数，也不构成 behavior 的并行行为分支。控制权始终归属于同一个 act。

首版对同一 act 内的并发约定为：**多个只读查询可以并发在途，至多一个持续控制效果生效**。需要「边移动边攻击」这类组合时，先由效果槽位或明确的组合 op 表达，不在 act 内制造第二个控制者。

停止 act 时，必须清理它留下的持续控制、未结束操作及相关回调；未确认停止前不能移交控制权。已发生的世界变化不会被取消操作自动回滚。

### 3.5 act 与 operation 的结果及收尾契约（暂定）

**每个 act 和 operation 都应明确成功、失败及结束路径，但判定范围不同，不要求使用完全相同的状态机。**

| 层级 | 成功边界 | 失败边界 |
| --- | --- | --- |
| QueryOp | 按查询契约取得结果，包括合法的空结果。 | 无法完成查询，或无法提供契约要求的数据。 |
| ControlOp | 完成该操作承诺的效果。 | 无法完成该操作承诺的效果。 |
| act | 完成完整行为的目标，并完成收尾。 | 无法完成行为目标，完成收尾后返回原因。 |

例如，查询附近目标返回空列表通常是查询成功；移动 act 因路径不可达而结束，则是行为失败。设置移动输入的 op 成功，只说明输入已按契约设置，不说明角色已到达目的地。op 成功不等于 act 成功。

每个 act／op 的行为契约应明确：

- **执行前提**：什么条件下可以开始，不满足时如何返回。
- **成功边界**：承诺完成什么，依据什么确认。
- **失败边界**：哪些情况导致无法完成，返回哪些原因。
- **持续效果**：调用结束后是否仍留下控制输入、后台操作等效果。
- **停止与收尾路径**：如何终止持续效果，何时可以确认停止。

op 报告基础操作结果，act 解释其对当前行为的影响，behavior 决定如何继续策略。act 可以在自身职责范围内重试或调整；仍无法完成时再向 behavior 返回失败。超出 behavior 恢复规则的情况交由 agent 决策，不要求每个 op 都自带备用策略。

上述要求是行为契约，方法与字段的设计见[接口文档](CONTRACTS.md)；瞬时查询不必套用持续动作的完整生命周期。契约应说明执行如何完成、失败或进入可识别的故障状态，不承诺穷举所有游戏异常，也不要求每个行为都能自行恢复。

### 3.6 policy：behavior 内部的决策单元

**policy 是 behavior 的附属纯函数，用来在 behavior 执行期间计算值，不是独立的控制层，也不是第四级。**

引入 policy 的原因：behavior 需要「从一组候选里选一个」「按多个因素打分」「构造下一次调用的参数」这类可复用的纯计算。若把决策塞进 act，act 会同时承担执行与决策，破坏三层分工；若在每个 behavior 里重复内联，又难以独立检查和复用。policy 把这些计算收敛为可锁定、可复用的纯函数产物。

| 特性 | 约定 |
| --- | --- |
| 形态 | 单文件可执行代码，在隔离 runner 中以纯桥运行；无 op、无 I/O、无宿主对象。 |
| 调用方式 | 只能由 `yield ctx.decide` 调用一次；结果恢复到 behavior 的局部变量，供后续代码使用。不能从 act 参数或其他命令中隐式调用。 |
| 输入输出 | 输入与输出都是受限 JSON；结果不直接产生控制效果。 |
| 生命周期 | 一次调用一次返回，异步等待、不阻塞 tick，不保存跨调用状态；不参与 act 的 start/update/stop/cleanup。 |
| 失败语义 | 抛错、超时或返回非法值时，`ctx.decide` 向 generator 抛出 `P2Error`；由 behavior 的 `try/catch` 或未捕获失败处理，不是控制故障，也不触发 act 清理。 |
| 作用域 | act 不能调用 policy，policy 也不能调用 act 或 op。 |
| 复用 | 作为内容产物按 digest 锁定，可被多个 behavior 引用并进入依赖闭包。 |

policy 可以复用，但复用发生在产物层，不新增调度层级：它回答「值/决策是什么」，behavior 代码仍决定「下一步做什么」。因此「行为由 policy 决定」的准确表述是：**policy 在明确的决策点给出结果，behavior 依据该结果决定下一步**。

「在明确决策点调用一次」是刻意的限制：它让跨进程纯计算只有一种形态（`yield ctx.decide`），运行时不必为任意表达式提供挂起与恢复，也避免一次选择被拆成多次隔离调用。调用时机、预算与失败分类见[运行时](RUNTIME.md)，接口与产物格式见[接口契约](CONTRACTS.md#4-act-与-policy-作者接口)。

## 4. 职责与扩展边界

### 4.1 三条职责边界

1. **behavior 只通过 act 操作角色。** behavior 可以读取观测、计算、判断和保存策略状态；纯计算可以由附属 policy 完成，实际动作通过统一的 act 接口执行。behavior 不得直接引用 ControlOp。
2. **act 不替 behavior 决定长期策略。** act 可以处理完成当前动作所需的局部变化，例如绕路，但不自行决定改去采矿、返家或更换长期目标，也不承担「选哪个目标」这类决策。
3. **允许组合行为复用，不为组合形式增加额外业务层级。** 多个 behavior 共用的行为组合可以通过 `call` 引用另一个 behavior 产物，纯计算可以提取为 policy 产物；这两者都是内容产物复用，不新增调度层级。act 下方明确设立 operation 基础层，隔离可复用的游戏接入操作。

agent 编写新 behavior 时使用已有 act 编排策略；需要新的完整行为时，可以通过已有 op 编写新 act。新增 act 与编写 behavior 是不同层次的行为开发。新增 op 在正式发布流程中属于基础库维护；**开发阶段按 §3.3/§4.3 允许现场编写并激活**，provider 接入面仍由核心维护。

### 4.2 行为变化与策略调整

策略内部的变化由 behavior 与执行器处理，例如采集中绕路、护卫时遇敌。策略本身需要改变时，由 agent 重新选择或调整 behavior，例如玩家改变目标，或当前策略不再适用。

模型编写新 behavior 与角色执行已有 behavior 是不同过程。编写期间，角色可以继续执行已有行为或等待，不要求模型在每次环境变化时现场编写程序。

### 4.3 operation 库的维护与扩展权限

operation 作为独立维护的基础库，统一提供名称、类型定义、参数与结果、错误含义、持续效果的停止及清理契约、接入实现和兼容信息。独立维护不强制独立仓库；初版作为同一个包内的独立模块，后续再考虑拆包/拆仓。

| 层级 | 游戏中的 agent 的扩展方式 |
| --- | --- |
| behavior | 使用已有控制结构、查询和 act 编写策略。 |
| policy | 用纯函数做有限计算，由 behavior 通过 `ctx.decide` 调用；不能提交 op，也不能决定控制流。 |
| act | 使用已发布的 QueryOp／ControlOp 协调完整行为。 |
| operation | 使用已有 op；也可现场编写 op 产物，检查后在 body 内激活使用。provider 接入面由核心维护。 |

**开发阶段允许运行中编写与激活 op**（见 §3.3）：op 与 behavior/act 一样是可检查、可激活的内容产物；provider 接入面（连接、库版本、能力握手）仍是稳定边界，后续可拆包。正式发布是否只允许“已提升”的 op，由发布配置决定；当前阶段不做额外审核。

缺少基础能力时应如实反馈，不通过猜测底层接口或直接访问游戏来绕过 operation 层。新增 QueryOp 与新增 ControlOp 遵循同一维护边界。

基础库的游戏兼容性验证属于库的维护工作，不属于被动 behavior 检测器的职责；检查通过不证明真实游戏兼容性。

### 4.4 接口版本与游戏实现的分离

operation 库维护明确的游戏兼容关系，不要求库版本号与 Minecraft 版本号一一相等。区分以下信息：

| 信息 | 用途 |
| --- | --- |
| op 接口版本 | 说明上层依赖的参数、返回值与行为契约。 |
| 库发布版本 | 记录实现修复、能力增加与兼容调整。 |
| 游戏版本兼容范围 | 说明对应实现支持的 Minecraft 版本或发行版。 |

```text
P2 核心及可替换的 behavior／act
              ↓
    统一的 operation 契约
         ↙             ↘
   Java 版实现       基岩版实现
```

两种实现遵守相同的操作含义、数据类型、结果、错误与停止契约，避免向上层泄露特定版本的内部对象。能力缺失应明确声明，不假装支持。接入实现变化优先在库内适配；无法维持原有契约时显式处理接口版本与兼容关系。

在统一契约成立的前提下，P2 核心无需因游戏版本或规则差异改变。游戏规则导致行为不适用时，由 agent 根据反馈调整 behavior／act，身体不承诺解决策略适配问题。当前游戏版本与可用能力可以通过查询向 agent 提供，P2 不替 agent 作出版本策略判断。

检测结论对应具体接口版本与可用能力集合，更换不兼容的库后不能直接沿用旧结论；精确binding及产物摘要见[发布设计](OPERATIONS-AND-RELEASE.md)。

D4 将环境 binding、产物依赖与运行实例分开：binding 固定 body 运行时、契约、provider、驱动及影响执行的配置，不包含内容产物集合（act／policy／被 `call` 的 behavior）；每个 artifact 锁定实际使用的确切依赖与闭包；run 固定 artifactId、binding 和参数。新增 act 或 policy 不改变环境或已有运行，采用新依赖的候选才重新检查；provider/环境变更仍需人类管理、停止清理和重新核验。

revision 表示源码版本，artifactId 表示确切可执行内容；同源码在不同依赖或 binding 下可以生成不同产物。启用与 switch 指定 artifactId，运行时不追随默认版本。候选可以面向其他 binding 静态检查并启用，但仅与当前加载环境一致且实际能力满足时才能启动。退休依赖阻止新 run，不替换已有 run 的后续步骤。摘要输入、规范化与变更范围见[发布设计 §3](OPERATIONS-AND-RELEASE.md#3-不可变-binding)，启用状态见[生命周期 §5](BEHAVIOR-LIFECYCLE.md#5-artifact-与检查凭据)。

### 4.5 仓库组织与包管理（初版单包，后续可拆）

**初版采用一个 npm 包交付：bridge、body、内置 Mineflayer provider、operation 声明、authoring 子路径、共享契约与预设 behavior／act／policy 同包；后续验证可行后再拆包/拆仓。** 包管理器用于开发和构建；
pm run bundle` 把 tarball 输出到 `bundles/`，通过 DSH 插件管理安装，初版不发布 registry。

包内按目录分层：contracts、authoring、operation、core、acts、behaviors、body、bridge、provider。模块名不等于发行包，依赖方向仍按 §1：bridge 不 import core/body/provider；core／acts／behaviors 不 import provider，只依赖 operation 的声明；provider 实现 operation 契约。初版用一个轻量 import-boundary 检查维持这些方向。

```text
主仓库
└─ 单包（初版）
   ├─ src/contracts      # 契约、消息、错误、摘要
   ├─ src/authoring      # behavior 编写接口
   ├─ src/operation      # QueryOp / ControlOp 的声明与契约，P2 核心保留
   ├─ src/core           # 执行器、run 运行时、注册表、broker
   ├─ src/acts           # 内置 act（单 op 包装，后续增强）
   ├─ src/behaviors      # 预设 behavior 与 policy
   ├─ src/body           # body 进程入口
   ├─ src/bridge         # DSH 插件
   └─ src/provider       # 初版同包分目录；后续整包拆出
```

`operation` 的声明留在主包，`provider` 是唯一直接接触游戏库的目录。初版即便同包提供，也要求二者不在同一目录、不互相 import 反向依赖，这样后续把 `provider` 拆成独立包时不需要改动核心。

同一个 tarball 安装到 DSH profile 获得运行时；项目以 devDependency 安装同一 tarball 获得 authoring，`/p2 setup` 校验版本一致。body 仍是独立子进程，provider 仍通过接口加载，act runner 仍隔离；合并的是交付物，不是进程或依赖方向。

后续出现独立维护者、独立发布节奏、第二 provider，或 body 需要脱离 DSH 运行时，再拆 provider/body/authoring。拆分保持包名、公开契约、协议、provider manifest/registry 不变，不要求 submodule。初版不建设多版本、provider store、registry、签名或自动更新。

## 5. behavior 的定义与构建

### 5.1 表达方式的架构决定

**behavior 采用受限生成器协程：模块在顶层调用注入的 `defineBehavior({ manifest, run })`，`run` 是 `function* (ctx)`；`defineBehavior` 由 runner 加载模块时注入，源码不 `import` 它。所有 I/O 只能通过 `yield ctx.query`／`ctx.act`／`ctx.decide`／`ctx.wait`／`ctx.progress`／`ctx.log` 发出；不采用 XML，也不构建节点图。**

`manifest` 声明 `id`、`mode`（`finite` 或 `continuous`）与 `parameters`。`run` 是作者编写的策略生成器：运行时推进到下一个 `yield`，执行对应命令，再把结果注入生成器。控制流由 JS 本身表达，但每一条游戏读写都必须表现为 ctx 命令。

```js
defineBehavior({
  manifest: {
    id: 'gather-ore',
    mode: 'finite',
    parameters: {
      item: { type: 'string', required: true },
      want: { type: 'number', required: true },
    },
  },
  *run(ctx) {
    let mined = 0
    while (mined < ctx.params.want) {
      const inv = yield ctx.query('inventory', {})
      const pos = yield ctx.query('position', {})
      const pick = yield ctx.decide('pick-ore', {
        inv: inv.value,
        pos: pos.value,
        item: ctx.params.item,
      })
      if (pick.kind === 'none') return ctx.fail('NO_CANDIDATE', 'no ore visible')
      yield ctx.act('move-to', { x: pick.x, z: pick.z })
      yield ctx.act('mine-one', { pos: pick.pos })
      mined += 1
      yield ctx.progress({ mined, want: ctx.params.want })
    }
    return ctx.succeed({ mined })
  },
})
```

为什么用 generator 而不是 `async/await`：

- 每个 `yield` 是明确的调度、取消与计时边界；运行时可以在边界注入结果、检查取消并实施单步预算。
- `async` 程序无法可靠抢占作者写出的 CPU 循环，也无法保证取消后没有遗留的异步链。
- generator 仍是普通 JS，作者不必学习另一套节点 DSL；代价是 I/O 被限制为显式命令，不能直接调用游戏接口。

### 5.2 静态检查与单步执行

**不存在“构建期生成节点图、运行期再求值”的两段式：模块本身就是产物。** 检查器读取不可变源码，校验模块顶层对 `defineBehavior` 的调用、manifest、参数 schema、禁用语法、引用解析与依赖闭包，并生成记录模块、摘要和依赖清单的 artifact；执行器加载该 artifact 并驱动生成器。启用前检查、产物身份与凭据规则见[扩展生命周期](BEHAVIOR-LIFECYCLE.md)。

运行期允许普通 JS 控制流，包括条件、循环、函数、闭包和纯计算；这正是 behavior 表达力的来源。但它不是任意程序：

- 所有游戏 I/O 必须通过 `yield` 的 ctx 命令；不得直接访问游戏、ControlOp、broker 或 provider。
- 禁止 `import`／`require`／`process`／`eval`／`Function`／`WebAssembly`／`fetch`，不注入计时器、文件或网络能力；禁止 `async`／`await`，以保持单步语义。
- 运行时不会执行作者传入的 Promise 或回调；命令之外的代码只应做有界纯计算。

单步执行以 `yield` 为边界：运行时一次推进到下一个命令，长 act 由端口异步驱动，不等待其完成。每一步有 CPU 时间预算，初值 **50ms**；超时按 `BEHAVIOR_STEP_TIMEOUT` 失败并走 act 收尾。长时间不让出的循环会被中断，作者必须让策略周期性 `yield`。

静态检查只能确认模块符合契约，不能证明生成器一定终止、每条路径都不抛错或目标可达。

### 5.3 选择理由与能力边界

**选择生成器协程，是为了用熟悉的 JS 表达顺序、分支、循环和函数复用，降低复杂策略的编写与维护成本。** 作者不必等待执行器新增专门的控制结构，参数化、局部函数与纯计算可直接使用语言能力。

代价是可审计性下降。behavior 没有计划结构或节点图，agent 与人类只能阅读代码，并通过运行字段（当前步骤、`activeAct`、`activeTarget`、`waiting`、`progress`、`lastFailure`、`lastRun`）推断当前阶段与下一步。完成条件、时效判断和恢复路径都写在代码里，静态检查无法证明其正确。

表达方式的变化不会带来新的游戏能力：

- 读操作仍受 QueryOp 约束，写操作仍受 ControlOp 与 act 契约约束；behavior 不能绕过 broker 直接调用游戏接口。
- 需要新的游戏能力时，仍须扩展 operation 库或 act，不能靠 behavior 代码自行实现。
- behavior 仍然无智能，只执行作者写定的策略；规划、目标选择与模型会话由 agent 承担。
- 单线程、单动作控制权、统一停止与收尾等执行约束不因改用 JS 而改变。

### 5.4 局部状态与数据流

**`ctx.params` 是启动时的只读快照；运行内状态由作者用普通 JS 局部变量、闭包或对象维护，执行器不提供单独的 locals 槽位。** 状态随本次生成器实例存在，运行结束、失败或取消即丢弃，不跨运行恢复，也不能写回 artifact。需要当前事实时重新查询世界；需要跨运行保留的信息必须由外部显式保存。

查询返回 `{ value, meta }`，`meta` 包含来源、作用域、采样时间与有效期。**时效不会自动传播**：快照被保存、复制或参与纯计算都不会刷新观测时间；跨 `yield` 复用旧快照前必须显式调用 `ctx.fresh(snapshot, maxAgeMs?)` 校验并取值，过期或无法证明新鲜时分别抛出 `STALE_OBSERVATION`／`FRESHNESS_UNPROVABLE`。读取新事实的唯一方式是重新 `query`；等待或执行 act 花费的时间不会让旧快照变新。

`ctx.act` 成功时恢复为 act 的输出，失败时抛出 `P2Error`；`ctx.query` 与 `ctx.decide` 失败同样抛出。作者可以用 `try/catch` 做局部恢复（重试、降级或切换分支），重试预算与错误分类由作者决定，运行时只记录结果。`ctx.fail(code, message)` 表示业务失败，不能被“目标已达成”掩盖；agent 通过 `lastRun` 读取失败原因。

`ctx.decide` 只做一次策略纯计算：输入是显式传入的 JSON 值，返回 policy 的结果，不附带观测元数据。允许 behavior 内联纯计算（距离、比较、参数整理）；跨 behavior 复用的决策应提取为 policy 产物。policy 不能读取或修改 behavior 的局部变量，也不能发起游戏操作；需要保留输入快照的时效时，应保留原 `{ value, meta }` 并在使用前调用 `ctx.fresh`。

## 6. behavior 运行契约与完成判定

**合法 behavior 由 manifest 与 run 共同声明运行契约，执行器依据统一契约执行、判定和报告。** behavior 定义不包含 agent 连接或模型会话调用逻辑。运行期命令、状态字段与可观测性见 [BEHAVIOR.md](BEHAVIOR.md)。

### 6.1 必需声明与可选扩展

| 内容 | 要求 | 职责 |
| --- | --- | --- |
| `manifest.id`、`parameters` | 必须 | 标识 behavior 并声明启动参数 schema；参数在启动时按 schema 校验，形成只读快照。 |
| `manifest.mode` | 必须 | `finite` 或 `continuous`，决定完成判定方式。 |
| 完成证据 | `finite` 成功时必须 | `run` 最终 `return ctx.succeed(evidence)`；evidence 为有界 JSON，由运行时记录。 |
| 运行内状态 | 按需 | 作者在生成器局部变量或闭包中维护；执行器不寻址、不恢复。 |
| 进度与日志 | 可选 | 通过 `yield ctx.progress`／`ctx.log` 上报；未声明时仍提供基本运行状态。 |
| 失败与恢复 | 可选 | `ctx.fail` 表达业务失败，`try/catch` 做局部恢复；未捕获错误按运行失败处理。 |
| 状态维护与事件发送 | 执行器统一提供 | 终态、事件与状态由执行器记录和上报；behavior 不另建上报通道。 |

**取消由执行器发起。** 收到停止或切换请求后，执行器停止当前 act，并调用生成器的 `generator.return()`；此后任何 ctx 命令都被拒绝。生成器的 `finally` 只能清理纯状态（例如释放本地句柄、重置变量），不能发出游戏动作，也不能等待新的 I/O。取消不可被 `try/catch` 吞掉：被取消的行为不能把取消转成成功，晚到的 act 结果也不能推进已结束的运行。

错误分类与收尾：未捕获的 `P2Error` 使本次 run 失败；其他未知异常记为 `BEHAVIOR_SCRIPT_ERROR`；两种情况都先完成 act 收尾，再报告终态。`ctx.fail(code, message)` 记录业务失败；生成器结束但未给出 `succeed`／`fail` 也按运行失败处理。

### 6.2 完成判定

- **`mode: "finite"`**：成功时必须最终 `return ctx.succeed(evidence)`。目标达成后停止后续动作、完成 act 收尾并记录证据，运行才进入成功；`return ctx.fail(code, message)` 进入业务失败。
- **`mode: "continuous"`**：不声明有限完成条件，由 agent 请求停止或切换，执行器发起取消；单次 act 成功不代表整个 behavior 成功，被停止时记录取消。

完成判定只读取本次运行已获得的状态与观测，不额外执行游戏动作。需要确认最新事实时，由 `run` 显式发起查询；执行器不替作者推断“目标已达成”，也不机械地把一次动作完成当作 behavior 完成。

evidence 由运行时记录并写入 `lastRun`，但**无法静态检查**：检查器不能证明 `run` 一定会产生成功终态，也不能校验 evidence 是否真的对应玩家目标。agent 必须读取运行结果与证据判断完成质量；这是用 JS 表达策略所付出的可审计性代价。因此，`ctx.succeed` 应携带可核实、有界且语义明确的证据，`ctx.fail` 不应被“看起来完成了”掩盖。停止请求优先于尚未提交的成功或失败；终态一旦记录，不因晚到消息改变。

## 7. 执行器、调度与切换

**behavior 描述策略，执行器统一落实调度与切换，act 实现动作的启动、推进和停止。** 执行器集中管理运行机制，不承担采矿、返家等具体游戏策略。

### 7.1 职责划分

| 内容 | 定义或发起方 | 落实方 |
| --- | --- | --- |
| 行为顺序、条件与优先级 | behavior | 执行器 |
| 步骤推进与等待规则 | 执行器的统一语义 | 执行器 |
| 更换 behavior 的请求 | agent 等上层调度者 | 执行器 |
| 动作停止的具体操作 | act 的实现 | 执行器请求，act 完成 |
| 当前步骤、等待原因与切换状态 | 执行器 | 保存在对应 run 的运行状态中 |

behavior 作者不自行实现定时器、取消流程或并发管理。

### 7.2 控制流与错误处理

**behavior 的顺序、条件、循环、重试与错误处理由作者用普通 JS 写定；执行器不提供 `sequence`、`if`、`repeat` 等节点，也不解释表达式。** 运行时只认识 `yield` 命令：generator 恢复后执行到下一个 `yield`，执行器按命令类型等待结果并恢复。

- **顺序与等待**：代码按语句顺序推进；每个 `yield ctx.query`／`ctx.act`／`ctx.decide`／`ctx.wait` 都暂停 generator，直到结果返回或失败抛出。
- **条件与循环**：`if`、`while`、`for` 与普通函数直接使用；判断依据是代码中的局部变量和刚恢复的观测。执行器没有独立的周期性条件求值轮次。
- **重试与恢复**：`try/catch` 捕获 act／query／decide 的 `P2Error`，重试次数、退避与放弃条件由作者决定；运行时只记录结果。
- **长期策略**：用循环、`ctx.wait` 与 `ctx.progress` 组织；行为必须周期性 `yield`，否则被单步超时终止。
- **决策**：需要 policy 时 `yield ctx.decide`，结果恢复到局部变量，由后续代码使用。
- **失败**：`return ctx.fail(code, message)` 主动失败；未捕获错误或自然返回按运行失败处理。

控制结构由代码表达，因此执行器不需要区分“普通流程推进”和“持续重新决策”：两者都是作者代码在不同 `yield` 之间做出的选择。切换整个 behavior 由执行器负责，见 §7.5。

### 7.3 统一节拍调度

首版使用固定调度周期，可暂以 **100ms 一次**作为起点，之后根据实测调整。这不是端到端反应时间保证。

每次调度处理已到达的命令结果、取消与切换请求，在 `yield` 边界恢复 generator，执行到下一个 `yield` 或终态；需要时启动或停止 act。

每次推进只做有限工作并尽快返回，不等待长动作完整结束。behavior 的调度频率不必等于底层动作的更新频率：移动等 act 及其底层实现自行处理动作细节，执行器不反复启动同一个正在执行的动作。

执行器没有独立的条件求值轮次：act 运行期间 generator 停在 `yield ctx.act`，不会被重新执行；需要新事实时，必须等命令返回或失败后，由代码再次 `ctx.query`。

### 7.4 中断与动作停止

执行器统一发起中断，act 必须实现实际停止能力。动作接口包含启动、推进或查询状态、请求停止、确认停止；runner与broker的契约见[接口文档](CONTRACTS.md)。

停止操作可包括停止寻路、解除持续控制、清理自身回调等。behavior 不直接停止其他 act，而是由执行器管理当前控制权。仅记录取消意图，不代表角色已经停止动作。

### 7.5 behavior 的切换

每个角色只运行一个主动 behavior，这是长期架构约束。切换采用“先停止，再接管”：

```text
接收新 behavior 的切换请求
    ↓
当前 behavior 停止推进新动作
    ↓
请求停止当前正在执行的 act
    ↓
确认旧动作停止
    ↓
启动新 behavior
```

behavior 内部的分支由代码选择，不存在执行器层面的分支切换。一次 act 未完成前 generator 不会恢复，因此不能在 act 运行期间根据新观测改走其他分支；需要中途改变策略时，由 agent 请求切换 behavior，或由 act 按自身契约处理局部调整。

- 旧动作晚到的结果不能继续推进新流程，执行器必须区分结果所属的运行。
- 停止超时不能视为停止成功；旧动作仍可能控制角色时，不启动与其冲突的新动作。暂定故障处理见第 7.9 节。
- 取消不会自动撤销已经发生的世界变化，例如已经放下的方块。

首版优先保证可靠切换，不要求恢复 generator 栈。重新选择原 behavior 时，从模块开头重新执行，根据当前世界状态重新开始；精确恢复留待确有需求时设计。

generator 推进、调度与切换统一组织在执行器内部，对外提供请求切换、停止、读取状态等少量操作。accepted与实际started/terminal区分，commandId用于查询最终结果，详见[接口文档](CONTRACTS.md)。

### 7.6 长期约束：单线程调度与单动作控制权

**behavior 采用单线程、非阻塞的调度方式，不提供通用并行；同一时刻至多一个 act 持有角色控制权。** 这是长期设计边界，不作为以后增加并行行为分支的过渡方案。

执行器轮流处理命令结果、动作进度、取消与切换请求，每次处理有限工作后返回，组织方式类似事件循环。单线程本身不能防止多个异步动作争抢角色，因此执行器还必须显式管理控制权，拒绝同时启动相互独立的多个控制 act。

当前 act 运行期间，generator 停在 `yield ctx.act`，执行器只推进 act、等待结果并处理取消；不会重新执行 behavior 代码，也不会评估其他条件。需要在动作中途改变决定时，只能由 agent 切换 behavior，或由 act 在自身职责内处理。

这一约束不要求模型推理、只读查询或底层非阻塞操作全部串行等待。一个 act 内仍可协调多个 op 的持续效果，具体边界见第 3.4 节；behavior 不将这些协调拆成争抢控制权的并行 act。

以采集时遭遇威胁为例：采集 act 尚未返回时，behavior 不能插入威胁处理；要中途停止采集，需要 agent 切换 behavior，或由 act 自身按契约处理。act 返回后，代码可以根据新的查询决定继续采集、重试或失败，不承诺从被打断的动作内部精确续接。

选择战斗、躲避或其他处理方式由 behavior 代码或 agent 的切换决定；执行器只负责停止、启动与等待，不自行评估条件。公共应对逻辑可以写成普通函数或独立 behavior 产物，不另开并行 behavior。若当前 behavior 未定义适用行为，执行器不会自行发明应对策略。

### 7.7 单步推进与等待状态（暂定）

behavior 没有节点或节点状态机。运行时可观察的是 run 状态、`currentStep`、`waiting`、`activeAct`／`activeTarget` 与收尾阶段；下表描述一次运行的推进形态，不对应可寻址的步骤树。

| 形态 | 含义 |
| --- | --- |
| 未推进 | generator 尚未启动，或上一个 step 已结束、等待下一次恢复。 |
| 推进中 | 正在执行两次 `yield` 之间的 JS；受单步 CPU 预算约束。 |
| 等待命令 | generator 停在 `yield`，等待 query／act／decide／wait 的结果或失败。 |
| 收尾中 | 已收到取消或终态意图，正在停止 act、结束 generator 并确认释放控制。 |
| 终态 | succeeded／failed／cancelled；收尾完成后才对外提交。 |

generator 只有一个恢复点，没有父/子步骤或按步骤区分的取消。取消、超时或终态后的晚到结果不会恢复 generator；新一轮运行重新从模块开头执行。

`blocked` 是 run 的业务状态，不是步骤状态；它表示已完成动作收尾后在等待外部决定，不表示还有子步骤在运行。

### 7.8 取消与交接（暂定）

取消是控制信号，不按普通失败传播。执行器收到停止或切换请求后，停止当前 act，调用 `generator.return()`，之后拒绝任何新的 ctx 命令；generator 的 `finally` 只能清理纯状态。

- 更换 behavior 时，先停止旧 run 的 act 并确认收尾，再启动新 run；不恢复旧 generator 栈。
- 同一个 behavior 内没有执行器层面的分支取消；代码路径的退出由 JS 控制流完成。
- 停止请求必须幂等：重复请求不重复启动清理过程，也不重置停止期限。
- 一旦开始停止，就完成本次停止；即使条件恢复，也不恢复 generator。
- 取消不能被 `try/catch` 吞掉，也不能把取消转成成功；晚到结果不恢复 generator。

### 7.9 停止及收尾超时的故障处理（暂定）

**超时表示未能按时确认停止或完成收尾，不证明旧动作已经停止，也不证明它一定还在执行。执行器必须保留旧控制权归属并暂停动作推进，不能将超时当作普通失败后继续启动动作。**

```text
请求停止或进入结束收尾
           ↓
在期限内确认完成？
    ├─ 是 → 结束旧运行，允许后续动作
    └─ 否 → 标记执行器故障，暂停动作推进
                     ↓
             继续收集结果并提供反馈
```

这套处理覆盖取消、正常成功和正常失败的所有收尾路径。即使行为已决定结束，只要仍无法确认持续控制释放，就不能交接给下一个 act。

故障期间不启动新控制 act，也不启动用于救场的另一个 behavior。保留旧 act 的归属信息，允许其完成停止与清理；当前事实查询、状态查询及执行反馈仍可用，新的策略请求不能绕过交接规则。

故障属于执行器状态，不按步骤或 act 伪造完成状态。取消中的 act 可以保持停止中，并记录已经超时。该故障不能伪装为普通 behavior 受阻：材料不足时可以安全更换 behavior，控制权未释放时不能。

解除故障须有明确依据，暂定允许两条路径：

1. 旧 act 的停止或收尾确认晚到，执行器确认清理完成、控制权释放，再重新评估当前请求并继续调度。
2. 底层确实提供可靠的控制重置能力，且确认旧控制与未完成操作已失效，执行器才允许重新接管。是否支持这一能力取决于 operation 库，不能仅清空执行器引用就宣称停止成功。

始终无法确认时保持故障状态，交由 agent 或人工处理。agent 可以取消后续目标、调整策略或请求受支持的恢复流程，不能通过更换 behavior 消除故障。

停止与收尾采用第 7.10 节的总期限与有限重试规则；重复请求不延长总期限，超时不强行交接，恢复必须得到明确确认。

### 7.10 停止与收尾的期限及重试规则（暂定）

**停止请求本身不反复重发；明确可重试的收尾操作最多自动重试一次，即总共尝试两次；所有尝试共用一个总期限。**

| 情况 | 处理规则 |
| --- | --- |
| act 正在停止，尚未返回结果 | 继续推进、等待，不算重试，也不重新启动停止流程。 |
| 某个收尾 op 明确失败，且允许安全重试 | 最多自动重试一次，使用总期限内的剩余时间。 |
| 停止或收尾已超过总期限 | 进入执行器故障，不开启新一轮自动重试。 |

重试针对失败的收尾操作，不重新执行整个 act，也不将已完成的清理全部重做。例如停止移动已成功、取消未结束操作发生可重试错误时，只重试后者。执行器统一管理次数和期限，act 按自身收尾流程报告结果；执行器、act 与 op 不得各自独立叠加重试预算。

自动重试必须同时满足以下条件：

- op 契约明确允许安全重复调用，不会产生重复副作用。
- 返回结果明确表明本次尝试已结束，且错误属于可重试类型。
- 总期限尚未耗尽。

不支持操作、参数错误等情况不自动重试；不能保证重复调用安全的操作也不自动重试。请求超时且无法确定前一次是否仍在执行时，可以按契约查询进度或继续等待，不能直接启动第二个同类操作。底层若支持对同一请求安全重发，须由 operation 库明确实现这一保证，并遵守统一预算。

最多一次重试是当前控制复杂度的暂定选择，给偶发错误一次恢复机会，不作为已经实测得出的最佳次数。

总期限从执行器首次请求停止，或 act 开始正常结束收尾时计起，覆盖取消、正常成功和正常失败的结束路径。每次重试及重复请求均不重新计时。

```text
开始停止／收尾
      ↓
在总期限内推进清理
    ├─ 成功 → 结束并释放控制权
    ├─ 可重试失败且尚有重试预算 → 重试一次，使用剩余时间
    ├─ 无法恢复或重试预算耗尽的清理失败 → 进入故障
    └─ 总期限耗尽 → 进入故障
```

期限是最长容忍时间；已经明确无法完成清理时，不必空等到期限耗尽。由执行器提供统一默认期限，允许受控配置为特定 act 覆盖；agent 编写的 behavior 不能任意延长期限，也不能通过重复请求重置计时。具体数值留待 operation 实现后，根据停止与收尾耗时测量确定。

进入故障后，晚到的停止或收尾确认仍可按第 7.9 节解除故障，但不再自动开启新一轮清理尝试。可靠的底层重置属于单独恢复流程，不隐藏为普通自动重试。

上述预算仅约束停止与收尾。路径不可达后换目标、采集失败后重新尝试等行为重试，仍属于 act／behavior 的策略规则，不共用这里的次数。

### 7.11 QueryOp 的异步等待、结果有效性与失败规则（暂定）

**查询通过 `yield ctx.query` 发起一次请求；命令完成前 generator 保持 waiting，不会被并发推进。QueryOp 一次调用只发起一次请求，失败或超时即抛出，不自动重试。**

`yield ctx.query` 提交后，执行器记录 `currentStep` 与 `waiting`，继续处理取消、失联、清理及其他 run 的调度；结果到达后才恢复当前 generator。generator 只有一个恢复点，同一时刻不会有两个未完成的查询或 act。

| 阶段 | 处理 |
| --- | --- |
| 发起 | `yield ctx.query` 提交一次请求；`currentStep` 形如 `query:position`。 |
| 等待 | generator 挂起；执行器继续处理取消、清理与其他调度。 |
| 返回 | 恢复 generator，值为 `{ value, meta }`。 |
| 明确失败或超时 | 向 generator 抛出 `P2Error`。 |
| 取消 | 丢弃等待中的请求与晚到结果，不再恢复 generator。 |

纯读取请求的取消不一定要求底层立即停止计算。只要晚到结果不能恢复已结束的 generator，P2 就可以结束本次查询；底层支持取消时，同时释放对应资源。查询没有持续控制效果，不需要像控制 act 一样等待释放角色控制权。

结果有效性分为两类：

- **归属有效性**：结果属于当前请求、当前 generator 及当前游戏连接。旧 behavior、旧 run 或连接重建前的请求不能恢复当前 generator；失败、超时或取消后的晚到结果也不能重新推进已结束的查询。
- **时效有效性**：结果的观测时点满足使用方允许的数据年龄。摘要与动作前置判断可以有不同要求，不为所有 QueryOp 统一规定一个固定有效期。

结果返回时间不一定等于观测时间。operation 应说明数据的观测时点；无法精确提供时使用保守的时间范围，不能按刚返回的时间将旧数据视为新鲜数据。超过使用方允许的时效或归属无效的结果不予接受，不能用于条件判断或据此启动新动作。

需要最新事实时须重新查询，但不将结果失效隐式转化为 QueryOp 内部自动重试。时效合格也不保证世界尚未变化；act／ControlOp 仍须处理真实执行时的失败。例如查询时材料充足，不等于之后一定合成成功。

| 情况 | 结果含义 |
| --- | --- |
| 在约定范围内成功查询，没有匹配目标 | 查询成功，结果为空。 |
| 部分数据不可见或不可用 | 按契约返回明确范围的部分结果，或报告数据不足。 |
| 接口不可用、连接中断、请求异常 | 查询失败，返回原因。 |
| 超过等待期限 | 查询失败，原因是超时。 |
| 结果已过时或不属于当前运行 | 不接受该结果，不能用于条件判断。 |

每个 QueryOp 明确是否允许部分结果，调用方必须知道结果覆盖的范围。“没有查到”与“无法查询”不能都变成条件为假，也不将未知数据伪装为不存在。具体可见范围与游戏数据内容留待游戏相关设计。

查询没有独立的“条件节点”，也不存在执行器替 behavior 周期求值的条件。相关规则是：

- 查询未完成时 generator 不会继续，因此不会出现“未知条件被自动当作假并改走其他分支”。
- 查询失败以 `P2Error` 抛回 generator；未捕获时 run 失败，捕获后可重试、降级或 `ctx.fail`。
- 不依据尚未完成或已经过时的观测启动新 act；旧快照必须 `ctx.fresh`。
- 如果策略要求无法确认环境就停止，由 behavior 代码显式处理；执行器不统一替所有策略作出决定。

例如采集 act 完成后再重新查询威胁；若威胁在 act 运行期间出现，behavior 不能在 act 中途插入判断，需要 agent 切换 behavior 或由 act 自身处理。查询一直无法完成时，由 `ctx.query` 抛出超时/失败，由作者代码决定后续。

QueryOp 不沿用停止与收尾操作的自动重试预算。确实需要再次尝试时，由 behavior／act 显式安排，并受次数或总期限约束。成功查询后为获取最新事实再次查询属于正常刷新；失败后再次尝试属于重试，不能用周期刷新掩盖失败后的隐式重试。

P2 只临时保存等待中的查询及必要结果，不保存历史观测、不计算环境变化，也不因此引入世界状态副本。查询期限、数据年龄的首版配置起点及跨进程时钟规则见[运行时](RUNTIME.md)，需游戏接入后实测调整。

## 8. 运行状态、恢复与事件反馈

### 8.1 运行状态与局部恢复

| 状态 | 含义 |
| --- | --- |
| 运行中 | 正在推进目标。 |
| 受阻 | 暂时无法推进，但仍可能恢复。 |
| 成功 | 已确认达到完成条件，并完成收尾。 |
| 失败 | 本次运行无法继续完成目标，已经结束。 |
| 取消 | 被主动停止或替换，已经结束。 |

“正在停止”等可作为内部过渡状态，收到请求不等于停止已完成。上述 behavior 状态是业务状态，不等同于 `currentStep`、`waiting` 等执行字段。

act 提供目标消失、路径不可达、材料不足等具体结果；behavior 代码用 `try/catch` 决定重试、降级或 `ctx.fail`。执行器只记录结果，不自动重试或换目标。需要外部决策时由 agent 处理；重试预算与总期限由 behavior 代码或配置约束，详见[运行时](RUNTIME.md)。

执行器不自行发明新的游戏策略。例如路径不可达后是否挖掘通道，应由 behavior 或 agent 决定。

### 8.2 状态查询与事件通知

执行器同时提供当前状态查询与主动的结构化事件通知。**通知 agent 不等于直接发起一次 LLM 会话。**

本节的事件仅指执行过程与结果的反馈，不要求观测层记录或生成环境变化事件。

```text
执行器更新状态并产生事件
    ↓
agent 侧调度逻辑接收事件
    ↓
决定是否、何时调用模型，以及附带哪些信息
```

| 事件或信息 | 基本处理原则 |
| --- | --- |
| 普通 act 变化、可恢复错误 | 记录，供查询和调试，不逐次唤起模型。 |
| 有意义的进展 | 更新摘要，可合并或限频通知。 |
| behavior 成功或失败 | 上报最终结果，供 agent 安排下一步。 |
| 受阻且需要外部决策 | 上报原因并标明需要决策。 |
| 停止或收尾超时导致执行器故障 | 提供故障及控制权未释放的信息；不得报告旧动作已停止或新 behavior 已接管。 |
| agent 自己发起的取消或替换 | 返回完成确认，通常无需再次唤起模型。 |
| 持续 behavior 正常工作 | 保持运行，不反复通知“仍然正常”。 |

事件应能说明所属 behavior 实例、状态变化、原因、可核实的结果或证据、可用的进度信息、已尝试的恢复动作，以及是否需要 agent 决策。字段、去重、合并、session投递与日志保留见[反馈与恢复](FEEDBACK-AND-RECOVERY.md)。

agent 侧负责事件排队、合并和模型调用调度。面向玩家的语言汇报主要由 agent 根据事实与对话情境组织；执行器不自行生成聊天内容。模型思考期间，执行器仍按当前 behavior 的规则运行或等待。

### 8.3 运行时反馈与检测分离

真实环境导致的动作失败，由 act 提供具体原因，执行器更新状态并产生结构化事件，agent 侧根据反馈决定调整参数、更换 behavior 或采取其他措施。behavior 代码中的 `try/catch` 局部恢复先于 agent 介入，执行器只记录结果。

act 执行失败不直接等于整个 behavior 失败，也不意味着 behavior 模块或接口不合法。随着游戏进行，由 agent 根据实际反馈迭代 behavior 的机制属于另一套流程，详见[扩展生命周期](BEHAVIOR-LIFECYCLE.md)，不合并进检测器。

### 8.4 首版日志与资源边界

D6 首版只提供异步 JSONL 调试日志和当前进程内的状态/去重/反馈队列。日志按大小轮换，允许删除旧文件和丢失崩溃尾部；写失败仅报告 loggingUnavailable，缓冲满则丢弃并计数，不阻塞行为或控制清理。accepted 和业务终态不等待落盘，不承诺重启后可查询。

请求、查询、检查、协议输出和 bridge 事件队列均有上限；普通工作满载时拒绝新增，停止、shutdown、heartbeat 和清理保留独立额度。命令 ID 在同 epoch 内不因日志轮换被忘记，内存额度满时拒绝新增普通业务；重启使用新 epoch、空运行，不恢复旧命令或通知。首版不实现持久索引、事务提交、日志修复、持久 pending 队列/ack 或崩溃自动对账。源码、artifact、显式目标及偏好文件仍保留；这些文件不代表旧运行状态已恢复。详见[调试日志](FEEDBACK-AND-RECOVERY.md#31-简单调试日志)与[队列规则](FEEDBACK-AND-RECOVERY.md#33-有界队列与停止优先)。

## 9. 被动的 behavior 检测器

**检测器验证 behavior 与执行器之间的契约，不验证真实游戏环境是否允许动作成功。** 它是被动工具，接收检查请求后返回通过或可定位的错误，不启动 behavior、不修改 behavior，也不触发 agent 会话。

### 9.1 定位与校验范围

检测器只负责语法、类型与模块检查，定位类似 `cargo check`，不负责行为测试。behavior 的结构与运行契约要求尽量通过类型定义、manifest 与 ctx 接口表达，不另行分析策略意图。

检查范围覆盖三类内容产物：behavior（模块、manifest、参数 schema 与引用）、act（代码结构、声明的 op 与封闭模块）、policy（纯函数结构、声明的输入输出、无 op 与无副作用语法）。三者的检查都不连接游戏、不试运行、不模拟环境。

通过检测意味着 behavior 模块在对应版本的执行器、act 接口及已声明的 operation 能力下合法，可以被接受并执行，不意味着动作一定成功。检测器不依赖真实 Minecraft 环境，也不模拟游戏环境或接口。本章后续小节说明完整职责。

### 9.2 检查流程与契约依赖

| 检查 | 要回答的问题 |
| --- | --- |
| 语法检查 | 源码能否被语言工具正确解析？ |
| 类型检查 | manifest、参数 schema、ctx 命令、act／policy 引用与返回值是否符合实际接口契约？ |
| 模块检查 | 模块能否加载并调用 `defineBehavior`，产生可执行的 manifest 与 generator？ |

复用现有语言工具进行语法与类型检查。模块检查在隔离环境加载模块、读取 manifest 与 generator，不执行 `run`，不推进 behavior、不执行 act 的游戏动作，也不调用实际 QueryOp 或 ControlOp，不需要真实观测或模拟输入。加载异常、模块形状非法或超时属于检查失败，因为未能成功获得可接受产物。

检测器与执行器应共享实际的类型定义、act 注册信息及其依赖的 operation 契约与可用能力声明，避免双方认可的接口不一致。这些信息由库与运行配置提供，不要求检测器连接游戏以探测能力。读取这些契约信息不等于模拟游戏接口。检查阶段使用 manifest、参数 schema、act／policy 引用与静态能力声明，实际游戏数据由运行时提供。

### 9.3 契约校验的边界

manifest 必需字段、参数 schema、ctx 命令与 act／policy 引用、可选字段要求，应纳入类型定义、manifest 与 ctx 接口，由检测器完成语法、类型和模块检查。它不判断 `run` 中的完成条件是否正确表达玩家意图，也不保证策略合理或目标可达。

### 9.4 通过检测的保证与限制

在对应版本的执行器、act 接口及已声明的 operation 能力下，behavior 模块合法，每个 ctx 命令与 act／policy 引用可以被执行器识别、接受并交给对应实现处理。这里的“能够执行”不等于“执行成功”，也不证明自定义 act 或底层 op 的实现没有运行时缺陷。

检测不保证目标可达、材料充足、任务能够完成、行为符合预期或策略高效，也不构成对任意模块代码安全性的证明。

| 情况 | 处理阶段 |
| --- | --- |
| 引用了不存在的 act | 检测阶段拒绝。 |
| 引用了不存在或当前能力声明不支持的 QueryOp／ControlOp | 契约依赖检查阶段拒绝，不通过真实游戏探测。 |
| `goto` 的目标类型不符合接口要求 | 检测阶段拒绝。 |
| 模块无法加载或 manifest 非法 | 检测阶段拒绝。 |
| `goto` 目标合法，但在真实世界中不可达 | 运行时反馈失败。 |
| 合成调用与配方参数合法，但实际材料不足 | 运行时反馈失败。 |
| 各个动作都可执行，但整体行为不符合玩家预期 | 交由独立的游戏内反馈循环处理。 |

## 10. 暂定示例：区域资源采集

以下 JavaScript 风格示例用于说明 behavior 的编写方式。act／policy 名称与参数类型为暂定接口，尚无对应实现，不是可直接运行的代码。

```js
defineBehavior({
  manifest: {
    id: 'collect-resources',
    mode: 'continuous', // 持续采集，直到被停止、替换或无法继续。
    parameters: {
      area: regionType(),
      resource: resourceType(),
    },
  },
  *run(ctx) {
    let completedHarvests = 0
    while (true) {
      const candidates = yield ctx.query('resource-candidates', {
        area: ctx.params.area,
        resource: ctx.params.resource,
      })
      ctx.fresh(candidates)
      const picked = yield ctx.decide('select-resource', {
        candidates: candidates.value,
      })
      if (picked.kind === 'none') {
        yield ctx.wait(1000)
        continue
      }
      yield ctx.act('move-to', { target: picked.target, reach: 'interaction' })
      yield ctx.act('equip-for', { target: picked.target })
      const harvested = yield ctx.act('harvest', { target: picked.target })
      completedHarvests += 1
      yield ctx.progress({ completedHarvests, last: harvested })
    }
  },
})
```

这个示例表达“在指定区域选择资源目标，移动到可交互位置，装备合适工具并采集，然后重复”。它是持续行为 behavior，不声明有限数量目标；`mode` 的字段名称与取值同样为暂定。

- `manifest.parameters` 声明实例内只读参数；没有单独的 locals 声明，`completedHarvests` 只是 `run` 内的普通局部变量，随本次运行结束而丢弃。
- `run` 是生成器；模块加载时只声明 manifest 与 `run`，不在加载阶段执行采集。执行器每次推进到下一个 `yield`，按命令等待结果后恢复。
- `ctx.params.area`、`ctx.params.resource` 在运行时读取；查询结果也是运行时返回的实际值，不需要预先声明的数据引用。
- `yield ctx.query` 返回 `{ value, meta }`，示例用 `ctx.fresh` 显式校验时效；`yield ctx.decide` 调用 policy 做纯选择，返回受限 JSON。
- `harvest` 的输出只在 act 成功并完成收尾后恢复；随后才增加一次 `completedHarvests`。失败或取消不能沿用上一轮输出，也不增加成功次数。
- `completedHarvests` 表示成功完成采集的次数，不代表背包中的物品数量；若目标是背包拥有指定数量的资源，须另用当前背包查询判断。
- `candidates` 的 `meta` 不会因保存或传给 `ctx.decide` 而变新；`picked` 只是 policy 的返回值。长动作后如需目标的最新状态，应重新查询，不能因 target 仍保存在局部变量中就认为事实一直新鲜。
- `while` 是普通 JavaScript 循环，由 `yield` 周期性让出；空结果时用 `ctx.wait` 避免忙循环。这里没有 `sequence`／`repeat` 节点，也没有执行器维护的循环位置。

示例只展示正常采集路径。查询返回空集合后的选择处理、目标失效、材料或工具不足等游戏规则由 `run` 中的代码决定，示例不暗示执行器自动选择恢复策略。状态与事件由执行器按统一契约管理，不在示例中自行发送；局部变量赋值立即可见，但查询、动作及收尾等待可能使执行跨越多个 tick。新动作前仍须重新确认受更新影响的条件，读取新值不等于取得最新游戏事实。

### 11.2 已有契约、仍需实现验证的内容

[接口文档](CONTRACTS.md)定义 behavior 模块、ctx 命令、act hook、op 结果、错误、body 命令、事件及版本绑定。代码片段是契约草案，不是可以直接运行的完整SDK。

- 查询/收尾期限、调度周期及数据年龄已有起始配置，需用运行测量调整，不能当SLA。
- 自定义act/policy的受限JS引擎需要中断、内存与宿主能力隔离验证；未完成前先用维护者 act 与最小 ctx 命令集，不把生成代码直接放进body。隔离只承诺三项：不能访问宿主能力、不能超出资源预算、不能绕过控制账本；不承诺语义安全或第三方代码可信，见[隔离设计](ISOLATION.md)。
- checker、日志、消息去重与生命周期仍需软件实现和测试；checker不因此增加模拟游戏职责。
- 初版单包交付已定；bridge/body/provider/authoring 的内部边界仍须通过 import-boundary 检查。首版须实测 `bundles/` tarball 干净安装、项目 authoring 版本一致、托管进程树回收、依赖闭包和离线安装；拆包与独立 launcher 后续验证。
- 崩溃时持续控制能否可靠释放由provider验证；P2不能仅凭进程退出宣称游戏已停止。

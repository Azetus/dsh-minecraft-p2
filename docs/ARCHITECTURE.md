## 1. 项目目标与设计原则

让 agent 以第二名玩家的身份参与 Minecraft，与人类玩家交流、协作，并根据玩家指令、自身目标和环境变化安排角色的行动。

agent 的控制方式类似策略游戏或 RTS：为角色选择和调整持续生效的行动策略，而不是逐次决定移动、攻击等具体操作。策略执行期间，角色通过程序持续与世界交互，不必为每个动作等待模型回复。

这是个人项目。设计优先考虑可理解、可开发和可维护，接受行为细节与反应能力上的取舍，不以 agent 能够即时决策为前提。

首版只支持本机一个body控制一个角色，一个拥有写权限的DSH会话。目标是模型选择/编写策略、代码持续执行；不承诺硬实时生存或无条件完成任务，不实现多角色编队、通用视觉接入或任意op自动自升级。

## 2. 系统组成与职责

### 2.1 系统组成

agent 是调度者与 behavior／act 作者。P2 的运行机制包含以下三个部分，它们依赖独立维护的 operation 基础库对接游戏：

| 部分 | 职责 |
| --- | --- |
| 观测层 | 基于查询 operation 提供当前事实，并用纯函数整理查询结果与生成摘要，供 agent 及执行中的行为使用。 |
| 行为系统（behavior 系统） | 保存、描述和管理可用的行动策略，包括预设 behavior 与自定义 behavior。 |
| 执行器 | 驱动当前 behavior 及其 act 的执行，落实具体动作与行为切换。 |

系统初始提供一组预设 behavior。人类开发者与 agent 都可以添加新的自定义 behavior；agent 根据目标和情况选择适用的 behavior，在现有 behavior 无法表达所需行为时编写新的 behavior。

operation 库统一提供游戏查询与控制的基础接口及对应实现。观测层不另行维护一套直接对接游戏的查询实现，act 也不自行绕过该库调用游戏接入接口。

**Mineflayer 是首套 operation 实现的底层依赖，不是 P2 公共接口。** core 的执行器、观测层及 behavior／act 仅使用统一契约；Mineflayer 对象、类型、事件和插件句柄不向这些上层泄漏。适配层转换数据、控制生命周期与失败结果，并声明实际能力。后续真实客户端主要替换 operation 实现及游戏驱动，不改写核心机制；行为内容仍需按能力与游戏规则检查适用性。详见[接入决策与依赖边界](MINECRAFT-INTEGRATION-OPTIONS.md#12-mineflayer-与-p2-的依赖边界)。

### 2.2 观测层：查询接口与摘要纯函数

**观测层由数个游戏环境查询接口，以及根据查询结果生成摘要的纯函数方法组成。P2 提供当前事实与执行反馈，不维护 Minecraft 世界状态副本，也不记录环境变化事件。**

- **游戏环境查询接口**：通过 QueryOp 读取当前游戏数据并返回结构化结果。查询结果随游戏状态变化，读取接口本身不是纯函数；具体游戏适配由 operation 库承担。
- **摘要纯函数**：根据传入的查询结果进行筛选、计算与格式化；相同输入产生相同输出，不自行读取游戏、不保存历史、不产生副作用。
- **观测层的范围**：不保存历史观测，不比较前后环境差异，不生成环境变化事件，也不主动触发模型会话。

```text
查询 operation（QueryOp）
    ↓
结构化观测结果
    ├─→ behavior 与执行器读取、判断
    └─→ 摘要纯函数 → agent／LLM
```

一次查询的结果可以供当前判断与摘要处理使用，这不等于维护一份持续同步的世界状态。behavior 的局部变量、目标引用、执行位置与运行状态仍由 behavior 实例及执行器保存，属于行动状态，不属于世界状态副本。

查询接口具体有哪些、返回什么数据、摘要如何组织，均不在当前机制设计阶段确定。

### 2.3 环境变化理解与执行反馈的分工

| 部分 | 职责 |
| --- | --- |
| 观测层 | 提供“现在观测到了什么”。 |
| 执行器 | 提供“正在做什么、执行结果如何”。 |
| agent／session | 根据上下文中的新旧观测及执行记录，理解变化并决定下一步。 |

agent 读取的观测、发出的操作及其实际执行反馈应进入同一 session 上下文。上下文不能只记录指令并将其视为已完成；实际进度与结果应关联对应的 behavior 实例。无需将每个 tick 或每个底层动作都送入上下文。

session 承担变化的理解与回顾，不持续观察游戏，也不会因游戏发生变化自动开始推理。agent 在下一次取得观测并被调度处理时，才能据此发现变化；当前设计接受这一反应时机上的取舍。

session 中的历史信息不替代 behavior、执行器与 act 对当前数据的读取及运行时判定。未进入或未保留在上下文中的历史，不视为已知事实。

**不记录环境变化事件，不影响执行器提供执行反馈。** behavior 完成、受阻、失败、取消等仍按照第 8 章的统一机制报告；它们属于 P2 自身的执行结果，不是对世界变化的追踪。当前不为观测层另行设计环境事件系统。

### 2.4 “身体”与“大脑”的职责

**P2 核心是“身体”，agent／LLM 是“大脑”。P2 核心独立于具体游戏版本；接入差异由 operation 实现承担，游戏规则差异及其策略影响由 agent 处理。**

| 部分 | 责任 |
| --- | --- |
| operation 库 | 将统一的查询与控制契约落实到对应游戏版本或发行版。 |
| P2 核心 | 构建、检查和执行行为定义，管理控制权，提供当前事实与执行反馈。 |
| agent／LLM | 理解游戏特性，判断策略是否适用，选择、修改或编写 behavior／act。 |

agent 编写的 behavior／act 是由 P2 执行的可替换行为内容，不等同于 P2 核心机制。为适应游戏版本而重写行为，不代表核心执行架构需要适配。

P2 核心不内置 Java 版或基岩版的策略分支，不负责保证同一策略跨版本有效，也不自动修正不适用的策略。operation 忠实执行并返回结果，P2 按契约反馈，agent 根据当前环境与 session 决定后续处理。

### 2.5 部署与所有权

```text
人类 ↔ DSH现有session/agent
              ↕ P2 scoped tools、执行反馈
          薄bridge插件
              ↕ 消息协议／stdio传输适配器
          插件持有的独立body子进程
          ├─ 可信树执行器、状态与事件
          ├─ 隔离的构建／act runner
          └─ operation broker → 选定provider → 游戏连接/驱动
```

DSH不逐tick操控角色。body的串行调度器控制唯一活动act，隔离runner只承载其代码；辅助进程不产生第二个控制者。broker持有实际游戏操作的账本与清理能力，生成代码不持原始连接。

首版人工 /p2 start 后，bridge 为正确项目的现有会话创建并持有一个 body，通过 stdio 通信。安装、加载或热重载不自动创建 P2 进程；启动 body 不自动启动 behavior。body 独立调度但生命周期跟随插件，插件释放时收尾并回收 body/辅助进程，不销毁用户 agent。模型 stop 只停 behavior，人工 stop 关闭托管 body；换 session 先关闭旧 body 再人工启动。

协议层与传输层分离：首版 UTF-8 JSON Lines，stdout 专用于协议、stderr 日志；保留命令去重、epoch 和事件语义。管道失效或 bridge 存活超时后清理退出，不重连旧 body、不自动重启。强制结束不构成游戏停止证明。独立 launcher、WS 鉴权及 lease 重连已整理为[后续设计](WS-FUTURE.md)，不阻塞首版；未来迁移还需补全独立服务生命周期。详见[运行时](RUNTIME.md)与[DSH 接入](DSH-INTEGRATION.md)。

## 3. 核心概念

### 3.1 behavior：持续行动策略

**behavior 是一段持续生效的行动策略，其本质是交给执行器运行的程序。**

为避免与 DSH 内部事务的 `job` 命名混淆，P2 原称 `job` 的概念统一改为 `behavior`（行为策略），原 `jobTree` 改为 `behaviorTree`（行为树）。这次调整只改变命名，保留原有运行契约、状态与职责边界；`job` 留作 DSH 自身的事务术语。

behavior 是策略定义，behaviorTree 是其组织行为的形式，执行器负责运行它。behavior 除行为树外还包含参数、完成条件、局部状态与恢复规则，不等同于一棵裸树。术语统一使用“behavior 定义”“behavior 实例”和“行为系统”；动作层级保持 behavior → act → operation。

behavior 通过条件、循环、顺序和切换等控制结构组织 act，并保存策略需要的状态。它不是一次性指令，也不局限于顺序动作列表。

设计借鉴 RimWorld ThinkTree 的行为组织思路：通过周期性条件评估、优先级和短路选择来决定行为。这里的 behavior 在概念上接近一棵被选中的行为树；采用代码构建 behaviorTree，并由统一执行器调度，具体共识见后文。

例如，“跟随玩家并处理靠近的敌人”可以在同一个 behavior 内完成跟随、接敌和恢复跟随，不需要每次都让 agent 更换 behavior。

区分以下两个概念：

- **behavior 定义**：可复用的策略程序，例如“区域采集”。
- **behavior 实例**：带有具体参数和执行状态的一次运行，例如“在指定森林收集 32 个云杉原木”。

### 3.2 act：可复用的完整行为

**act 是可复用、可中断的完整行为，协调基础 operation 完成一项边界明确的动作。** 此概念原称 step，今后统一使用 act；改名保留原有职责与生命周期，并明确其下的 operation 实现层。

典型例子包括移动到目标附近、装备指定物品、采集一个目标。

act 的粒度不按代码量、耗时或引擎原子操作划分。移动 act 可以持续较长时间，并在内部处理寻路与局部调整；behavior 无需重复实现这些细节。

条件判断、循环和优先选择属于 behavior 的控制结构，不与具体动作混为一谈。控制结构可以由统一语法或接口提供，暂不单独增加业务层级。

### 3.3 operation：游戏基础操作

**operation（简称 op）是直接对接游戏的、可复用的基础操作，包括读取游戏数据的查询操作和改变角色或游戏状态的控制操作。**

| 类型 | 职责 | 使用约束 |
| --- | --- | --- |
| QueryOp | 读取当前游戏数据并返回结果。 | 不改变角色或游戏状态；供观测层、behavior 条件及 act 使用。 |
| ControlOp | 发起动作，设置或清除控制状态。 | 只有当前持有角色控制权的 act 可以调用。 |

“原子化”表示基础操作的粒度，不承诺瞬间完成、不可中断、事务原子性或自动回滚。部分 op 的效果会持续生效，需要 act 协调和清理。op 不拥有独立策略，也不复制一套 behaviorTree 调度机制；底层完成或错误结果由 act 接收并形成行为反馈。

```text
动作控制路径：behavior → act → ControlOp → 游戏
数据读取路径：游戏 → QueryOp → behavior／act 的判断
                              → 观测层组织与摘要 → agent
```

因此，behavior → act → op 的层级约束适用于动作控制，不要求所有读取都经过 act。behavior 查询与完成判定不占用角色动作控制权。

构建 behaviorTree 时只声明查询及其数据引用；执行器运行时才调用实际查询。QueryOp 可以采用异步实现，但等待查询不能阻塞整个调度循环；等待、结果有效性与失败处理的暂定规则见第 7.11 节。

### 3.4 一个 act 协调多个基础操作

同一时刻至多一个 act 持有角色控制权，不意味着角色只能产生一种底层动作效果。一个 act 可以在短暂更新中依次计算并提交多个 op，协调移动、朝向、交互等效果；具体游戏行为留待后续设计。

这些协调可以分解为 act 内部的可复用函数，不要求实现为一个巨大函数，也不构成 behaviorTree 的并行子树。控制权始终归属于同一个 act。

停止 act 时，必须清理它留下的持续控制、未结束操作及相关回调；未确认停止前不能移交控制权。已发生的世界变化不会被取消操作自动回滚。

### 3.5 act 与 operation 的结果及收尾契约（暂定）

**每个 act 和 operation 都应明确成功、失败及结束路径，但判定范围不同，不要求使用完全相同的状态机。**

| 层级 | 成功边界 | 失败边界 |
| --- | --- | --- |
| QueryOp | 按查询契约取得结果，包括合法的空结果。 | 无法完成查询，或无法提供契约要求的数据。 |
| ControlOp | 完成该操作承诺的效果。 | 无法完成该操作承诺的效果。 |
| act | 完成完整行为的目标，并完成收尾。 | 无法完成行为目标，完成收尾后返回原因。 |

例如，查询附近目标返回空列表通常是查询成功；移动 act 因路径不可达而结束，则是行为失败。设置移动输入的 op 成功，只说明输入已按契约设置，不说明角色已到达目的地。op 成功不等于 act 成功。

每个 act／op 的行为契约应明确：

- **执行前提**：什么条件下可以开始，不满足时如何返回。
- **成功边界**：承诺完成什么，依据什么确认。
- **失败边界**：哪些情况导致无法完成，返回哪些原因。
- **持续效果**：调用结束后是否仍留下控制输入、后台操作等效果。
- **停止与收尾路径**：如何终止持续效果，何时可以确认停止。

op 报告基础操作结果，act 解释其对当前行为的影响，behavior 决定如何继续策略。act 可以在自身职责范围内重试或调整；仍无法完成时再向 behavior 返回失败。超出 behavior 恢复规则的情况交由 agent 决策，不要求每个 op 都自带备用策略。

上述要求是行为契约，方法与字段的设计见[接口文档](CONTRACTS.md)；瞬时查询不必套用持续动作的完整生命周期。契约应说明执行如何完成、失败或进入可识别的故障状态，不承诺穷举所有游戏异常，也不要求每个行为都能自行恢复。

## 4. 职责与扩展边界

### 4.1 三条职责边界

1. **behavior 只通过 act 操作角色。** behavior 可以读取观测、计算、判断和保存策略状态；实际动作通过统一的 act 接口执行。
2. **act 不替 behavior 决定长期策略。** act 可以处理完成当前动作所需的局部变化，例如绕路，但不自行决定改去采矿、返家或更换长期目标。
3. **允许组合行为复用，不为组合形式增加额外业务层级。** 多个 behavior 共用的行为组合可以提取为辅助函数或子程序，也不要求 behavior 只能展开成一层 act。act 下方明确设立 operation 基础层，隔离可复用的游戏接入操作。

agent 编写新 behavior 时使用已有 act 编排策略；需要新的完整行为时，可以通过已有 op 编写新 act。新增 act 与编写 behavior 是不同层次的行为开发，新增 op 则属于基础库维护。

### 4.2 行为变化与策略调整

策略内部的变化由 behavior 与执行器处理，例如采集中绕路、护卫时遇敌。策略本身需要改变时，由 agent 重新选择或调整 behavior，例如玩家改变目标，或当前策略不再适用。

模型编写新 behavior 与角色执行已有 behavior 是不同过程。编写期间，角色可以继续执行已有行为或等待，不要求模型在每次环境变化时现场编写程序。

### 4.3 operation 库的维护与扩展权限

operation 作为独立维护的基础库，统一提供名称、类型定义、参数与结果、错误含义、持续效果的停止及清理契约、接入实现和兼容信息。独立维护不强制独立仓库；首版可以作为同一项目中的独立包。

| 层级 | 游戏中的 agent 的扩展方式 |
| --- | --- |
| behavior | 使用已有控制结构、查询和 act 编写策略。 |
| act | 使用已发布的 QueryOp／ControlOp 协调完整行为。 |
| operation | 查询现有能力、提出缺失能力需求；候选实现进入基础库的开发维护流程。 |

允许 AI 帮助开发、修复和升级 op，但游戏运行中的 agent 不得将刚生成的 op 自动加入可用能力。新 op 需经过库自身的检查与发布流程后，才能供行为使用；具体门槛见[发布设计](OPERATIONS-AND-RELEASE.md)。

缺少基础能力时应如实反馈，不通过猜测底层接口或直接访问游戏来绕过 operation 层。新增 QueryOp 与新增 ControlOp 遵循同一维护边界。

基础库的游戏兼容性验证属于库的维护工作，不属于被动 behaviorTree 检测器的职责；构建通过不证明真实游戏兼容性。

### 4.4 接口版本与游戏实现的分离

operation 库维护明确的游戏兼容关系，不要求库版本号与 Minecraft 版本号一一相等。区分以下信息：

| 信息 | 用途 |
| --- | --- |
| op 接口版本 | 说明上层依赖的参数、返回值与行为契约。 |
| 库发布版本 | 记录实现修复、能力增加与兼容调整。 |
| 游戏版本兼容范围 | 说明对应实现支持的 Minecraft 版本或发行版。 |

```text
P2 核心及可替换的 behavior／act
              ↓
    统一的 operation 契约
         ↙             ↘
   Java 版实现       基岩版实现
```

两种实现遵守相同的操作含义、数据类型、结果、错误与停止契约，避免向上层泄露特定版本的内部对象。能力缺失应明确声明，不假装支持。接入实现变化优先在库内适配；无法维持原有契约时显式处理接口版本与兼容关系。

在统一契约成立的前提下，P2 核心无需因游戏版本或规则差异改变。游戏规则导致行为不适用时，由 agent 根据反馈调整 behavior／act，身体不承诺解决策略适配问题。当前游戏版本与可用能力可以通过查询向 agent 提供，P2 不替 agent 作出版本策略判断。

检测结论对应具体接口版本与可用能力集合，更换不兼容的库后不能直接沿用旧结论；精确binding及产物摘要见[发布设计](OPERATIONS-AND-RELEASE.md)。

D4 将环境 binding、产物依赖与运行实例分开：binding 固定 body/IR、契约、provider、驱动及影响执行的配置，不包含 act 集合；每个 artifact 锁定实际使用的确切 act 产物与依赖闭包；run 固定 artifactId、binding 和参数。新增 act 不改变环境或已有运行，采用新依赖的候选才重新检查；provider/环境变更仍需人类管理、停止清理和重新核验。

revision 表示源码版本，artifactId 表示确切可执行内容；同源码在不同依赖或 binding 下可以生成不同产物。启用与 switch 指定 artifactId，运行时不追随默认版本。候选可以面向其他 binding 静态检查并启用，但仅与当前加载环境一致且实际能力满足时才能启动。退休依赖阻止新 run，不替换已有 run 的后续节点。摘要输入、规范化与变更范围见[发布设计 §3](OPERATIONS-AND-RELEASE.md#3-不可变-binding)，启用状态见[生命周期 §5](BEHAVIOR-LIFECYCLE.md#5-artifact-与检查凭据)。

### 4.5 仓库组织与包管理（暂定，待发布验证）

**首版暂采用一个 Git 仓库中的多个独立包，包管理器暂选 pnpm；后续可选择将 operation 实现拆为独立仓库，不要求最终一定拆仓。** 这一选择以 P2 与 operation 上层实现继续采用 TypeScript／JavaScript 为前提，尚未确定最终交付形式。

首版将 P2 核心、operation 契约与 operation 实现放在主项目仓库中，方便接口、实现与检查共同调整。各包拥有独立的公开入口、依赖声明和版本，跨包使用公开接口，不直接引用其他包的内部源码。以下仅示意包边界，不确定具体名称与目录：

```text
主仓库
└─ packages
   ├─ p2-core
   ├─ operation-contract
   └─ operation-minecraft-java
```

暂用 pnpm workspace 管理同仓库包依赖，通过锁文件固定开发与构建所用的依赖组合。工作区包可分别打包或发布，不因源码位于同一仓库就必须作为一个包交付。包管理器负责软件依赖；operation 能力声明、游戏兼容检查和运行时实现选择仍由 P2 的机制负责。

后续出现独立维护者、独立发布节奏或其他项目复用需求时，可以拆分 operation 实现仓库。契约包暂建议继续由 P2 项目维护，实现包依赖该契约。拆仓时保留包名与公开契约，将主项目的工作区依赖改为已发布版本，并迁移相应构建、检查与发布流程；正常消费已发布包不要求使用 Git submodule。

首版可考虑将 operation 打成版本化包并随完整发行包交付，之后再决定是否使用包注册平台。单个包归档不等于包含全部依赖的离线发行包；若接入涉及其他语言组件，应使用对应构建工具，不要求 pnpm 替代它们。

**以上工具与交付选型仍暂定，未通过实际发布验证。** 已核验 DSH bundle 入口、兼容声明及宿主依赖解析；首版 bridge 使用宿主接口并管理 body 子进程，body 自行携带依赖闭包。详见[DSH 接入](DSH-INTEGRATION.md)与[发布设计](OPERATIONS-AND-RELEASE.md)。首版进程树回收、完整发行和游戏驱动交付仍需原型验证；独立 launcher 属于后续 WS 阶段。当前仅有设计文档，不代表运行工程已实现。

## 5. behaviorTree 的定义与构建

### 5.1 表达方式的架构决定

**采用方案二：通过带类型的代码接口构建行为树（behaviorTree），再由统一执行器运行。behavior 不采用 XML 定义，也不采用直接执行任意异步程序的形式。**

这一决定明确了 behavior 的表达方式；控制结构、调度与切换的基本机制见后文，数据IR和构建接口见[接口文档](CONTRACTS.md)。

### 5.2 构建与执行分离

- 作者通过 `sequence`、`repeat` 等构建函数及 act 包装函数组合行为；构建产物契约已在接口文档描述，示例中的游戏专用函数名称仍非最终SDK。
- 构建函数产生行为节点，不直接执行游戏动作。例如，调用 `goTo(...)` 只创建移动节点，不会立即移动角色。
- 构建阶段可以利用宿主语言的函数、循环与计算能力，生成数据、复用子树和组织节点。
- 构建完成后，执行器负责推进 behaviorTree。执行期间的条件判断、循环和环境响应，通过树中定义的行为与查询表达。

产物是可序列化的节点图及有界表达式，不含需要body执行的作者任意闭包。自定义act代码通过隔离runner使用受控op能力，构建与运行隔离的要求见[扩展生命周期](BEHAVIOR-LIFECYCLE.md)。

省去 XML 的解析与映射，不代表省去 behaviorTree 执行器。

### 5.3 选择理由与能力范围

代码接口便于使用类型检查、编辑器提示、函数复用与参数化计算，降低复杂 behavior 的编写和维护成本。

在控制结构、查询与 act 相同的前提下，运行时能力并不会因为改用代码而自动增加。新的完整行为可以通过已有 op 扩展 act，真正缺失的游戏基础能力则需要扩展 operation 库；构建阶段的自由计算也不等于允许执行阶段运行任意程序。

### 5.4 局部状态与数据流

behavior 的数据流采用显式赋值、声明输出和独立局部作用域：assign 节点用受限表达式更新 local，query/act 将成功结果写入绑定的输出槽，子树通过明确输入与成功输出复用行为组合。所有写入由执行器落实，act 不直接修改 behavior locals。

behavior 参数在实例内只读，behavior locals 跨循环与树内分支切换保留；子树每次进入创建独立局部帧，取消后重入重新初始化。新调用的输出槽先标记为待产出，不能沿用上一轮结果；act 的成功输出必须等业务成功及收尾确认后发布。重复、迟到结果不重复写入。

策略计数、当前观测与历史执行证据有不同含义。当前观测经计算、赋值或子树传递仍保留来源、时效及世界作用域，赋值不刷新观测时间；累计成功动作次数也不能直接作为当前物品数量。第一版允许 locals 保存查询快照，但这一存储选择保留后续评估空间；locals 不随游戏自动同步，不构成 P2 世界副本。详细约定见[数据契约](CONTRACTS.md#31-数据归属与寿命)和[运行规则](RUNTIME.md#43-局部状态与结果写入)。

D2 采用执行器内部按顺序写入、后续节点同轮立即可读；启动新 act 和提交终态前通过[统一检查点](RUNTIME.md#31-新动作与终态的统一检查点)。相关 local 更新使旧条件判定失效；未知或过期的必要条件不能放行新动作。单次赋值原子更新，整个 tick 不回滚；轮末只汇总状态和事件。

## 6. behavior 运行契约与完成判定

**合法 behavior 应提供完整的运行声明，执行器依据统一契约执行、判定和报告。** behavior 定义不包含 agent 连接或模型会话调用逻辑。

### 6.1 必需声明与可选扩展

| 内容 | 要求 | 职责 |
| --- | --- | --- |
| 标识、参数定义、行为树 | 必须 | 描述如何使用和执行 behavior。 |
| 运行类型 | 必须 | 区分有限目标与持续行为。 |
| 完成条件 | 有限目标必须 | 声明怎样确认目标达成。 |
| 局部状态 | 按需 | 保存本次运行需要记住的信息。 |
| 恢复与受阻处理规则 | 可选 | 默认失败传播、零行为重试；显式recover才进行有限重试、备用流程或blocked。 |
| 进度、阶段等补充信息 | 可选 | 未声明时仍提供基本运行状态。 |
| 状态维护与事件发送 | 执行器统一提供 | behavior 不自行标记成功或实现重复的上报逻辑。 |

取消也遵循统一机制：behaviorTree 使用支持中断的控制结构与 act，由执行器管理停止过程，不要求每个 behavior 重新实现取消函数。

### 6.2 完成判定

- **有限目标 behavior**：达到声明的完成条件并完成收尾后结束，例如背包中指定资源数量达到目标值。
- **持续行为 behavior**：正常情况下持续运行，例如护卫、跟随；一次动作完成不代表整个 behavior 成功，被替换时记录取消。

完成条件读取观测与本次运行状态，不执行游戏动作。优先通过已有、可组合的判断接口表达，不要求每次检查都调用模型。

同轮竞争按[运行时完成裁决](RUNTIME.md#42-完成判定)处理：有效取消优先于尚未提交的成功/失败；未处理的程序或契约错误不能被目标成立掩盖；有效目标证据可以优先于普通环境失败，但仍须收尾及最终新鲜确认。控制权不确定时保留结束意图并进入故障，禁止提交终态或启动新控制者；已经提交的终态不因晚到消息改变。

目标含义必须由 behavior 定义及参数明确。例如“背包总量达到 32”“本次额外获得 32”“累计向箱子存入 32”是不同条件，执行器不自行推断玩家意图。

行为树走完不等于目标达成；predicate 目标条件成立后，执行器停止后续动作，收尾并完成最终确认后报告成功。不能机械确认结果时，显式声明 externalConfirmation，仅在树根成功且 act/broker 收尾完成后进入 blocked/CONFIRMATION_REQUIRED；根失败、取消及持续行为不能进入完成验收。

D3 将外部验收绑定到 bodyEpoch、runId、confirmationId，每个运行最多一条请求，固定目标与执行摘要。有效确认使原实例 succeeded，有效否定使其 failed/EXTERNAL_GOAL_REJECTED；无法判断时继续等待，补做工作则新建实例。非法确认命令只被拒绝，不等于目标被否定。来源由可信 bridge 通道确定，区分 agent 判断和玩家确认，不伪装成游戏自动验证。请求不自动超时，但 bridge 存活期限与 owner 授权仍生效；重复决定不重复生效，取消优先，终态不可改写，重启不复活旧请求。具体见[外部验收契约](CONTRACTS.md#71-外部完成验收契约)和[运行规则](RUNTIME.md#44-外部完成验收)。

## 7. 执行器、调度与切换

**behavior 描述策略，执行器统一落实调度与切换，act 实现动作的启动、推进和停止。** 执行器集中管理运行机制，不承担采矿、返家等具体游戏策略。

### 7.1 职责划分

| 内容 | 定义或发起方 | 落实方 |
| --- | --- | --- |
| 行为顺序、条件与优先级 | behaviorTree | 执行器 |
| 节点推进与重新评估的规则 | 执行器的统一语义 | 执行器 |
| 更换 behavior 的请求 | agent 等上层调度者 | 执行器 |
| 动作停止的具体操作 | act 的实现 | 执行器请求，act 完成 |
| 执行位置、节点状态与切换状态 | 执行器 | 保存在对应 behavior 实例的运行状态中 |

behavior 作者不自行实现定时器、取消流程或并发管理。

### 7.2 控制结构的基本语义

以下名称为暂定接口；控制结构的结果传播规则采用当前暂定方案：

| 控制结构 | 运行规则 |
| --- | --- |
| `sequence` | 记住执行位置；当前子节点成功后推进下一个，失败则向上传播；全部成功才成功。 |
| `if` | 进入时选择分支，继续执行已选中的分支，并返回其成功或失败结果；持续重新判断由反应式结构承担。 |
| `reactivePriority` | 周期性按优先级检查条件，选择第一个满足条件的分支，必要时停止当前分支再切换；选中分支的成功或失败作为自身结果。 |
| `repeat` | 子树成功后，在后续调度中开始下一轮；失败默认向上传播，不默认无限重试，也不在一次更新中无限循环。 |
| `assign` | 完整求值并校验受限表达式后写入目标 local；失败保留原值，不执行游戏动作。 |
| 子树引用 | 复用定义，每次进入捕获只读输入并初始化独立 locals，成功后发布声明输出；取消后重入不复用旧帧。 |

普通流程推进与持续重新决策必须明确区分，不将所有节点都解释为“每次更新从头运行”。节点技术状态见第 7.7 节，不等同于业务目标完成或向 agent 汇报成功；完整规则及wait/recover结构见[运行时](RUNTIME.md)。

对于 `reactivePriority`，条件不成立表示分支当前不适用，可以检查下一分支；选中分支执行失败则默认向上传播，不自动吞掉错误并改跑其他分支。没有条件满足时返回带原因的失败；需要长期等待的策略应显式提供等待或空闲分支。重试、备用方案与其他恢复行为由 behavior 声明。

条件查询出错或尚未返回不等同于条件为假；未知结果的等待、失败与分支推进采用第 7.11 节的暂定规则。

### 7.3 统一节拍调度

首版使用固定调度周期，可暂以 **100ms 一次**作为起点，之后根据实测调整。这不是端到端反应时间保证。

每次调度处理最新观测、动作结果和切换请求，评估需要持续检查的条件，推进当前节点，并发出必要的动作启动或停止请求。

每次推进只做有限工作并尽快返回，不等待长动作完整结束。behaviorTree 的调度频率不必等于底层动作的更新频率：移动等 act 及其底层实现自行处理动作细节，执行器不反复启动同一个正在执行的动作。

### 7.4 中断与动作停止

执行器统一发起中断，act 必须实现实际停止能力。动作接口包含启动、推进或查询状态、请求停止、确认停止；runner与broker的契约见[接口文档](CONTRACTS.md)。

停止操作可包括停止寻路、解除持续控制、清理自身回调等。behavior 不直接停止其他 act，而是由执行器管理当前控制权。仅将节点标记为取消，不代表角色已经停止动作。

### 7.5 behavior 与分支切换

每个角色只运行一个主动 behavior，这是长期架构约束。切换采用“先停止，再接管”：

```text
接收新 behavior 的切换请求
    ↓
当前 behavior 停止推进新动作
    ↓
请求停止当前正在执行的 act
    ↓
确认旧动作停止
    ↓
启动新 behavior
```

树内分支切换复用同一套中断机制：先停止被替换分支的动作，再启动新分支。

- 旧动作晚到的结果不能继续推进新流程，执行器必须区分结果所属的运行。
- 停止超时不能视为停止成功；旧动作仍可能控制角色时，不启动与其冲突的新动作。暂定故障处理见第 7.9 节。
- 取消不会自动撤销已经发生的世界变化，例如已经放下的方块。

首版优先保证可靠切换，不要求暂停后精确恢复到任意节点。重新选择原 behavior 时，可以根据当前世界状态重新开始或重新规划；精确恢复留待确有需求时设计。

树推进、调度与切换统一组织在执行器内部，对外提供请求切换、停止、读取状态等少量操作。accepted与实际started/terminal区分，commandId用于查询最终结果，详见[接口文档](CONTRACTS.md)。

### 7.6 长期约束：单线程调度与单动作控制权

**behaviorTree 采用单线程、非阻塞的调度方式，不提供通用并行节点；同一时刻至多一个 act 持有角色控制权。** 这是长期设计边界，不作为以后增加并行子树的过渡方案。

执行器轮流处理条件评估、动作进度、结果和切换请求，每次处理有限工作后返回，组织方式类似事件循环。单线程本身不能防止多个异步动作争抢角色，因此执行器还必须显式管理控制权，拒绝同时启动相互独立的多个控制 act。

当前 act 运行期间，执行器仍能重新评估其祖先节点中的反应式条件，并检查更高优先级的分支。轮流检查多个分支的条件，不等于推进多个分支的动作；选中替代分支后，仍须先停止当前 act，再移交控制权。

这一约束不要求模型推理、只读查询或底层非阻塞操作全部串行等待。一个 act 内仍可协调多个 op 的持续效果，具体边界见第 3.4 节；behaviorTree 不将这些协调拆成争抢控制权的并行 act。

以采集时遭遇威胁为例：behavior 可以通过反应式优先选择，将威胁处理放在采集分支之前。执行器发现对应条件成立后，停止采集 act，确认停止，再推进威胁处理分支。威胁解除后，可根据当前事实重新进入采集分支，不承诺从被打断的动作内部精确续接。

这一过程仍属于同一个 behavior，不因分支切换而将整个 behavior 标记为取消。选择战斗、躲避或其他处理方式由 behavior 定义；执行器只落实条件评估与切换。公共应对逻辑可以复用为子树，不另开并行 behavior。若当前 behavior 未定义适用行为，执行器不会自行发明应对策略。

### 7.7 树节点的统一状态（暂定）

控制节点、查询节点与 act 节点统一采用以下运行状态，不替代 behavior 的业务状态，也不要求底层 op 采用相同状态机。

| 状态 | 含义 |
| --- | --- |
| 未开始 | 本次运行尚未进入节点。 |
| 运行中 | 已进入，仍需后续调度。 |
| 停止中 | 已收到取消请求，正在停止子节点或清理自身操作。 |
| 成功 | 本次执行正常完成，相关动作已经收尾。 |
| 失败 | 本次执行无法正常完成，相关动作已经收尾。 |
| 已取消 | 本次执行被主动终止，停止和清理已确认完成。 |

```text
未开始 → 运行中 → 成功 / 失败
             ↓
           停止中 → 已取消
```

立即完成的节点可以在同一次调度内经过运行中到达终态。成功、失败、已取消均表示已经完成收尾；发现动作目标已经达成或无法达成，不代表可以在清理前报告终态并交接控制权。正常结束的收尾尚未完成时，节点仍未进入成功或失败终态。

终态不直接变回运行中。循环或重新进入分支时，执行器开始下一次运行，以nodeRunId区分新旧结果；与body/连接/act代际一起拒绝晚到结果，详见[运行时](RUNTIME.md)。

“受阻”保留为 behavior 业务状态，暂不增加为通用节点状态。节点通过失败原因、等待行为及 behavior 恢复规则表达当前情况。

### 7.8 取消传播与交接（暂定）

取消是控制信号，不按普通失败传播。控制节点收到取消请求后，不再启动新动作，并将停止请求传给当前活动子节点；子节点确认停止后，父节点才能结束取消过程。

- 更换整个 behavior 时，沿当前活动路径停止，最终旧 behavior 进入已取消状态。
- 同一个 behavior 内切换分支时，旧分支进入已取消状态，优先选择节点仍运行，随后进入新分支；子节点取消不自动意味着父节点取消。
- 停止请求必须幂等：重复请求不重复启动清理过程，也不重置停止期限。
- 一旦开始停止，就完成本次停止；即使条件恢复，也不将旧 act 从停止中拉回运行中。
- 停止期间可以更新后续分支选择，但新分支必须等控制权释放后才能启动，并在启动前重新检查条件。

### 7.9 停止及收尾超时的故障处理（暂定）

**超时表示未能按时确认停止或完成收尾，不证明旧动作已经停止，也不证明它一定还在执行。执行器必须保留旧控制权归属并暂停动作推进，不能将超时当作普通失败后继续启动动作。**

```text
请求停止或进入结束收尾
           ↓
在期限内确认完成？
    ├─ 是 → 结束旧运行，允许后续动作
    └─ 否 → 标记执行器故障，暂停动作推进
                     ↓
             继续收集结果并提供反馈
```

这套处理覆盖取消、正常成功和正常失败的所有收尾路径。即使行为已决定结束，只要仍无法确认持续控制释放，就不能交接给下一个 act。

故障期间不启动新控制 act，也不启动用于救场的另一个 behavior。保留旧 act 的归属信息，允许其完成停止与清理；当前事实查询、状态查询及执行反馈仍可用，新的策略请求不能绕过交接规则。

故障属于执行器状态，不为每种树节点增加一种故障状态。取消中的 act 可以保持停止中，并记录已经超时。该故障不能伪装为普通 behavior 受阻：材料不足时可以安全更换 behavior，控制权未释放时不能。

解除故障须有明确依据，暂定允许两条路径：

1. 旧 act 的停止或收尾确认晚到，执行器确认清理完成、控制权释放，再重新评估当前请求并继续调度。
2. 底层确实提供可靠的控制重置能力，且确认旧控制与未完成操作已失效，执行器才允许重新接管。是否支持这一能力取决于 operation 库，不能仅清空执行器引用就宣称停止成功。

始终无法确认时保持故障状态，交由 agent 或人工处理。agent 可以取消后续目标、调整计划或请求受支持的恢复流程，不能通过更换 behavior 消除故障。

停止与收尾采用第 7.10 节的总期限与有限重试规则；重复请求不延长总期限，超时不强行交接，恢复必须得到明确确认。

### 7.10 停止与收尾的期限及重试规则（暂定）

**停止请求本身不反复重发；明确可重试的收尾操作最多自动重试一次，即总共尝试两次；所有尝试共用一个总期限。**

| 情况 | 处理规则 |
| --- | --- |
| act 正在停止，尚未返回结果 | 继续推进、等待，不算重试，也不重新启动停止流程。 |
| 某个收尾 op 明确失败，且允许安全重试 | 最多自动重试一次，使用总期限内的剩余时间。 |
| 停止或收尾已超过总期限 | 进入执行器故障，不开启新一轮自动重试。 |

重试针对失败的收尾操作，不重新执行整个 act，也不将已完成的清理全部重做。例如停止移动已成功、取消未结束操作发生可重试错误时，只重试后者。执行器统一管理次数和期限，act 按自身收尾流程报告结果；执行器、act 与 op 不得各自独立叠加重试预算。

自动重试必须同时满足以下条件：

- op 契约明确允许安全重复调用，不会产生重复副作用。
- 返回结果明确表明本次尝试已结束，且错误属于可重试类型。
- 总期限尚未耗尽。

不支持操作、参数错误等情况不自动重试；不能保证重复调用安全的操作也不自动重试。请求超时且无法确定前一次是否仍在执行时，可以按契约查询进度或继续等待，不能直接启动第二个同类操作。底层若支持对同一请求安全重发，须由 operation 库明确实现这一保证，并遵守统一预算。

最多一次重试是当前控制复杂度的暂定选择，给偶发错误一次恢复机会，不作为已经实测得出的最佳次数。

总期限从执行器首次请求停止，或 act 开始正常结束收尾时计起，覆盖取消、正常成功和正常失败的结束路径。每次重试及重复请求均不重新计时。

```text
开始停止／收尾
      ↓
在总期限内推进清理
    ├─ 成功 → 结束并释放控制权
    ├─ 可重试失败且尚有重试预算 → 重试一次，使用剩余时间
    ├─ 无法恢复或重试预算耗尽的清理失败 → 进入故障
    └─ 总期限耗尽 → 进入故障
```

期限是最长容忍时间；已经明确无法完成清理时，不必空等到期限耗尽。由执行器提供统一默认期限，允许受控配置为特定 act 覆盖；agent 编写的 behavior 不能任意延长期限，也不能通过重复请求重置计时。具体数值留待 operation 实现后，根据停止与收尾耗时测量确定。

进入故障后，晚到的停止或收尾确认仍可按第 7.9 节解除故障，但不再自动开启新一轮清理尝试。可靠的底层重置属于单独恢复流程，不隐藏为普通自动重试。

上述预算仅约束停止与收尾。路径不可达后换目标、采集失败后重新尝试等行为重试，仍属于 act／behavior 的策略规则，不共用这里的次数。

### 7.11 QueryOp 的异步等待、结果有效性与失败规则（暂定）

**查询可以异步等待，但不能阻塞调度；结果只代表一次观测，查询失败不能当作条件不成立。QueryOp 一次调用只发起一次请求，失败或超时即返回原因，不自动重试。**

查询节点进入后发起请求，等待期间保持运行中并让出调度。执行器继续处理取消、其他条件检查及当前 act 的推进，不在一次更新中等待查询结束。同一次节点运行只保留一个未完成请求；后续调度检查已有请求，不重新发起查询。

| 查询状态 | 节点处理 |
| --- | --- |
| 尚未发起 | 发起一次查询。 |
| 等待结果 | 保持运行中，让出调度。 |
| 返回可接受的结果 | 保存结果，节点成功。 |
| 明确失败或等待超时 | 节点失败，返回原因。 |
| 所属分支被取消 | 停止使用该请求，忽略晚到结果。 |

纯读取请求的取消不一定要求底层立即停止计算。只要晚到结果不能推进旧节点或写入新运行，P2 就可以结束该查询节点的运行；底层支持取消时，同时释放对应资源。查询没有持续控制效果，不需要像控制 act 一样等待释放角色控制权。

结果有效性分为两类：

- **归属有效性**：结果属于当前请求、当前节点运行及当前游戏连接。旧分支、旧 behavior 或连接重建前的请求不能将结果写入当前运行；失败、超时或取消后的晚到结果也不能重新推进已结束的查询。
- **时效有效性**：结果的观测时点满足使用方允许的数据年龄。摘要与动作前置判断可以有不同要求，不为所有 QueryOp 统一规定一个固定有效期。

结果返回时间不一定等于观测时间。operation 应说明数据的观测时点；无法精确提供时使用保守的时间范围，不能按刚返回的时间将旧数据视为新鲜数据。超过使用方允许的时效或归属无效的结果不予接受，不能用于条件判断或据此启动新动作。

需要最新事实时须重新查询，但不将结果失效隐式转化为 QueryOp 内部自动重试。时效合格也不保证世界尚未变化；act／ControlOp 仍须处理真实执行时的失败。例如查询时材料充足，不等于之后一定合成成功。

| 情况 | 结果含义 |
| --- | --- |
| 在约定范围内成功查询，没有匹配目标 | 查询成功，结果为空。 |
| 部分数据不可见或不可用 | 按契约返回明确范围的部分结果，或报告数据不足。 |
| 接口不可用、连接中断、请求异常 | 查询失败，返回原因。 |
| 超过等待期限 | 查询失败，原因是超时。 |
| 结果已过时或不属于当前运行 | 不接受该结果，不能用于条件判断。 |

每个 QueryOp 明确是否允许部分结果，调用方必须知道结果覆盖的范围。“没有查到”与“无法查询”不能都变成条件为假，也不将未知数据伪装为不存在。具体可见范围与游戏数据内容留待游戏相关设计。

反应式条件查询的默认处理规则如下：

- 尚未完成的条件为未知，不能当作假并跳过它去选中新分支。
- 已有 act 可以继续推进；等待查询本身不立即取消当前动作。
- 不依据尚未完成或已经过时的条件启动新的分支动作。
- 查询最终失败时按节点失败传播与 behavior 恢复规则处理；若需退出当前分支，仍须先停止当前 act，再结束分支。
- 如果策略要求无法确认环境就立即停止，由 behavior 显式声明，执行器不统一替所有策略作出这一决定。

例如采集过程中重新查询威胁，等待期间可以继续当前采集 act，确认威胁存在后再切换；查询一直无法完成时，在期限到达后进入明确的失败处理，不无限沿用此前没有威胁的判断。

QueryOp 不沿用停止与收尾操作的自动重试预算。确实需要再次尝试时，由 behavior／act 显式安排，并受次数或总期限约束。成功查询后为获取最新事实再次查询属于正常刷新；失败后再次尝试属于重试，不能用周期刷新掩盖失败后的隐式重试。

P2 只临时保存正在执行的查询及必要结果，不保存历史观测、不计算环境变化，也不因此引入世界状态副本。查询期限、数据年龄的首版配置起点及跨进程时钟规则见[运行时](RUNTIME.md)，需游戏接入后实测调整。

## 8. 运行状态、恢复与事件反馈

### 8.1 运行状态与局部恢复

| 状态 | 含义 |
| --- | --- |
| 运行中 | 正在推进目标。 |
| 受阻 | 暂时无法推进，但仍可能恢复。 |
| 成功 | 已确认达到完成条件，并完成收尾。 |
| 失败 | 本次运行无法继续完成目标，已经结束。 |
| 取消 | 被主动停止或替换，已经结束。 |

“正在停止”等可作为内部过渡状态，收到请求不等于停止已完成。上述 behavior 状态也不等同于树节点用于流程推进的技术状态。

act 提供目标消失、路径不可达、材料不足等具体结果；behavior 声明局部恢复规则，执行器落实这些规则。可恢复的 act 问题不直接等于整个 behavior 失败。默认不自动重试、不换目标；未声明恢复则失败，显式外部决策路径才blocked。恢复规则须有限次数与总期限，详见[运行时](RUNTIME.md)。

执行器不自行发明新的游戏策略。例如路径不可达后是否挖掘通道，应由 behavior 或 agent 决定。

### 8.2 状态查询与事件通知

执行器同时提供当前状态查询与主动的结构化事件通知。**通知 agent 不等于直接发起一次 LLM 会话。**

本节的事件仅指执行过程与结果的反馈，不要求观测层记录或生成环境变化事件。

```text
执行器更新状态并产生事件
    ↓
agent 侧调度逻辑接收事件
    ↓
决定是否、何时调用模型，以及附带哪些信息
```

| 事件或信息 | 基本处理原则 |
| --- | --- |
| 普通 act 变化、可恢复错误 | 记录，供查询和调试，不逐次唤起模型。 |
| 有意义的进展 | 更新摘要，可合并或限频通知。 |
| behavior 成功或失败 | 上报最终结果，供 agent 安排下一步。 |
| 受阻且需要外部决策 | 上报原因并标明需要决策。 |
| 停止或收尾超时导致执行器故障 | 提供故障及控制权未释放的信息；不得报告旧动作已停止或新 behavior 已接管。 |
| agent 自己发起的取消或替换 | 返回完成确认，通常无需再次唤起模型。 |
| 持续 behavior 正常工作 | 保持运行，不反复通知“仍然正常”。 |

事件应能说明所属 behavior 实例、状态变化、原因、可核实的结果或证据、可用的进度信息、已尝试的恢复动作，以及是否需要 agent 决策。字段、去重、合并、session投递与日志保留见[反馈与恢复](FEEDBACK-AND-RECOVERY.md)。

agent 侧负责事件排队、合并和模型调用调度。面向玩家的语言汇报主要由 agent 根据事实与对话情境组织；执行器不自行生成聊天内容。模型思考期间，执行器仍按当前 behavior 的规则运行或等待。

### 8.3 运行时反馈与检测分离

真实环境导致的动作失败，由 act 提供具体原因，执行器更新状态并产生结构化事件，agent 侧根据反馈决定调整参数、更换 behavior 或采取其他措施。behavior 已声明的局部恢复规则仍可先由执行器落实。

act 执行失败不直接等于整个 behavior 失败，也不意味着 behaviorTree 在结构或接口上不合法。随着游戏进行，由 agent 根据实际反馈迭代 behavior 的机制属于另一套流程，详见[扩展生命周期](BEHAVIOR-LIFECYCLE.md)，不合并进检测器。

### 8.4 首版日志与资源边界

D6 首版只提供异步 JSONL 调试日志和当前进程内的状态/去重/反馈队列。日志按大小轮换，允许删除旧文件和丢失崩溃尾部；写失败仅报告 loggingUnavailable，缓冲满则丢弃并计数，不阻塞行为或控制清理。accepted 和业务终态不等待落盘，不承诺重启后可查询。

请求、查询、构建、协议输出和 bridge 事件队列均有上限；普通工作满载时拒绝新增，停止、shutdown、heartbeat 和清理保留独立额度。命令 ID 在同 epoch 内不因日志轮换被忘记，内存额度满时拒绝新增普通业务；重启使用新 epoch、空运行，不恢复旧命令或通知。首版不实现持久索引、事务提交、日志修复、持久 pending 队列/ack 或崩溃自动对账。源码、artifact、显式目标及偏好文件仍保留；这些文件不代表旧运行状态已恢复。详见[调试日志](FEEDBACK-AND-RECOVERY.md#31-简单调试日志)与[队列规则](FEEDBACK-AND-RECOVERY.md#33-有界队列与停止优先)。

## 9. 被动的 behaviorTree 检测器

**检测器验证 behaviorTree 与执行器之间的契约，不验证真实游戏环境是否允许动作成功。** 它是被动工具，接收检查请求后返回通过或可定位的错误，不启动 behavior、不修改 behavior，也不触发 agent 会话。

### 9.1 定位与校验范围

检测器只负责语法、类型与构建检查，定位类似 `cargo check` / `cargo build`，不负责行为测试。behavior 的结构与运行契约要求尽量通过类型定义和构建接口表达，不另行分析策略意图。

通过检测意味着 behaviorTree 在对应版本的执行器、act 接口及已声明的 operation 能力下合法，可以被接受并执行，不意味着动作一定成功。检测器不依赖真实 Minecraft 环境，也不模拟游戏环境或接口。本章后续小节说明完整职责。

### 9.2 检查流程与契约依赖

| 检查 | 要回答的问题 |
| --- | --- |
| 语法检查 | 源码能否被语言工具正确解析？ |
| 类型检查 | 参数、引用、构建函数与返回值是否符合实际接口契约？ |
| 构建检查 | 定义能否成功加载、完成构建，并产生执行器能够接受的 behaviorTree？ |

复用现有语言工具进行语法与类型检查。构建检查调用构建入口，但不推进 behaviorTree、不执行 act 的游戏动作，也不调用实际 QueryOp 或 ControlOp，不需要真实观测或模拟输入。构建异常或超时属于检查失败，因为未能成功获得产物。

检测器与执行器应共享实际的类型定义、act 注册信息及其依赖的 operation 契约与可用能力声明，避免双方认可的接口不一致。这些信息由库与运行配置提供，不要求检测器连接游戏以探测能力。读取这些契约信息不等于模拟游戏接口。构建阶段使用参数、查询与状态的声明及引用，实际游戏数据由运行时提供。

### 9.3 契约校验的边界

必需声明、完成条件的接口与类型、受支持的行为节点及可选字段要求，应纳入类型定义与构建接口，由检测器完成语法、类型和构建检查。它不判断完成条件是否正确表达玩家意图，也不保证策略合理或目标可达。

### 9.4 通过检测的保证与限制

在对应版本的执行器、act 接口及已声明的 operation 能力下，behaviorTree 合法，每个 act 的调用可以被执行器识别、接受并交给对应实现处理。这里的“能够执行”不等于“执行成功”，也不证明自定义 act 或底层 op 的实现没有运行时缺陷。

检测不保证目标可达、材料充足、任务能够完成、行为符合预期或策略高效，也不构成对任意构建代码安全性的证明。

| 情况 | 处理阶段 |
| --- | --- |
| 引用了不存在的 act | 检测阶段拒绝。 |
| 引用了不存在或当前能力声明不支持的 QueryOp／ControlOp | 契约依赖检查阶段拒绝，不通过真实游戏探测。 |
| `goto` 的目标类型不符合接口要求 | 检测阶段拒绝。 |
| 定义无法完成构建 | 检测阶段拒绝。 |
| `goto` 目标合法，但在真实世界中不可达 | 运行时反馈失败。 |
| 合成调用与配方参数合法，但实际材料不足 | 运行时反馈失败。 |
| 各个动作都可执行，但整体行为不符合玩家预期 | 交由独立的游戏内反馈循环处理。 |

## 10. 暂定示例：区域资源采集

以下 TypeScript 风格示例用于说明构建方式。函数名称、类型声明与数据引用写法均为暂定接口，尚无对应实现，不是可直接运行的代码。

```ts
export default defineBehavior({
  id: "collect_resources",
  mode: "continuous", // 本例持续采集，直到被停止、替换或无法继续。

  parameters: {
    area: regionType(),
    resource: resourceType(),
  },

  locals: {
    candidates: slot(resourceCandidatesType()),
    target: slot(blockTargetType()),
    harvestResult: slot(harvestResultType()),
    completedHarvests: slot(nonNegativeIntegerType(), { initial: 0 }),
  },

  build({ params, locals }) {
    return repeat(
      sequence(
        queryResources({
          area: params.area,
          resource: params.resource,
          output: locals.candidates,
        }),
        assign(locals.target, selectResource(locals.candidates)),
        goTo({ target: locals.target, reach: "interaction" }),
        equipFor({ target: locals.target }),
        harvest({ target: locals.target, output: locals.harvestResult }),
        assign(locals.completedHarvests, add(locals.completedHarvests, literal(1))),
      ),
    );
  },
});
```

这个示例表达“在指定区域选择资源目标，移动到可交互位置，装备合适工具并采集，然后重复”。它是持续行为 behavior，不声明有限数量目标；`mode` 的字段名称与取值同样为暂定。

- `parameters` 声明实例内只读参数；`locals` 声明每个 behavior 实例独有的局部状态，`completedHarvests` 显式初始化为 0 并跨 repeat 轮次保留。
- `build` 构建并返回行为树，不执行采集流程，也不是每次更新时重新调用的行动函数。
- `params.area`、`locals.target` 等在构建阶段是数据引用；执行器运行节点时，才读取对应实例中的实际值。
- `queryResources` 构建 QueryOp 查询节点，将合格结果写入 `candidates`；`selectResource` 是作者的受限集合选择表达式构建辅助函数，`assign` 将结果写入 `target`。这些调用不在构建阶段查询游戏，也不把任意回调交给执行器运行。
- `harvestResult` 仅在采集 act 业务成功且收尾完成后获得本次输出；后续 assign 记录一次成功完成的采集。新一轮调用不能用上一轮输出代替本轮结果，失败或取消也不增加成功次数。
- `completedHarvests` 表示成功完成采集的次数，不代表捡到的物品数量；若目标是背包拥有指定数量的资源，须另用当前背包查询定义完成条件。采集过程中已发生的世界变化不会因失败或取消自动回滚。
- `candidates` 及其派生的当前事实保留观测元数据；长动作后如需目标的最新状态，应重新查询，不能因 target 仍保存在 local 中就认为事实一直新鲜。
- `sequence` 负责按顺序推进并记住当前执行位置；`repeat` 描述重复行为，由执行器调度，不是在构建阶段执行 JavaScript 循环。

示例只展示正常采集路径。查询返回空集合后的选择处理、目标失效、材料或工具不足等游戏规则仍待设计，示例不暗示执行器自动选择恢复策略。状态与事件由执行器按统一契约管理，不在示例中自行发送；sequence 表达数据依赖顺序，已成功写入的值对后续节点立即可见，但查询、动作及收尾等待或调度预算可能使执行跨越多个 tick。新动作前仍须重新确认受更新影响的条件，读取新值不等于取得最新游戏事实。

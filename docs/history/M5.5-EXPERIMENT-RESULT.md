# M5.5 实验结论：behavior 表示方式（IR vs 受限 JS）

> 决策 memo。依据：`exp/behavior-ir` 与 `exp/behavior-js` 两轮实机生存实验，**同一世界缺陷、同一套 act/policy**，只差 behavior 的表示方式。
> 原始记录（本机 `.m5-runs/`，未入库）：`M5.5-IR-round1.md`、`M5.5-JS-round1.md`。
> 本文不设死亡次数/用时等硬指标（见[实验计划 §2](EXPERIMENT-BEHAVIOR-SUBSTRATE.md)）。

## 1. 结论

**采用受限 JS 生成器作为 behavior 的表示方式，但不迁就原型的现有能力缺口：先把 IR 的可观测性与审计能力补到 JS 运行时上，再把 behavior 层切到 JS。**

这不是"两者都要"的混合：behavior 仍是单一表示（JS 生成器），保留的是 IR 时代已经验证过的**运行时性质**，而不是 IR 的语法。边界：

| 保留自 IR | 放弃自 IR | 新增于 JS |
| --- | --- | --- |
| 结构化 `currentStep`（类型 + 引用 + 摘要） | 节点/表达式 DSL 本体 | 生成器协程作为计划 |
| 每次 act 启动前的完成条件检查点 | `recover` 的声明式规则 | `try/catch` 局部降级 |
| `status.progress` 落库 | 一棵树的静态可读性 | 直接写算术/循环/条件 |
| 隔离 runner 内的执行 | `externalConfirmation` 的现有实现 | 作者显式 `succeed/fail` |
| 时效自动传播 | — | （需补齐，见 §5） |

理由（有实机证据的只有前三条，后两条是推断，已标注）：

1. **作者循环**：JS 侧 8 个内容文件、0 次 checker 失败；IR 侧 15 个文件、2 次 checker 失败（列表循环越界、工作台参数无法条件省略）。
2. **失败局部化**：同一采集任务，JS 用 `try/catch` 跳过不可达目标；IR 在**首个** `GOTO_NO_PATH` 就整 run 死亡（3 次长跑均如此）。
3. **算术与循环**：JS 可用 `Math.floor(position.y)` 每轮从观测推导坐标与列表 `for`；IR 只能由 agent 手算整数坐标，且列表循环需要 `if + 计数器 + 无害 act` 兜底。
4. （推断）**新原语速度**：`js-tunnel` 62 行、半小时内实战成功；IR 同类需要新节点或重排树。样本只有一次。
5. （推断）**可观测/审计是运行时问题，不是表示问题**：IR 的四项优势都能在 JS 运行时实现，而 IR 的四项代价（DSL 冗长、失败整 run 死、坐标手算、行为分裂）无法通过改运行时消除。

## 3. 证据类别逐项

### 3.1 表达上限

两轮都**没有**因为"表示不了"而停手：IR 用 15 节点表达采集/狩猎/阶梯；JS 用 80–110 行表达同样内容，还能直接写威胁分支。真正的上限没测到——两轮都被基线阻塞在石具之前（见 §4）。

### 3.2 作者循环

- IR：`forage-wood` 151 行、`hunt-food` 150 行；`craft-plan` 与 `craft-table-plan` 因参数无法条件省略而分裂成两个文件；首次运行前改过 2 次 checker 错误。
- JS：3 个 subagent 行为（95/80/101 行）**首次 check 即通过**，1 次实战逻辑修正（`js-dig-stairs` 斜坡格）。
- 观察（人类）：JS 轮前五分钟进度超过 IR 轮 50 分钟；IR 采集原木时明显卡住。**注意**：两轮在同一会话内先后进行，JS 轮带有 IR 轮的经验，进度差不能全部归因于表示方式。

### 3.3 长跑稳定性

两轮都没有达成"≥10 分钟不切换"：IR 死于首个 `GOTO_NO_PATH`；JS 死于夜间怪物（3 次死亡）。这一项**两边都不成立**，不能作为判定依据。

### 3.4 组合复用

act/policy 两轮完全复用（`dig-stair-step` 由 IR 轮 subagent 写、JS 轮直接使用）。JS 侧额外复用方式：把一个 policy 的 `avoid` 入参当"跳过集合"回灌（`js-forage-wood`），说明策略参数化比 IR 的分支树更灵活。

### 3.5 可观测性（IR 明显更强）

- IR：`status.activeNode` 为节点 id（如 `dig`、`approach`），`status.progress` 落库。
- JS：`activeNode` 为行内标签（`act:goto`/`query:position`），`ctx.progress` **不进入 status**（原型限制），排障只能看 `activeAct` 与 `lastRun.error`。
- JS 的 finite 行为在 `activeRun.completion` 显示 `externalConfirmation`，但 `pendingConfirmation` 永远为 null——**会让人误判有验收在等待**。

### 3.6 安全性

- IR：behavior 是数据，由可信执行器运行，天然没有作者代码执行面。
- JS：behavior 代码在 body 进程内 `node:vm` 执行，**不是**隔离 runner（见[../BEHAVIOR.md §7](../BEHAVIOR.md)），`import/require/eval/Function` 靠静态正则拦截，`vm` 不是完整边界。要作为主线必须先搬进隔离 runner。

### 3.7 维护局部性

JS 侧改动是"改一个函数"；IR 侧改动常要重排节点、补 `if` 兜底、同步多个文件（如 `craft-plan`/`craft-table-plan`）。JS 的隐患是作者可以写出 50ms 以上的单步循环（`JS_STEP_TIMEOUT`）或吞掉取消，IR 则没有这类执行面风险。

### 3.8 agent babysitting

- IR：一次 `p2_switch` + 轮询约 10–20s；50 分钟约 40 次 switch。
- JS：同量级，但**每次失败的代价更小**（`try/catch` 自己跳过），agent 需要介入的频次明显低：本轮 JS 的 switch 次数约 20 次，其中多数是推进目标而非修错。

## 4. 两轮共同失败的项目（基线阻塞，不计入 substrate 判定）

| 项 | 现象 | 归属 |
| --- | --- | --- |
| D3 | `dig` 挖脚下方块不结算 → `ACT_TIMEOUT`（30s），身体留在洞里 | provider op（待确认，未修） |
| D4b | `goto`/`move-to` 进不去 1 格深台阶/竖井；JS 报 `STEP_LIMIT`、IR 假成功后卡住 | pathfinder movements 限制 |
| D4c | 高处重生 `y=72`，`maxDropDown=3` 无法下降 → 所有目标 `GOTO_NO_PATH` | 同上 |
| 石具 / 铁 | 地面 32 格内无暴露石头；向下卡 D4b | 基线 + 世界（村庄，圆石在房屋里） |

**结论：本轮不构成对 IR 表达力上限的负面证据**，只构成"共享基线不够用"的证据。

## 5. 转为 JS 主线前必须补齐的运行时能力（核心改动清单）

| # | 改动 | 归属 | 理由 |
| --- | --- | --- | --- |
| 1 | `currentStep` 结构化 `{type, ref, summary}` 并落 `status`；`ctx.progress` 进 `status.progress` | `src/core/js-runtime.ts` + status 映射 | 本轮 JS 排障只能看 `activeAct` |
| 2 | 有限行为的完成检查点显式化：作者声明完成条件，运行时在每次 act 启动前检查；去掉误导性的 `completion:"externalConfirmation"` | `js-checker.ts` + `js-runtime.ts` | 防止"循环退出即成功"与假验收 |
| 3 | behavior 代码搬进隔离 runner（`role=behavior`），不再在 body 进程内 `vm` | `src/runner/*` + `js-runtime.ts` | 架构的隔离承诺 |
| 4 | 时效策略：`ctx.fresh()` 自动传播或默认告警 | `js-runtime.ts` | 本轮 `js-hunt-food` 显式不用 `fresh` |
| 5 | 取消语义加固：`finally` 只能清纯状态、取消不可被 `try/catch` 吞掉 | `js-runtime.ts` | 作者代码面风险 |

以上任一项未完成前，JS 只能作为实验分支，不能替换 `dev` 的 behavior 层。

## 6. 双维护成本

如果按 §1 的方案切换，**不需要**长期双维护：IR 执行器随 `dev` 移除（或降级为"仅用于冻结集验证"），JS 成为唯一 behavior 表示。若短期需要 IR 兜底，成本集中在：两套 checker、两套 runner 角色、两套 status 映射——按现有代码量估算约为 behavior 层代码的 1.8 倍，不建议维持超过一个里程碑。

## 7. 未验证项与归因修正

未验证：

- 石具/铁链路（两轮都被 D4b/D4c 阻塞）；
- "behavior 内威胁处理生效"（`js-forage-safe` 写好但没活到能证明自己）；
- ≥10 分钟长跑（两轮都没成立）；
- JS 在隔离 runner 内的行为（当前是原型）；
- 夜间存活能力的 substrate 差异。

归因修正（来自人类观察，必须在引用本 memo 时一并考虑）：

1. **IR 轮"活过两夜"不能算 IR 的优势**：IR 轮夜间是被村庄**铁傀儡**清掉了攻击角色的僵尸；JS 轮没有这层保护，死了 3 次。夜战对照应在同一保护条件下再做。
2. **JS 轮进度更快，部分来自同一会话内的经验积累**（先做 IR、再做 JS），不能全部归因于表示方式。
3. **楼梯卡住更可能是"楼梯没挖好"**（身体 2 格高，台阶空间/宽度不足），不是 substrate 差异。
4. **寻路问题与 IR/JS 无关**，但 JS 的 `try/catch` 让它更容易在策略内绕过——这是可维护性差异，不是表达力差异。
5. **石头/铁的失败归因于 agent 的 Minecraft 知识不足**（村庄出生点、圆石在房屋结构中、铁需向下挖），建议后续让 DSH 检索 wiki 获取知识，而不是让 P2 系统解决策略知识问题。

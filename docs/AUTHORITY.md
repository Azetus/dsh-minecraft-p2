# P2 决策权约定

> 本文是开发约定与评审依据，不是运行时授权机制。它只回答“谁决定什么”，不回答“怎么实现”；具体机制以 [ARCHITECTURE.md](ARCHITECTURE.md)、[CONTRACTS.md](CONTRACTS.md)、[RUNTIME.md](RUNTIME.md) 为准。现有 giver 的归属审计另文维护，不并入本文。

## 0. 一句话

**Agent 决定做什么、做到什么程度、在什么限制下；P2 决定在已定任务内怎么做。**

P2 只有三类例外可以自己发起动作：**已登记的紧急反应**、**已登记的自理规则**、**Agent 预授权的反应策略**。三者的共同点是：不是 P2 自己生成的新目标，而是 Agent 事先登记/授权的有限反应。

## 1. 关键不对称

Agent 可以把世界事实、自身能力、许可转化为目标，并下达 order/duty。P2 不能。

对 P2 而言：

- **事实不是指令**：天黑、看到矿、羊在旁边，都不构成任务。
- **许可不是任务**：允许攻击被动生物，不等于去猎羊。
- **能力不是职责**：会建房子、会做饭，不等于应该给自己建/做。

P2 可以观察、报告、建议，但不能自行开工。

这个不对称是职责二分的核心：Agent 是第二玩家的战略层，P2 是身体。把三条“不是”也套到 Agent 身上，会把 Agent 限制成被动执行器；不套到 P2 身上，P2 就会从世界现象里自己长出新任务。

## 2. 两条边界

| 归属 | 内容 |
|---|---|
| **Agent** | 目标、区域、资源、风险、权限、完成条件、预算、任务切换 |
| **P2** | 路径、站位、目标实例、工具、交互位置、重试、拾取、施工顺序 |

判断标准：

> **改变承诺 → Agent；不改承诺 → P2。**

这里的“承诺”包括：目标、区域、资源计划与保留材料、风险与权限、完成条件、预算、已声明的世界副作用（搭桥、垫脚、清障、放置等）。

### 2.1 紧急反应、预授权与显式指令

Agent 的思考延迟是常驻树存在的理由。P2 必须在 Agent 尚未反应时先控制角色，并把情况上报；Agent 的新指令到达后，P2 让位，而不是否决 Agent 的决定。

| 情况 | 决定权 | P2 行为 |
|---|---|---|
| Agent 的 order/duty 已覆盖当前危险 | Agent | 执行 order；不因“更安全”而否决 |
| 没有显式命令，触发已登记的自理/紧急规则或预授权反应 | Agent 预先授权 | 按规则行动 + 通知 |
| 新命令与正在进行的反应冲突 | Agent | 停止旧反应，执行新命令；必要时先完成最小生存动作并报告 |
| 即时危险未被任何命令/规则覆盖 | P2 默认反射 | 先避险 + 通知；Agent 后续接管 |
| 无任务、无危险 | — | base activity（默认 wandering，有界）；不自行生成任务 |

三个定义：

- **“已覆盖”只按显式字段判断。** 当前 active order/duty 的目标、区域、`hazards`、combat ROE、完成条件里明确命中的危险，才算覆盖；只覆盖命中的那一类/那一个目标，不扩展到其他目标或未列出的危险。未 active、观测过期、只是“Agent 可能想……”都不算覆盖。
- **“最小生存动作”只做单步避险。** 离开岩浆、脱离坠落、脱离近身攻击、脱离窒息等避免立即死亡/失去行动能力的动作；不做新战术目标、不追击、不扩大范围。做完立即执行新命令并上报。新命令显式授权该危险时，不触发。
- **“通知”不等于送达。** 通知是 P2 在 body 内产生的 notice；bridge 的 wake 可能因 Agent running 排队。P2 不等待送达、不等待确认；Agent 的 order/duty 到达后覆盖反应。通知必须带“P2 已做了什么”和当前状态。

两条边界：

- **任务层服从 Agent，身体层保留最小生存反射。** 新命令覆盖任务，不关闭身体对岩浆、坠落、攻击等即时危险的最小反应；P2 在通知里说明“为生存移动，任务状态未变”。
- **通知与行动并发。** P2 发出通知的同一拍开始按预授权行动，不等待 Agent 确认；等待确认会退回“一停一顿”。

预授权是 Agent 的策略，不是 P2 的目标：`fight`（允许目标/撤退血量/接敌半径/leash）、`selfCare` 都由 Agent 设定、可撤销；P2 不能自行新增规则。没有 `p2_policy.fight` 时，P2 默认避险并上报，不自行战斗、不扩大目标。
自动 fight 永不选择玩家、被动/中立生物；显式 `attack` order 不受此限制：它是 Agent 明确点名，目标选择属于 Agent 决策权，P2 不做保护过滤。显式 attack 期间，常驻树只保留岩浆/深水等致命环境反射，不因敌对、低血、饥饿或卡住而打断；技术失败（目标丢失/无路/看不见/预算）仍然如实上报。

“一直行动”不等于“一直自己找事”：有任务或有预授权反应时不要停；没有任务时执行 base activity——默认 `wandering`，只在 anchor 半径内做局部移动，不采集、不建造、不战斗、不生成新任务。要改变它必须显式 `p2_base_activity`，要完全停住用 `hold`。

行动质量与验收口径见本机 `PLAN.md` 的“终极目标”：连贯性优先，允许犯错和死亡，不以存活率作为硬指标。

## 3. P2 的三条约束

### 3.1 不无限追溯前置

P2 只做任务里已经声明的前置：换工具、清障、走到工作面、拾取自己的掉落。

需要新的资源链（找矿 → 做炉 → 冶炼 → 做工具）→ 交回 Agent。

边界不是“它是不是必要条件”，而是“它是不是这个任务已经声明、受约束的完成方式”。**“这是必要条件”不是扩展职责的理由。**

### 3.2 必须闭环

任务不变时，执行细节由 P2 推进；不能每遇到一个分支就等 Agent 补命令。

- Agent 反复补命令 = **能力缺口**，开发期补 P2，不是把脚本写进 Agent。
- 精确指令是合法的：明确要求、调试、纠正都可以。
- 持续依赖精确指令才能完成普通任务，才是退化。判断标准是“同一目标的 Agent 指令次数”，不是“有没有下过 go/dig”。

### 3.3 受阻不换任务

任务无法继续时，停下/上报，不顺手做另一件事。

树要能表达“保留意图”（hold），不能把所有“没工作”都压成“可以去做别的”。受阻、让出、取消必须有不同含义。

## 4. 双树的分工

| 树 | 放什么 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **常驻树** | 紧急反应、已登记的自理规则、预授权反应 | 抢占当前工作 | 生成新任务、长期目标 |
| **主树** | Agent 已下达/启用的 order/duty | 在任务内选下一项工作 | 从空闲或世界事实生成新任务 |

树的位置是**调度**，不是授权：常驻树的紧急反应可以抢占，但不因为“放在常驻树”就获得目标权；主树的 duty 可以持续工作，但不因为“放在主树”就能自己扩大范围。

空闲是状态，不是任务生成器。默认 base activity（`wandering`）是已登记的有限默认行为，只做 anchor 半径内的局部移动，不采集/建造/战斗；它不是新任务，也不从世界机会里生成目标。要改变 kind 或半径必须显式 `p2_base_activity`，要完全停住用 `hold`。

### 4.1 架构落点

二分应体现在结构上，而不是在运行时加一套权限检查。建议守住五点：

1. **控制面唯一**：order/duty 只能由 Agent 侧创建；body 内部没有创建入口。
2. **树分支类型化**：常驻树只放紧急/自理；主树只放 order/duty/idle；不放“自创任务”的 giver。
3. **giver/driver 边界**：giver 只选目标，driver 只执行；没有任何一层生成新目标。
4. **hold / nowork 分开**：受阻不等于让出；树要能保留意图，不能从 blocked 掉到 idle 或另一个任务。
5. **idle 是状态，不是任务生成器**：base activity 只能做有限的 idle/wandering/escort；游荡不采集、不建造、不战斗，也不从世界事实生成新目标。

这些是结构约束，不是授权机制；后续需要动代码时，只动这五个结构点。

## 5. 已登记的自理规则（v1）

v1 只保留三条，且都是有限动作：

- **self.eat**：饱腹度低 + 背包有可吃食物 + 不在危险中 → 吃一个；不狩猎、不离区。
- **self.retreat**：health 低或敌对近身 → 退到安全格；没有已启用的战斗规则（combat ROE）不反击。
- **self.unstuck**：移动受阻超过阈值 → 局部脱困；不做长距离绕路。

v1 三条默认启用；Agent 可关闭/调整阈值，但不能让 P2 自行新增规则。不做 sleep / build / farm / mine。新增一条自理规则是设计决定，必须按本文评审，不能作为运行时自发行为长出来。

## 6. Agent 侧约定

- 默认下 goal/duty，不下逐格/逐动作脚本。
- 精确指令是例外：明确要求、调试、纠正。
- 显式 `equip` 是 Agent 的手持物决定：成功后，下一次 `dig`/`attack`/`clear` 不自动换工具/武器（中间可有 `go`/`place`/`use` 等非装备动作）；该动作启动后恢复自动。自动选择只服务于未显式指定的动作。
- 需要自动自卫时先设 `p2_policy`；需要指定目标时用显式 `attack` order，并可选择任何实体（P2 不代替 Agent 做目标保护判断）。
- 不在每次失败后重新规划；先让 P2 在任务内重试。
- 要改目标、范围、资源或风险时，明确改 order/duty，而不是让 P2 自己看着办。
- 如果发现自己必须反复补命令才能完成普通任务，记能力缺口，开发期补 P2。

## 7. 三个测试

- **承诺测试**：做完这个决定，目标、区域、资源计划/保留材料、风险/权限、完成条件、预算是否仍然成立？有一项改变 → 交回 Agent。
- **闭环测试**：Agent 沉默 10 分钟，P2 能不能把已经授权的工作做完？不能 → 能力缺口，不是 Agent 脚本的理由。
- **机会测试**：世界出现一个新机会（矿、箱子、动物、夜晚），P2 会不会在没有任务的情况下开始另一件事？会 → P2 越界。

## 8. 评审清单

每个新增 giver/driver/行为，先回答：

1. 它服务哪个 order/duty/已登记规则？
2. 它放在常驻树还是主树？为什么？
3. 它会不会改变任务的目标、区域、资源、风险或完成条件？
4. 它需要的前置是否已在任务内声明？
5. Agent 沉默时，它能否闭环？
6. 世界出现新机会时，它会不会自行开工？
7. 能否用一句话说清“在什么任务下、因为什么条件、做了什么”？
8. 如果它是紧急/预授权行为：Agent 已覆盖当前危险时是否让位？未覆盖时是否先行动并上报？

Agent 侧新增工具/提示词，另答：

9. 它鼓励 goal/duty 级指令，还是逐格脚本？如果是后者，设计错误。

答不出，就不写。

## 9. 示例

| 情况 | 归属 | 判断 |
|---|---|---|
| 饱腹度低，背包有食物 | P2 | self.eat；不狩猎、不离区 |
| Agent 命令“现在进食” | P2 执行 | order；同一能力，不同触发来源 |
| 没食物，附近有羊 | Agent | P2 只报告；不转狩猎 |
| 天黑，附近有床 | Agent | P2 不自生成睡眠任务 |
| 已启用“夜间在床 X 休息” | P2 执行 | duty；条件触发 |
| 165 格外目标 | P2 | 方法：分段移动 |
| 指定区域采原木，选下一棵 | P2 | 方法：区域内选目标 |
| 原木不足，想改采石头建房 | Agent | 改变资源方案 |
| 按蓝图建造，调整施工顺序 | P2 | 方法：不改设计 |
| 蓝图不可用，想抬屋顶/移门 | Agent | 改变设计结果 |
| 工具不在背包，任务允许做 | P2 | 任务内已声明的前置 |
| 工具链需要采矿/冶炼 | Agent | 新资源链，不是“必要条件” |
| 允许攻击被动生物 | Agent | 许可不是任务 |
| 敌对攻击，有 combat ROE | P2 | 紧急反应 + 已启用 ROE；否则撤 |

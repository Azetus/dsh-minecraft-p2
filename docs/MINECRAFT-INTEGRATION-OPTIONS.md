# dsh-minecraft-p2：Minecraft 接入决策、方案比较与验证计划

> 本文说明 Minecraft 接入路线的决策、方案比较、operation 适配要求与验证门槛。已选择独立客户端路线，初版使用 Mineflayer 验证；真实客户端实现与运行方式待后续验证。
>
> 本机安装元数据和官方资料用于判断能力边界，不代表实际联机或模组兼容性已通过验收。
>
> 关联：[主架构](ARCHITECTURE.md)。

## 1. 接入目标与不变边界

接入实现需要让 P2 成为与人类玩家同时存在、分别拥有角色状态和控制权的第二个角色。仅在玩家当前客户端接管玩家自己的按键，不能满足该目标。

所有接入实现均遵守以下边界：

- DSH 中的 agent 选择和编写 behavior／act／policy；P2 body 执行行为，不等待模型完成每个动作决策。
- operation 库对外提供统一的 QueryOp／ControlOp 契约，隔离游戏版本、加载器和接入实现。游戏内部对象、原始网络包及模组特有类不泄漏到 behavior。
- 一个角色同一时刻至多一个 act 持有控制权；游戏驱动可以处理多个底层控制效果，但不能另外运行一套竞争性的 behavior 调度器。
- P2 查询当前事实，不复制完整世界、不保存环境变化历史、不向 agent 自动广播每个游戏事件。执行结果反馈与环境事件追踪分开。
- 协议库或游戏本身为联网、渲染和物理所需的实体／区块缓存属于底层实现。允许查询这些已有数据，但不再将它们复制成 P2 的世界模型。
- operation 只能承诺真实可提供的能力；特定模组交互缺失时明确返回不支持。agent 可以调整策略，不能以生成底层调用代码绕过 operation 库。
- 接入库的兼容性测试独立于被动 behaviorTree 检测器；后者不连接真实游戏，也不模拟游戏接口。

### 1.1 接入路线决策

最初评估两条路线：一是在逻辑服务端通过 mod 创建并维护玩家角色，不运行 P2 客户端；二是让 P2 通过自己的独立客户端连接游戏。后者包括协议客户端与真实客户端；真实客户端可以有窗口或无头运行。“是否无头”是运行方式，不是与协议客户端、真实客户端并列的实现类别。

**正式接入选择独立客户端路线。初版使用 Mineflayer 作为验证实现。** 第 3 章对应首版协议客户端，第 4 章保留后续真实客户端方案；第 5 章的服务器角色方案保留为已评估记录，不再作为当前实施方向。

不采用服务器角色路线的原因是个人项目的精力与维护成本：正常玩家行为由客户端和服务端共同完成，服务端创建实体后还需要补齐相应的行为驱动、玩家生命周期及模组交互；此外还要维护游戏版本、Fabric／NeoForge 差异及兼容验证。该决定不表示服务器角色技术上不可行，也不表示客户端路线无需开发 mod；后续真实客户端仍可能需要查询与控制 mod，但无需由本项目替代整个玩家客户端。

初版固定一个 Mineflayer 支持的原版或可接受原版客户端的环境，验证 P2 的观测、执行、中断切换、失败反馈与 agent 调整行为。具体版本、独立身份和连接方式仍需确定；不默认采用本机整合包，也不以原版实验通过证明模组兼容。多人服务器接入须经所有者允许和控制；具体授权机制后续设计，不把无需服务端安装驱动等同于无需授权。

### 1.2 Mineflayer 与 P2 的依赖边界

**Mineflayer 是首套 operation 实现使用的底层依赖，不是 P2 的公共接口。** P2 core 的执行器与观测层仅依赖统一 operation 契约，behavior／act／policy 同样不能直接调用 Mineflayer 或其插件。

```text
P2 core：执行器、观测层；behavior／act／policy
                   ↓
           统一 operation 契约
                   ↓
           具体 operation 实现
             ├─ Mineflayer 适配 → 协议客户端 → 游戏服务器
             └─ 客户端 mod 适配 → 真实客户端 → 游戏服务器
                                  （有窗口／无头）
```

- 数据：对外返回契约定义的数据，不泄漏 Mineflayer 的 bot、实体对象、类型、事件或插件句柄。观测摘要只处理规范化查询结果。
- 控制：启动、完成、失败、取消、停止确认和旧请求失效由适配层映射到 P2 契约；不把底层方法返回直接视为动作完成或控制权释放。
- 能力：各实现声明实际支持的 operation 集合、版本与限制，缺失能力明确反馈，不要求所有实现功能完全相同。
- 替换：后续主要替换 operation 实现及驱动，保留核心调度和观测机制；behavior／act／policy 是否适用取决于能力与游戏规则，必要时重新检查、调整。此处不承诺运行中热替换。

## 2. 方案 A：独立协议客户端（Mineflayer，首版验证已选）

```text
P2 body → TypeScript operation 实现 → 协议客户端 → Minecraft 服务器
人类客户端 ────────────────────────────────────→ 同一服务器
```

### 2.1 第二角色如何成立

协议客户端建立自己的玩家连接，与人类客户端分别拥有玩家身份。服务器是否要求认证、如何分配独立身份、是否允许加入，须按目标服务器的真实配置处理。单机世界需要提供可供第二连接加入的服务器入口，不能认为存在本地存档就能直接加入。

Mineflayer 提供创建机器人、实体与方块读取、控制、背包、挖掘等接口，因此可以作为 operation 的底层实现来源；它不要求通过图像识别或操作系统键鼠驱动角色。[Mineflayer 项目说明](https://github.com/PrismarineJS/mineflayer)

### 2.2 适用条件与成本

- 可以不运行第二个完整图形客户端；operation 与 body 的上层语言一致时，集成链较短。
- 最适合先验证受支持协议版本、原版或能接受该客户端的服务端环境。
- 模组握手、自定义数据包、动态注册表、物品组件、配方和特殊交互必须逐项核验。能连接不等于能正确操作模组内容。
- 有些高级插件本身持有长期控制状态；必须纳入当前 act 的所有权与停止契约，不能成为绕过执行器的第二控制者。

例如 pathfinder 文档区分了等待下一路径节点停止的 `stop()` 与立即清除目标的 `setGoal(null)`；其寻路生成器还可能在分片预算内占用事件循环。**我们不能将“调用停止函数返回”直接翻译为“旧 act 已清理并释放控制权”。** operation 需要确认自己的持续输入、挂起工作和回调已收敛，并限制计算占用。[Mineflayer-pathfinder 停止与计算接口](https://github.com/PrismarineJS/mineflayer-pathfinder/blob/master/readme.md)

### 2.3 此路线的验证门槛

1. 对 1.21.1 原版基线建立独立角色连接，确认基础身份、背包、移动与查询。
2. 初版以原版兼容环境验证为范围。若另行尝试 NeoForge 目标，须单独验证登录及注册表，不以原版基线通过替代模组测试；不将补齐复杂模组协议作为初版前提。
3. 若实验 26.2，先获得明确的依赖支持证据；当前不把它列为现成支持目标。
4. 在行为切换、网络延迟与未完成挖掘／寻路时，确认旧控制停止后新 act 才接管。
5. 验证实际模组代表性对象；若特殊能力缺失，应形成受限能力声明，而不是宣称全兼容。

## 3. 方案 B：第二个真实客户端 + Fabric／NeoForge 客户端驱动 mod（后续方向）

```text
P2 body → operation 客户端适配器 → P2 专用游戏客户端中的驱动 mod
                                         ↓
人类客户端 ───────────────────────────→ 同一服务器
```

### 3.1 第二角色如何成立

驱动 mod 控制所在客户端的玩家。若安装到人类当前唯一客户端并直接控制当前玩家，得到的是替人操作，不是同时存在的第二玩家。

因此该候选通常需要第二个游戏客户端实例、独立角色身份及独立运行配置，并加入同一个服务器／开放联机的单机世界。P2 实例可以减小显示开销，但“可无界面运行且所有 mod 正常工作”不能预先承诺。

### 3.2 适用条件与成本

- 游戏自己的客户端处理对应版本的协议、物理与已安装模组；有机会减少自己重建模组客户端协议的工作。
- Fabric 与 NeoForge 仍需各自实现驱动、构建与版本适配；不能把同一 JAR 当作两种加载器的通用插件。
- 查询只能报告驱动实际持有的数据。客户端未加载区块、未同步的容器和其他服务端私有信息，必须表达为未知／范围不足，不能填成不存在。
- 第二客户端增加内存、CPU 和启动维护成本；窗口失焦、暂停、退出世界、模组菜单都需要验证。
- 控制必须落在游戏允许的线程和生命周期中，收到外部消息不等于已执行。完成状态不能仅以网络写入成功判定。

Minecraft 单机与 LAN 仍有逻辑服务端，客户端与服务端数据需要按各自职责同步；服务端权威状态不能仅由修改客户端对象来替代。此判断基于 Fabric 与 NeoForge 官方侧别模型。[Fabric 网络与单机服务端](https://docs.fabricmc.net/develop/networking)、[NeoForge 逻辑侧与物理侧](https://docs.neoforged.net/docs/1.21.1/concepts/sides/)

### 3.3 此路线的验证门槛

1. 在人类和 P2 两个实例中确认两个独立角色同时存在；P2 操作不改变人类客户端控制。
2. 各加载器分别构建最小驱动，在目标版本中查询一个当前事实并执行一个可停止控制。
3. 验证客户端失焦、打开界面、世界切换、退出和重连，不能让旧输入继续生效。
4. 对模组交互区分“游戏客户端已正确加载”和“驱动已提供可用 operation”；前者不自动带来后者。
5. 测量双实例资源占用和停止确认延迟，确认可接受后再决定是否推进该路线。

### 3.4 有窗口与无头运行

后续真实客户端先以可见窗口、较低画质验证驱动和目标模组交互，便于观察与调试；再根据实际 CPU、内存、渲染占用评估无头运行。低分辨率、降低画质与适当缩小渲染距离均为候选优化，不预先固定最低值，也不能因后台降速破坏客户端逻辑、网络处理与动作推进。查询和寻路所需的数据范围须同时验证。

HeadlessMc 是可无头运行真实 Minecraft 客户端的命令行启动器，可作为后续运行基础候选，不替代 P2 的 operation 控制驱动。其配套 HMC-Optimizations 说明，仅抑制 LWJGL 调用仍可能保留游戏内部的渲染计算；进一步跳过渲染需要额外优化，且可能影响其他模组。因此无头模式不等于低成本或完整兼容保证，本项目尚未选择或测试该依赖。[HeadlessMc](https://github.com/headlesshq/headlessmc)、[HMC-Optimizations](https://github.com/headlesshq/hmc-optimizations)

## 4. 方案 C：逻辑服务端驱动 + 完整服务器角色（已评估，不采用为当前方向）

以下保留原方案分析与验证门槛，供追溯取舍，不属于当前实施计划。

```text
P2 body → operation 服务端适配器 → 服务端驱动 mod → P2 服务器角色
人类客户端 ────────────────────────────────→ 同一逻辑服务端
```

### 4.1 第二角色如何成立

服务端驱动创建并维护一个可被世界与人类客户端识别的独立角色，并对它执行操作。它可以部署在专用服务器，也可以针对本地集成服务器实现；两种运行方式必须分别验证。

这里的关键工作不是“创建一个名称为 FakePlayer 的对象”，而是补齐目标玩家语义：正常 tick、移动、碰撞、伤害、死亡／重生、背包、容器交互、保存与退出，以及其他 mod 对该角色的识别方式。

NeoForge 1.21.1 分支的通用 `FakePlayer` 是模拟玩家操作的基础实现：源码中的 `tick()`、`die()` 为空，免伤判断直接返回真，容器打开返回空。因此它不能未经改造就作为本项目完整生存 P2 的实现。[NeoForge FakePlayer 源码](https://github.com/neoforged/NeoForge/blob/1.21.1/src/main/java/net/neoforged/neoforge/common/util/FakePlayer.java#L91)

Carpet 的 `EntityPlayerMPFake` 展示了另一类更完整的服务器玩家实现，包含玩家加入、状态加载等流程，可作为研究先例；这不是我们已选择的依赖，也不证明其当前分支与本机 26.2 或 NeoForge 兼容。[Carpet 服务器玩家实现](https://github.com/gnembon/fabric-carpet/blob/master/src/main/java/carpet/patches/EntityPlayerMPFake.java)

### 4.2 适用条件与成本

- 不必增加完整图形客户端；可以在服务器权威状态上处理操作。
- 必须具有部署服务端驱动的条件。若目标是无权修改的远程服务器，此路线不适用。
- 服务端能读取更多数据不代表 agent 应获得全图信息。operation 契约应限制查询范围与可见性，不默认穿透所有未加载区域或私有容器。
- 正常生存行为不能通过直接赠送物品、瞬移或绕过玩家交互来冒充成功；哪些辅助能力允许存在，需要显式声明。
- 某些模组对 fake player、网络玩家和普通实体区别处理；同为 `ServerPlayer` 子类并不证明兼容。
- 驱动线程切换与完成反馈必须明确。NeoForge 官方网络文档说明其 payload 处理线程可配置，并提供将工作提交到主线程的机制；具体调用方式取决于最终驱动版本。[NeoForge payload 处理线程](https://docs.neoforged.net/docs/1.21.1/networking/payload/)

### 4.3 此路线的验证门槛

1. 角色能被人类客户端看见、独立行动、正常受伤死亡并恢复，证明不是工具用的免伤虚拟执行上下文。
2. 验证世界保存／重新加载、玩家列表与角色身份，不生成重复角色。
3. 验证容器、背包及代表性 mod 交互，记录拒绝 fake player 的情况。
4. 分别验证集成服务器和专用服务器，防止服务端代码依赖仅客户端存在的类。
5. 验证 body 关闭后角色停止、旧控制失效，以及人工重新 start 后新 epoch 的连接/对账；明确服务器暂停与世界卸载时的行为。

## 5. 候选比较

下表为基于架构的工程判断，成本是相对预估，不是实测结果。

| 维度 | A：协议客户端 | B：第二客户端 mod | C：服务器角色 mod |
| --- | --- | --- | --- |
| 第二角色来源 | 独立网络玩家连接 | 第二真实客户端的玩家 | 驱动维护的服务器玩家角色 |
| 是否需要第二完整客户端 | 否 | 是 | 否 |
| 是否要求服务端安装 P2 mod | 原版适用场景通常不要求；目标服务器兼容性需验证 | 取决于所需能力，纯客户端控制可作为候选 | 是，或驱动集成服务器逻辑 |
| 本机 26.2 证据 | 当前 Mineflayer 测试表未覆盖 | 有 Fabric 26.2 开发资料，驱动未实现 | 可研究服务端实现，完整角色兼容未验证 |
| 本机 NeoForge 1.21.1 证据 | 原版版本被测试，模组环境未知 | 需 NeoForge 客户端驱动及第二实例 | 有基础 FakePlayer 源码，但完整玩家语义不足 |
| 自定义内容接入 | 可能涉及额外协议与数据适配 | 游戏可加载对应 mod，仍需暴露交互能力 | 可访问服务端实现，但 fake player 兼容须验证 |
| 运行资源 | 相对较低，仍需物理与世界数据 | 相对较高 | 相对较低，工作转入服务器 |
| 主要维护压力 | 协议、数据版本与高级插件控制状态 | 两种加载器／版本、客户端生命周期 | 完整玩家语义、服务端 mod 相互作用 |
| 最重要的先验验证 | 能否正确连接目标模组世界 | 双角色和双实例是否可接受 | 是否真实满足生存玩家语义 |

当前已选择客户端路线：A 用于首版验证，B 用于后续真实客户端与模组环境评估，C 保留为历史方案。具体实验版本与环境仍须确定，不能为了省事静默更换用户现有版本、卸载 mod 或修改存档。

## 6. 所有接入实现必须满足的 operation 接口要求

本节规定适配义务，不预先确定 Minecraft 查询字段或完整 op 清单。

| 义务 | 验证内容 |
| --- | --- |
| 明确身份与连接代际 | 结果绑定当前角色与连接，重连后拒绝旧回调与旧引用。 |
| 有限范围查询 | 报告观测时点／保守时点范围、查询范围、完整／部分结果及失败原因。 |
| 查询不自动重试 | 一次请求失败或超时直接返回；上层策略可以显式决定下一次查询。 |
| 控制所有权 | 仅当前 act 的控制句柄可提交 ControlOp，旧运行不能恢复写入。 |
| 区分接收与完成 | 请求进入队列、调用成功返回、游戏侧完成，不能混为同一结果。 |
| 停止及清理 | 明确持续输入、进行中操作与回调如何失效；确认前不交接控制权。 |
| 断连处理 | 不能把连接关闭直接当作所有持续控制已释放；底层需有可验证的释放路径或进入故障。 |
| 无隐式策略 | 驱动不自行切换采矿／战斗／返家；局部物理或寻路调整只能在声明的 act／op 范围内。 |
| 明确不支持 | 未实现的操作和无法提供的数据返回结构化原因，不猜测接口或伪造成功。 |

“控制已释放”不等于角色位置立即不变：惯性、掉落、击退和已经发生的世界效果可能继续存在。验收应确认旧控制器不再产生新的控制写入、持续输入已按契约处理、未完成操作已结束或可靠失效；不能要求撤销游戏物理。

外部通信只传数据与已注册操作请求，不允许直接远程执行任意游戏端代码。具体传输可由各适配器选择，仍须有请求关联、大小限制、连接身份与版本握手，不能将网络线程上的收包当成游戏线程上的动作完成。

## 7. 最小验证顺序与通过标准

这些验证属于未来接入实现的测试计划，不是本次已执行事项，也不加入 behaviorTree 检测器。

| 阶段 | 最小验证 | 通过标准 |
| --- | --- | --- |
| G0：版本可构建 | 固定游戏、加载器、运行时和依赖版本，构建最小驱动／客户端 | 能清楚报告版本与能力，没有假定跨版本通用。 |
| G1：真正的 P2 | 两个角色同时存在并分别操作 | 人类输入与 P2 控制不争用同一角色。 |
| G2：查询语义 | 成功、空结果、部分可见、超时、断连及晚到响应 | 不将未知当作不存在，不自动重试，不接受旧连接结果。 |
| G3：控制生命周期 | 启动持续动作、取消、清理失败、故障恢复 | 旧 act 未确认结束时新 act 无法接管；无旧回调重新施加控制。 |
| G4：行为切换 | 一个长动作被反应式分支打断，随后恢复选择 | 行为切换不依赖 LLM；记录实际停止和接管耗时。 |
| G5：游戏及 mod 语义 | 生存、背包、交互、代表性模组对象 | 操作遵守所声明游戏语义；缺失能力可观测。 |
| G6：运行与发布 | 暂停／卡顿、世界卸载、重连、body 重启、安装与回退 | 无重复角色或遗留控制；发行物能复现同一依赖组合。 |

首个小实验使用 Mineflayer，在固定的原版兼容环境中优先验证版本支持、独立角色、当前事实查询与停止机制，再推进完整 behavior。后续真实客户端实验先验证双实例角色隔离与代表性模组交互，再评估无头或低画质运行。第 5 章服务器角色门槛仅作历史记录，不进入当前实施顺序。

实际耗时至少记录查询等待、动作收尾、分支切换、游戏线程等待及 body 调度延迟；区分正常运行与暂停／服务器卡顿。100ms 的 body 调度周期不等于游戏端 100ms 响应承诺。具体 timeout 数值在这些数据之后确定。

## 8. 后续决策与资料边界

需要后续明确：

1. 首个 Mineflayer 验证版本及原版兼容测试环境；后续真实客户端的目标版本、加载器与模组包。
2. 本地单机的可连接入口、专用服务器连接配置及服务器所有者授权与控制机制。
3. 独立角色身份配置，以及真实客户端的资源预算、有窗口／无头运行方式和控制驱动选择。
4. 首批必须支持的游戏／模组行为与查询可见性；其余能力可明确不支持。
5. 游戏暂停、世界卸载和 body 丢失时，驱动能提供什么停止证明与恢复路径。
6. 初版单包已包含 bridge、body、内置 provider 与 authoring；真实客户端阶段哪些驱动按游戏版本单独安装、哪些组件需要拆分；不由 npm 替代 Java mod 构建。

本次引用的游戏框架官方资料与项目源码均用于确认能力边界。官方支持声明不等于对本机整合包的测试结果，分支源码也不等于已经发布的固定版本。正式实施时应锁定所选依赖，再将验证结果和限制写入 operation 的兼容声明。

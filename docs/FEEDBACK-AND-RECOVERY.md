# 执行反馈、调试日志与后续恢复边界

> 本文定义首版执行反馈、session 投递、简单调试日志与有界队列。日志服务开发和调试；可靠落盘、持久通知队列及崩溃恢复均为后续功能。
>
> 关联：[主架构](ARCHITECTURE.md)、[运行时](RUNTIME.md)、[DSH 接入](DSH-INTEGRATION.md)。

## 1. 信息归属

| 信息 | 首版保存位置 | 用途与边界 |
| --- | --- | --- |
| 当前查询结果 | body 请求/实例内存；主动读取的摘要可进入 session | 当前决策，不建世界状态库。 |
| 当前节点、act、控制账本 | body 内存 | 当前进程内的停止、清理与故障处理；崩溃后不重建。 |
| 源码、artifact、revision 与 binding | 项目工作区 | 保留内容产物与检查资料，不等于恢复旧 run。 |
| 当前目标、偏好与明确记忆 | 显式项目文件 | 跨 session 保留意图，不恢复旧控制栈。 |
| 命令结果、外部验收请求与决定 | 当前 bodyEpoch 的内存记录 | 去重、status/command.get 查询；重启失效。 |
| 执行事件 | body/bridge 有界内存队列 | 当前进程的界面与模型反馈，无跨崩溃投递保证。 |
| 调试日志 | 有大小上限的 JSONL 文件 | 尽力记录执行线索，允许轮换、丢尾和丢弃诊断，不是运行权威状态。 |
| 玩家交流及结果摘要 | DSH session | 使用宿主原有会话能力，不新增 P2 持久消息队列。 |

不保存全量历史观测，不对环境做 diff，不根据环境变化自动唤醒模型。日志故障、控制故障和事件投递积压分别报告，不能将日志不可用等同于角色控制失效。

## 2. 事件最小结构

事件包含 eventId、bodyEpoch、seq、kind、bindingId，以及适用的 runId、definitionId、revision、artifactId、commandId、状态、reason、进度和 needsDecision；展示时间可保留。revision 定位源码，artifactId 定位确切构建及依赖。事件表达当前进程知道的事实，不证明该事实已经写入文件。

| 事件类 | 首版处理 |
| --- | --- |
| command.accepted/rejected/superseded | 当前 epoch 内可查询，通常不额外唤醒。 |
| run.started、phase.changed | 更新状态并合并进度。 |
| run.blocked/failed/succeeded | 优先进入内存决策队列；终态仍由运行契约判定。 |
| run.cancelled | 请求方取得结果，不重复唤醒。 |
| executor.faulted/recovered | 优先报告控制权状态，恢复不等于完成目标。 |
| registry.checked/enabled/retired | 关联 artifact，不宣称已通过游戏测试。 |
| connection.changed | 报告连接变化，不推断游戏状态。 |
| 调试与 tick 统计 | 默认不逐条进入模型上下文，详细级别按需启用。 |

错误保留原始原因及必要位置。外部验收事件关联 bodyEpoch、runId、confirmationId、commandId、真实来源与简短依据；重复决定不重复产生终态，非法命令不产生 run.failed。外部确认不能标为游戏自动验证。证据摘要有界，不把所有 QueryOp 响应变为观测历史。

## 3. 当前状态、日志与内存预算

status 是当前进程状态的权威入口：health、connection、owner、activeRun、当前 act、pending switch、待确认请求、最近命令结果及对应事件游标；另报告 loggingUnavailable、droppedLogCount，不混入控制健康状态。日志可辅助人工诊断，不用于重建 status。

事件序号只在同 bodyEpoch 内比较。订阅可读取仍在内存环形缓冲中的事件，重复按 eventId 去重；超出保留范围返回 EVENT_GAP 并查询 status，不补造历史。新 epoch 不提供旧命令、旧确认请求或旧事件游标的恢复。

### 3.1 简单调试日志

日志使用 JSONL，字段至少包括时间、级别、模块、事件及适用的 bodyEpoch、runId、commandId、artifactId。记录启动/退出、命令结果、behavior/act 状态变化、错误和耗时；默认不逐 tick 输出，不记录凭据及无界完整对象。

采用单一有界异步写入队列追加文件。单段约 10MiB、总占用约 100MiB 为初始配置；达到限额时关闭并轮换文件，删除最旧的已关闭日志，包括当前 epoch 的旧日志。轮换不影响独立的内存状态或去重记录，不保留事务日志及停止专用磁盘额度。

accepted、completed 和运行终态均不等待日志落盘，也不要求 fsync。正常退出只在有限时间内尽力写完缓冲；异常退出允许丢失尾部记录或留下不完整的最后一行。首版不自动修复、截断或扫描日志来恢复运行，不建立持久索引。

写入失败、权限错误或磁盘已满时，设置 loggingUnavailable 并向 stderr/界面尽力报告，停止反复写入失败的文件，避免递归刷错；不因此拒绝正常业务或停止 behavior。日志状态独立于 executor health。可在下次人工启动重新尝试日志初始化。

缓冲积压优先合并/丢弃 debug 与重复进度；仍满时允许丢弃其他日志并累计 droppedLogCount，下一次可报告时给出摘要。错误日志也不承诺绝不丢失。stdout 只传协议，stderr 持续消费；stderr 自身背压时同样有界降级，日志从不阻塞执行器或收尾。

### 3.2 内存命令去重

当前 epoch 内，同 commandId 同内容返回已有结果，不同内容拒绝；进行中命令也先登记到内存，防止并发重复执行。accepted 表示内存中已受理，completed 表示本进程内该命令完成，不承诺重启后可查询。

内存记录独立于日志文件，日志删除、写失败或关闭均不影响去重。不在同 epoch 中淘汰一个已受理 ID 后把它当新命令执行。达到内存额度时拒绝新的普通业务，保留停止/退出处理额度；必要时受控关闭，而不是无限增长或静默忘记命令。对未知命令不推断它从未执行，不自动换 ID 重做。

body 重启后生成新 epoch，内存命令记录为空，拒绝携带旧 epoch 的请求；不从日志恢复命令，也不自动重放。人工启动新任务前读取当前环境，未确认的旧结果保持未知。

### 3.3 有界队列与停止优先

以下是首版实现起点，可由开发者配置；计数和字节预算先到者生效，需软件压力测试。日志预算不承担可靠消息存储。

| 资源 | 初始上限 | 满载处理 |
| --- | --- | --- |
| 普通待处理请求 | 32 条／4MiB | 明确返回未受理过载错误，不隐式排无限队列。 |
| 普通在途 QueryOp | 16 个／合计 16MiB 结果预算 | 拒绝新增，无隐藏重试；清理查询另预留 4 个名额及 4MiB。 |
| 构建 | 1 个执行、2 个等待；等待载荷合计 4MiB | 返回 BUILD_BUSY。 |
| 普通协议输出 | 64 条／4MiB | 合并进度、停止接受新增普通工作；持续无法发送时按传输故障清理退出。 |
| 停止、shutdown、heartbeat 与清理管理消息 | 独立预留 16 条／256KiB | 紧凑消息、重复停止合并；收尾结果使用预留通道，不能被普通请求占满。 |
| bridge 待投递事件 | 128 条／4MiB，仅内存 | 优先合并/淘汰进度；仍满则报告反馈缺口，按当前 status 汇总，不增长无界队列。 |
| 日志缓冲 | 256 条／1MiB | 合并/丢弃并计数，不影响业务。 |
| 当前 epoch 命令记录 | 10,000 条／16MiB | 拒绝新增普通业务；停止/退出另用上述预留额度，预留也无法处理时自主清理关闭。 |

消息仍受单条 1MiB 上限；优先管理消息须紧凑，不能借它携带源码或大查询结果。清理查询的结果预算与紧凑管理消息预算分别计量。大小在入队前核验，已有请求的结果也要受限；超限返回明确错误，不把截断结果当完整成功。构建只入队路径与摘要，不复制无界源码。

stop、shutdown、heartbeat 不能依赖普通队列腾空。优先级作用于未发送消息，不能让已写入管道的字节插队；限制提前发送的缓冲，并让 body 的自主存活检测与 broker 清理独立于 stdout。需要持续控制登记的未决操作也必须有界，超限拒绝新操作，不能丢弃已有控制账本。

事件尽量在编号前合并；已编号事件被内存缓冲淘汰后保留缺口信息。运行终态仍保存在当前进程的命令/run 记录中，不能仅因某条通知被丢弃就伪造成功或重复执行。首版不承诺事件一定被模型读到。

## 4. bridge 的事件整理与唤醒

bridge 使用可单测的内存队列模块，分类/合并逻辑与 DSH 注入调用分开，模型不进入 body tick 等待路径。

| 输入 | 首版规则 |
| --- | --- |
| 人类在 DSH 发送消息 | 走 DSH 原有会话路径，不被 P2 自动预算吞掉。 |
| behavior 终态/受阻 | 300ms 合并窗口，形成事实摘要和决策问题。 |
| 控制故障 | 优先提示，同一故障不连续唤醒。 |
| 一般进度 | 最短 5s 合并，通常随下一次自然回合提供。 |
| tick、重复 waiting | 不进入 session。 |

自动决策初始最多 3 次/分钟、突发预算 1 次；已有模型回合时合并到下一步上下文，只保留一个待唤醒意图。预算耗尽时在有界内存队列中保留/合并摘要，超限按 §3.3 报告缺口，不宣称无限期保留全部终态通知。

确认请求按 bodyEpoch、runId、confirmationId 合并；暂时无法判断不自动催问。管道有效时可通过 status 取回当前请求；插件退出或 body 重启后不恢复旧通知/请求。owner 授权撤销和存活超时仍触发停止，与日志可用性无关。

## 5. 首版投递与会话关联

首版只处理当前进程内的有序事件和有界重读，不实现持久 pending 队列，不发送代表“已可靠保存”的 events.ack。events.subscribe 与 status 用于当前 epoch 的订阅和缺口后的同步；不承诺跨崩溃至少一次投递。

bridge 使用内存批次标识去重/合并，并展示来源；注入成功不等于模型已经阅读。插件退出后未投递通知可以丢失，不从调试日志或 DSH 日志自动重建投递状态。DSH 已正常保存的会话消息由宿主自行管理；P2 不承诺跨系统 exactly-once。

投递绑定 ownerSessionId、bodyEpoch 和适用 bindingId。换 session 先关闭旧 body 再人工 start，不能将旧会话消息、运行或确认请求静默迁移。可显式提供人工整理的目标摘要；当前进程已知的未决控制仍须先清理，不因取消崩溃恢复而绕过停止规则。

游戏文本始终是观测数据；未来接入游戏聊天仍需核验玩家身份和授权。bridge 只释放自己创建的进程、工具和内存队列，不销毁用户已有 agent。

## 6. 人格、目标与跨 session 记忆

显式的长期目标、偏好、源码和 artifact 文件仍可保存；日志简化不删除这些用户资料，也不改变 D4 的不可变产物与启动核验。

```text
project-state/
  persona.json
  goals.json
  memories/
  session-links.json
```

结构化文件带 schemaVersion 和来源，修改用原子替换保存；明确区分事实、承诺与假设。人工 start 可读取已保存目标及偏好，再查询当前环境决定新 behavior；不能把历史文件或未完整的日志当成上次运行已经完成的证明。compaction 不是长期记忆的唯一载体。

## 7. 异常退出与后续恢复功能

| 情况 | 首版处理 |
| --- | --- |
| 人工 /p2 stop、插件卸载/热重载 | 尽力完成控制收尾、回收进程，有界刷新日志；重载后保持未启动。模型 stop 仅停止行为，body 保留。 |
| EOF、输出失效、bridge 存活超时 | body 能继续执行时主动停止并退出，不等待日志成功。 |
| runner 崩溃且 body 存活 | 依据内存控制账本清理；业务失败与清理故障分开。 |
| body/DSH 崩溃或机器重启 | 不恢复命令、节点栈、控制账本或待投递队列；日志仅供人工查看，新 body 空运行并使用新 epoch。 |
| 游戏断连/换世界 | 运行时现有失效与停止规则仍生效；旧引用不可使用。 |
| 日志不可写或缓冲溢出 | 报告 loggingUnavailable/丢弃计数，继续正常业务；不视为控制故障。 |

存活的 bridge 可以将观察到的异常退出显示为 interrupted/结果未知，不能保证宿主也崩溃时还能留下该记录。新进程仍做正常启动与连接核验，但不读取旧日志执行自动对账、恢复或归档；未确认的游戏控制问题由开发者/人类检查，不能用“已重新启动”证明旧控制已经停止。异常断管后的尽力停止与进程树回收仍须验证。

以下单列为后续功能，实施前重新设计：关键记录同步落盘、持久命令索引、日志尾部修复与完整性恢复、事务提交/在线压缩、持久通知队列与 ack、跨崩溃状态对账。后续 [WS 设计](WS-FUTURE.md)中的可靠投递设想依赖这些能力，不默认属于首版。

## 8. 调试与回放边界

首版提供尽力而为的日志阅读与当前进程状态查询。日志可能不完整，不能保证完整执行轨迹、自动故障恢复或整局确定性回放。开发者可以用受控输入测试执行器，这不要求将真实游戏输入全部录制。

## 9. 指标与验收

记录必要的 tick/query/act 耗时、失败原因、队列占用、过载拒绝数、droppedLogCount 和日志可用状态。accepted 的延迟目标不包含可靠落盘承诺，也不是硬实时 SLA。

首版验证：日志目录不可写/磁盘满时行为和停止仍正常；日志轮换不影响内存去重；缓冲满会丢弃并计数而不阻塞；终态响应不等日志；崩溃尾部可残缺且不触发自动修复；重启拒绝旧 epoch 并不恢复通知；普通请求/构建/输出满载时停止与心跳仍可处理。持久化恢复故障注入不作为首版退出条件。

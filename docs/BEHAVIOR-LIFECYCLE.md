# behavior／act 编写、检查、启用与迭代

> 本文规定 behavior／act 的编写、检查、代码隔离、产物启用与反馈迭代流程。检查器保持被动，不依赖真实游戏，也不承担游戏模拟测试。
>
> 关联：[主架构](ARCHITECTURE.md)、[契约](CONTRACTS.md)、[运行时](RUNTIME.md)。

## 1. 两种扩展与一条维护路径

| 内容 | 作者 | 启用路径 |
| --- | --- | --- |
| behavior | 人类或 agent | 源码 → 静态/构建检查 → 不可变 artifact → 注册 → 显式启动。 |
| act | 人类或 agent | 源码及能力声明 → 类型/打包检查 → 隔离运行包 → 注册 → behavior 引用。 |
| operation | 基础库维护者，AI 可协助写候选 | 库开发、独立测试、兼容验证与版本发布；游戏中 agent 不能自动安装。 |

behavior 不承担 op 实现，act 只用已发布 op。缺能力时返回 CAPABILITY_MISSING 及最小能力需求，agent 可以改变目标或提出基础库变更，不能绕过 broker 使用原始游戏 API。

## 2. 候选及产物生命周期

```text
draft → checking → checked → enabled
             └─→ rejected
enabled → retired（不再允许新运行，已有运行按约定结束）
```

运行实例、源码版本和产物状态分开。编辑文件产生新的源码 revision；相同源码改用其他依赖或 binding 可以产生不同 artifactId。checked/enabled/retired 跟随确切产物及目标 binding，不将同一 revision 的所有构建混为一体。检查通过不是自动启用，启用也不是开始游戏动作。

默认允许绑定 owner 的 agent 请求检查、注册 behavior／act 并切换行为，前提是已有的人类启动授权及受限运行环境均成立；不为每次可逆扩展强加人工确认。插件安装、body 管理、operation 升级仍走人类管理面。

## 3. 检查请求

请求给出工作区内源路径、预期 sourceDigest、目标 bindingId、artifactKind 和确切依赖选择。先读取不可变源快照，摘要不符返回 SOURCE_CHANGED；符号链接或相对路径不能越出允许源码目录。构建前固定本次依赖清单，只使用本地已锁定的模块和环境静态声明，不能现场联网安装或在构建中追随 latest。act 依赖选择属于内容清单，不再放进环境 binding。

可在当前 run 继续使用旧 act 时检查新 act/behavior，也可被动检查另一个 binding 的候选；检查不切换加载环境。未通过检查的候选依赖不能提供可复用的通过凭据，所需检查必须覆盖候选及其闭包；无关的旧产物不因此重查。

| 阶段 | 检查范围 | 不执行的工作 |
| --- | --- | --- |
| 解析 | TS/JS 语法与允许的模块格式 | 不推断玩家意图。 |
| 类型 | builder、act hook、op 参数/返回值、依赖声明 | 不证明算法终止或行为有效。 |
| 构建 | 有界执行 behavior 构建入口，生成并解析 IR；act 则打包代码和声明 | 不启动 act hook，不调用 QueryOp/ControlOp。 |
| 产物接受 | 必需声明、节点结构、schema、引用、依赖闭包、体积限制 | 不模拟环境，不向游戏试请求。 |

类型与产物接受检查覆盖 assign 的可写目标和表达式类型、query/act 输出与 local schema 的匹配，以及子树参数、局部帧和返回映射的合法性。拒绝写只读参数、跨帧直接写入、共享可变 locals 和隐藏的运行时回调。检查不证明作者的累计指标符合玩家目标；结果归属、成功收尾及观测时效仍由运行时验证，见[数据流契约](CONTRACTS.md#32-显式赋值与成功输出)。

构建检查不是“执行任意源码看是否报错”。只开放 builder-sdk、可审核纯辅助库和虚拟输入引用；禁止实际游戏/DSH连接。源代码可能在模块顶层计算，因此导入和构建都在隔离构建环境完成。

检查超时、内存预算耗尽、无法加载或不能产生合法IR均为检查失败。报告包含阶段、code、源码位置/节点路径、依赖信息和修复提示，不直接改源码或触发模型会话。

首版起点：构建总时间 10s、受限引擎内存 128MiB、构建进程外部上限按运行平台配置；最多 10000 节点、深度64。这些是防止检查器被无限循环拖住的工程预算，不是行为正确性测试。

## 4. 构建及 act 的代码隔离

body 的可信调度器不能与生成代码共用一个可被无限循环占住的 JavaScript 执行栈。设计要求为“独立进程 + 受限 JS 执行上下文 + 显式能力桥”：

- 构建上下文仅注入 builder 与纯函数；运行上下文仅注入当前 act 的 query/control桥、时钟及必要数学操作。
- 没有 Node process、fs、网络、子进程、原生模块或 DSH 对象，不继承用户会话凭据。
- module loader 仅加载产物中的已锁定模块，禁止任意路径、动态包获取及逃出产物目录。
- 每次 hook 有执行预算和独立的外部无响应监测；进程可终止，但终止后依然由 broker 完成控制清理。
- 单个 runner 串行执行一个 act，辅助函数复用不引入多行为控制权。

具体嵌入式 JS 引擎作为实现技术选型保留验证门槛：必须支持中断/内存限制、明确宿主绑定及异步任务调度，QuickJS/WASM 类实现可调查。未验证前不得把“子进程”或普通 JS context 宣称为完整安全隔离，也不得直接在 body 中 eval 生成代码作为替代。

这是运行环境的验收要求，不扩大被动检查器职责。首个实现阶段可以只启用维护者内置 act，并完成 behavior 构建隔离；只有满足上述门槛后才开放 agent 自定义 act 的自动启用。最终系统仍保留自定义 act 能力，阶段限制必须对 agent 明示。

## 5. artifact 与检查凭据

revision 标识源码，artifactId 标识确切可执行产物；sourceDigest、bindingId、artifactDigest 的输入与排除项统一按 [D4 摘要规则](OPERATIONS-AND-RELEASE.md#32-身份与摘要规则)处理。artifactId 直接由 artifactDigest 形成，检查凭据另外绑定 artifactDigest、bindingId 和 checker 版本。产物摘要已覆盖精确依赖闭包；检查时间作为凭据元数据，不参与产物身份，也不能仅按文件名或 revision 缓存“通过”。

产物目录只读保存，启用时复核摘要、目标 binding 与依赖凭据。目标 binding 可以不同于当前加载环境，但须有本地静态声明，不能因启用而加载 provider。失败返回详细差异，不悄悄降级旧依赖。源码变化、依赖选择变化、契约/环境变化要求重新检查采用这些变化的候选及闭包；首版可完整重查待启用包，不将新增 act 扩大成全库重查。

注册表按目标 binding 保存各 artifactId 的 checked/enabled/retired 状态，并可维护 `(bindingId, definitionId)` 到默认 enabled artifactId 的发现映射；多个旧/新产物可同时 enabled。默认映射只用于选择，请求进入执行器前须解析为确切 artifactId；运行期间不再读取 latest。behavior 的 act 引用与其传递依赖也锁定确切内容，不能把同名或同 revision 的不同产物互换。

某 act 产物退休后，依赖它的 behavior 即使仍显示 enabled，也不得新启动；注册表应显示阻断原因。已有 run 保留原依赖闭包继续按约定结束，包括该 run 后续节点对原 act 的使用；退休本身不发出停止请求。依赖产物保留供当前 run、诊断及受控回滚使用；回滚需重新满足检查与启用要求，不通过默认版本回退偷偷替换引用。

## 6. 启用与切换的事务边界

1. activate 明确指定 artifactId；校验 owner、产物及目标 binding 下的检查凭据。
2. 验证本地不可变依赖闭包及其启用资格；所引用的 act 产物须在同一目标 binding 下已检查并启用，退休依赖不能通过。纯辅助库核验锁定内容及允许模块规则，不单独要求 enabled 状态。检查不连接游戏，不为其他目标 binding 加载 provider。
3. 原子提交该目标 binding 下的 enabled 记录及所需默认映射，记录启用事件。
4. 用户/agent 显式请求 switch(artifactId, params, commandId)；复核参数、摘要、闭包启用状态、凭据、当前加载 binding 与实际能力，并准备 runner 所需不可变模块。此时不得有游戏动作，目标环境不符或候选无效均不能停止旧行为。
5. 执行器先停止旧行为并确认收尾，再启动新运行；授予新控制权前再次核验候选及依赖资格，失败不假称新行为已接管，也不改选其他版本。

启用失败保留旧enabled映射。切换期间旧行为已经停止而新行为启动失败时，保持无主动行为并报告；默认不自动恢复旧行为，因为它可能不再适合世界状态。

撤销启用不会自动停止当前实例；管理接口必须明确是“禁止新运行”还是“同时请求停止”。operation升级更严格：先结束所有依赖该provider的运行并确认清理，再切换binding，首版无热更新。

## 7. 默认恢复与上报

缺省行为为：失败传播、零行为重试、不自动换目标。作者使用 recover 声明可恢复码和预算；结束时清理仍遵循独立的最多一次追加重试规则。

外部输入不足可显式 blocked，无控制权，事件标明 needsDecision=true。不能把任何未知错误都归 blocked 无限等待；默认未声明的错误终止失败。模型不在线时blocked保持，body不现场生成策略。

配置文件只有参数不含任意运行脚本。agent改参数先经过schema校验；修改运行中的参数采用新实例切换，不直接改变当前act正在使用的参数对象。

## 8. 游戏内反馈迭代循环

真实反馈循环独立于检测器：

```text
运行结果／玩家意见
   → agent读取当前事实与关联revision
   → 判断是环境阻碍、目标变化、能力缺失还是实现错误
   → 选择现有behavior、改参数或写新revision
   → 被动检查 → 显式启用/切换 → 新的实际反馈
```

同一次普通环境失败不自动将artifact判为坏代码或停用。代码异常可使本次run失败并留下诊断；是否修复/退休由agent或维护者决定，不启动隐藏代码自进化循环。

一次决策回合最多提交一个待启用候选；连续3次检查失败默认停止自动修复链，汇总原因给当前session。这个上限属于bridge/agent调度配置，不是检测器内部调用模型的次数。行为失败也受会话唤醒预算控制，避免游戏tick驱动无限模型回合。

## 9. 三类验证的明确分工

| 验证 | 拥有者 | 需要游戏吗 |
| --- | --- | --- |
| 用户behavior／act语法、类型、构建检查 | checker | 不需要，也不模拟。 |
| runtime状态机、消息去重、预算、停机等软件测试 | P2开发者 | 用人工构造的接口结果验证核心，不属于用户checker。 |
| operation契约与游戏兼容测试、行为体验试验 | 库维护者/游戏内反馈流程 | 需要对应游戏候选环境，单独执行。 |

检查通过仅保证产物在绑定契约下可被执行器接受；不保证每一条代码路径不会异常、查询一定成功、游戏目标可达或自动生成代码可信。

D4 软件验收覆盖：A 锁定 H1 运行时检查/启用 H2 不影响 A；B 显式引用 H2 后得到独立 artifact；同源码换依赖或 binding 保留源码 revision 但改变 artifactId；重复检查不改变产物身份；退休 H1 阻止依赖它的新 run，却不替换 A 的后续节点；另一 binding 的候选可静态检查/启用，但环境不符时 switch 拒绝且不停止当前行为。
